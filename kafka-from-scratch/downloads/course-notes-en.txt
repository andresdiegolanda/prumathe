KAFKA FROM SCRATCH. COURSE NOTES
Apache Kafka 4.1.2 | 2026-10-18 | v1.3.0

WHAT KAFKA IS
=================================================================
What it is, where it came from, where it fits and where it does not. Read it once; the lessons do the rest.

A log that many read at their own pace
Kafka is an event streaming platform: a service that stores events in order, keeps them for as long as you decide, and lets any number of programs read them, each at its own pace. The unit is the record: a key, a value and a timestamp, appended to a partition of a topic and never modified.
That is the difference from a queue. In a queue a message is consumed and disappears; in Kafka reading moves a bookmark, the offset, and the event stays. Two teams can read the same history for different reasons, a new system can start from the beginning, and a bug can be fixed by reprocessing.
→ A message is consumed; an event is read.

Where it came from
Kafka was built at LinkedIn to absorb the stream of activity events from its website, page views and searches among them, which the message brokers of the time could not take at that volume without slowing down or losing the ability to scale out. The design bet was to put the ordered, append-only log at the center of the architecture instead of connecting every system to every other one.
LinkedIn released it as open source in January 2011; it entered the Apache Incubator in July 2011 and became a top level Apache project in October 2012. Its creators, Jay Kreps, Neha Narkhede and Jun Rao, later founded Confluent, the company built around it. Since then the changes that matter most to how it is used are the ones on the timeline.
2011 Open source: LinkedIn publishes Kafka in January; Apache Incubator in July.
2012 Apache project: Top level project since October.
2017 Transactions: Version 0.11: idempotent producer and transactions, the basis of exactly once processing.
2022 KRaft: Version 3.3 marks KRaft, the metadata quorum without ZooKeeper, as production ready.
2025 Kafka 4.0: First major release without ZooKeeper; the new consumer rebalance protocol is generally available; early access to queues (share groups).
2026 Share groups: Version 4.2 makes share groups production ready: acquisition and acknowledgment per record, the queue pattern inside Kafka.

Where it fits
The official documentation lists its use cases. These are the ones you will meet in event driven systems and enterprise integration.
- Integration between systems that must not know each other: A producer publishes a fact once; any number of consumers subscribe, today or next year, without the producer changing.
- Replayable history: Reprocess after a bug, audit what happened and in what order, feed a new system with the past.
- High volume ingestion: Activity tracking, metrics and log aggregation: many writers, sustained throughput, consumers that fall behind without losing data.
- Change data capture and outbox: Turn database changes into events other systems can react to, with the atomicity the business change needs.
- Stream processing: Transform, join and aggregate events as they arrive, with state that survives restarts (Kafka Streams).
- Event sourcing and commit log: Record state changes as an ordered sequence of events and rebuild state from it; replicate state between the nodes of a distributed system.

Where it does not fit
This part is the course’s judgment, not official documentation. Each row says what to use instead.
- Request and response: A caller that needs an answer now gains nothing from a durable log in between and pays with latency and complexity. Use instead: An HTTP or gRPC API.
- Task queues with priorities, delays or per message discard: A partition is an ordered log: no priority, no scheduled delivery, no deleting one message. Share groups add acknowledgment per record, not priority or delay. Use instead: A task queue such as RabbitMQ or SQS, or a table with a worker.
- A database to query: Kafka stores and delivers; it does not search, index or answer “what is the current value of x” without a consumer that builds that view. Use instead: A relational or document database, fed from Kafka if you want.
- Large payloads: Images, PDFs and videos inflate the log and the network for every consumer; the default record limit is about 1 MB for a reason. Use instead: Object storage for the bytes and an event with the reference.
- Global order across different keys: Order is guaranteed within a partition. One partition gives global order and no parallelism; several give parallelism and order per key only. Use instead: Design around keys, or a single writer with a sequence number if the volume allows it.
- A small system: Two services and a few thousand events a day do not pay for a cluster that someone has to operate, upgrade and watch. Use instead: A table, a transactional outbox or the queue your cloud already gives you; Kafka later, if the volume or the number of consumers grows.

How to decide
1. Will more than one consumer need the same fact, now or later?
2. Will you need to go back: replay, audit, rebuild?
3. Does order per key matter?
4. Does the volume, or the number of producers and consumers, justify a cluster?
5. Who will operate it, and do they know it will not run itself?
Three yes answers and you are in the right place. Lesson 00 shows how the course works and leaves Docker ready.

02. An event is a fact
=================================================================
Keep what happened. Let each reader decide what to do.

Write the past tense
OrderPlaced records a fact that already happened. ShipOrder is a command asking someone to act. Our fictional café publishes orders once so billing and the kitchen can react independently.
→ A useful event says what happened, to which entity, and when.

Append; do not overwrite
A partition is an ordered log. New records go at the end. Reading a record does not remove it, so two applications can read the same history at different speeds.
→ Consumption and deletion are separate decisions.

Replay has a boundary
A new reader can replay retained records. It cannot recover records already removed by retention. Replaying a payment event must not charge a customer again: external effects need their own deduplication.
→ A log lets you reread history; it does not undo side effects.

03. Inside a record
=================================================================
Key, value, timestamp, headers. Four different jobs.

The envelope and the payload
The key often identifies an entity: order-42. The value holds the fact. Kafka stores bytes, not a mandatory JSON structure; a serializer turns application values into those bytes.
→ A key is not a unique-record constraint.

Context travels with the fact
Headers can carry a trace ID or schema version. A timestamp can represent producer creation time or broker append time, depending on topic settings. Event time inside the payload can be different again.
→ Be explicit about which clock a timestamp describes.

The address arrives later
Kafka assigns a partition offset after appending a record. Topic + partition + offset identifies a log position, not a universal business event. The same fact can be republished at another position.
→ Use a separate event ID when business deduplication matters.

04. One topic, many logs
=================================================================
A partition is the unit of order and parallel work.

Name the stream
A topic is a named stream, such as orders. It is divided into partitions. Each partition has its own sequence of offsets, so offset 4 can exist in partition 0 and partition 1.
→ An offset only has meaning inside its partition.

Scale by splitting work
Different partition leaders can live on different brokers. Clients can read or write several partitions in parallel. More partitions also mean more metadata, files, replication and recovery work.
→ Partition count is a design choice, not a free speed dial.

Do not invent a global order
Kafka preserves the log order within a partition. It does not promise an order across partitions. If two events must stay ordered, design their keys and producer behavior for the same partition.
→ Partition 0 offset 8 is not “before” partition 1 offset 3.

05. Keys choose a lane
=================================================================
Keep related facts together without creating a hot spot.

Hash the serialized key
The standard Java producer hashes a non-null serialized key with Murmur2, takes a positive value, and applies modulo partition count. Identical bytes map to the same partition while that count stays fixed.
→ Same key bytes + same partition count = same partition.

Choose the ordering boundary
An order ID groups one order’s events. A store ID groups a whole store, which can overload one partition. A null key follows the client’s partitioning strategy; do not assume round-robin.
→ Choose the smallest entity whose events need ordering.

Adding lanes can move keys
Changing partition count changes the modulo result for many keys. Earlier records remain in their original partitions. A migration may need a new topic and a deliberate cutover.
→ Adding partitions does not redistribute old records.

06. The producer’s waiting room
=================================================================
Batching, compression, acknowledgments and timeouts.

Collect a batch
send() typically places a record in the producer’s buffer. The producer batches records by destination partition. batch.size and linger.ms influence how full a batch becomes before it is sent.
→ Calling send() is not the same as a successful acknowledgment.

Trade latency for efficiency
Larger batches and compression can reduce network and disk work. Waiting to fill batches can add latency. Measure with your event size, key distribution and latency budget.
→ Throughput without a latency target is an incomplete result.

Handle success and failure
Use callbacks or futures to observe completion. acks controls broker confirmation; delivery.timeout.ms bounds delivery attempts. A timeout can leave an uncertain outcome: the write may have reached Kafka.
→ A retry needs a duplicate strategy.

07. One stream, independent teams
=================================================================
Share the work within a group. Share the history across groups.

Give an application a group ID
Consumers with the same group.id cooperate. In an ordinary consumer group, a partition is assigned to at most one member at a time. That member can own several partitions.
→ The group is the logical subscriber.

Parallelism has a ceiling
Three partitions can keep at most three group members busy reading them. A fourth member waits without an assignment. This says nothing about threads used after polling; those require careful ordering and commit design.
→ More consumers than partitions does not increase read parallelism.

Let another team join
Kitchen and billing use different group IDs. Each group reads all the retained orders independently and stores its own progress. They do not take events away from one another.
→ Same group: divide work. Different groups: independent reads.

08. A bookmark, not a receipt
=================================================================
Position, committed offset and lag are different measurements.

Track the next record
A consumer’s position is the next offset it will fetch. Its committed offset is the durable bookmark used after a restart. Commit 3 means “resume at 3,” not “record 3 is complete.”
→ After processing offset n, usually commit n + 1.

Measure distance
For a simple log, lag is log-end offset minus committed offset. It measures distance in offsets, not seconds or business completion. Gaps from compaction or transactions mean it is not always an exact record count.
→ Low lag can coexist with wrong business results.

Reset with intention
auto.offset.reset applies when no valid committed offset exists. It does not override a valid bookmark. To replay a group, stop its members and deliberately reset its offsets.
→ earliest does not mean “start over every time.”

09. When the team changes
=================================================================
Membership, assignment, heartbeats and processing time.

Join, leave, reassign
When members join or leave, the group redistributes partitions. A coordinator broker manages group membership. Committed offsets let a new owner resume a partition.
→ Partition ownership can change while the process is alive.

Alive is not the same as progressing
Heartbeats show membership liveness. max.poll.interval.ms limits how long a consumer may go between polls. A long processing batch can lose its assignment even if the host is healthy.
→ Bound processing time and handle partition revocation.

Know which protocol you run
Kafka 4.x supports the newer consumer group protocol with server-side assignment. Clients must opt in with group.protocol=consumer. Classic cooperative assignment is a separate mechanism; this lab explicitly uses classic.

10. Copies that follow a leader
=================================================================
A partition can survive the loss of a broker.

One leader per partition
The leader handles writes for a partition. Follower replicas fetch its log. A replication factor of three means three copies on three brokers, not three partitions.
→ Partitioning divides work; replication copies it.

Track the in-sync replicas
ISR is the set of replicas considered in sync with the leader. A slow or failed follower can leave it. Replica placement and failure domains determine which failures your copies can survive.
→ Three copies on one laptop still share one laptop’s fate.

Promote an eligible replica
When a leader fails, Kafka can elect another eligible replica. Clients refresh metadata and retry. Availability depends on controller quorum and the remaining eligible replicas, not just on a replica count.
→ Failover is a protocol, not an instantaneous switch.

11. What does “saved” mean?
=================================================================
acks, minimum ISR and the price of staying available.

Choose the acknowledgment
acks=0 waits for no broker response. acks=1 waits for the leader. acks=all waits for the in-sync replicas required by the write protocol. None of these means a consumer processed the event.
→ Producer acknowledgment is a storage guarantee, not a business receipt.

Set a floor for safe writes
With acks=all, min.insync.replicas=2 requires at least two ISR members. If the ISR shrinks below two, writes fail. With acks=1, this setting does not force two replicas to acknowledge.
→ acks=all and min.insync.replicas work together.

Prefer an explicit failure
A replication factor of three and minimum ISR of two can keep accepting writes after one replica loss. Refusing writes under worse conditions protects the chosen durability contract. It is not a substitute for backups or tested recovery.
→ An unavailable write can be safer than an acknowledged loss.

13. History has a horizon
=================================================================
Segments, retention time and the earliest readable offset.

Write in segments
Kafka appends records to an active log segment. Older segments become eligible for cleanup. Time retention and size retention limit stored history; size limits apply per partition.
→ Deletion works on segments, not on individual record timers.

Let the beginning move
When old segments are deleted, the earliest offset advances. Offsets are not renumbered. A consumer whose bookmark is now too old needs an offset reset policy or a recovery decision.
→ A slow consumer does not prevent ordinary retention deletion.

Budget recovery time
Retention must cover outage time, detection time and catch-up time, with room for growth. Tiered storage can extend storage options when configured with a compatible remote storage implementation; it is not an automatic backup.
→ Your recovery plan must finish before the history disappears.

14. Keep the latest known value
=================================================================
A log can also rebuild a table.

Interpret keys as rows
A compacted topic eventually retains at least the latest value for each key, subject to tombstone handling. Consumers can rebuild current state by applying changes in partition order. Compaction does not happen at write time.
→ Compaction is asynchronous cleanup, not an upsert API.

Leave a deletion marker
A record with a non-null key and a null value is a tombstone. It tells a rebuilding table to remove the key. Tombstones themselves can be removed after delete.retention.ms. The string "null" is not a null value.
→ A deletion has to travel before its marker disappears.

Keep the addresses stable
Compaction leaves gaps but preserves the order and offsets of surviving records. With cleanup.policy=compact,delete, retention can also remove segments, including the latest value of a key.
→ A compacted log is a change history with a cleanup policy.

15. The crash between two actions
=================================================================
Process, commit, crash. The order changes the guarantee.

Commit before the effect
If the application commits the input offset and then crashes before its effect, the restarted consumer skips work. This is the at-most-once risk: a record may be processed zero times.
→ A bookmark ahead of work can lose work.

Commit after the effect
If the effect succeeds and the app crashes before committing, the record is read again. This is the at-least-once tradeoff: duplicates must be safe. Auto-commit is not proof that business work completed.
→ An offset commit and a database write are separate transactions.

Plan for poison events
Bound retries. A dead-letter topic can preserve failed events with error context, but publishing there and committing input must be coordinated. Routing around one event can break entity ordering; decide deliberately.
→ A dead-letter topic needs an owner and a replay procedure.

16. Two different kinds of duplicate
=================================================================
A network retry is not a repeated business request.

Make producer retries safe
An idempotent producer uses a producer identity and sequence numbers. Kafka can recognize retrying the same batch and avoid appending it twice within that protocol. It requires compatible acks, retries and in-flight settings.
→ Enable idempotence explicitly when teaching or reviewing a configuration.

Two send calls are two writes
Calling send() twice with identical key and value creates two logical records. Restarting an application and resending a business request is also not automatically deduplicated by producer idempotence.
→ Idempotent production is not business deduplication.

Choose a business identity
An idempotent sink records a stable event ID together with its effect in one atomic database transaction. A unique constraint can reject reapplication. An in-memory set is only a demo: it disappears on restart.
→ The deduplication record and the effect must succeed together.

17. Make the boundary atomic
=================================================================
Output records and input offsets can commit together.

Begin, write, commit or abort
A transactional producer can write to multiple partitions atomically. A stable transactional.id fences an older producer instance using the same identity. Aborted records may exist physically but are hidden from read_committed consumers.
→ Physical presence and committed visibility are different.

Commit progress with output
A Kafka-to-Kafka processor writes its output and calls sendOffsetsToTransaction with the next input offsets and group metadata. The transaction commits both, or neither. Disable input auto-commit.
→ Exactly-once processing requires the whole read-process-write protocol.

Name what is outside
Kafka transactions do not include an email, a payment API or an arbitrary database transaction. read_committed waits behind open transactions at the last stable offset; this can affect apparent lag and latency.
→ “Exactly once” must always name its boundary.

18. A contract that can evolve
=================================================================
Bytes need an agreed meaning.

Separate storage from meaning
Kafka brokers accept bytes; they do not inherently validate your JSON business fields. A schema defines the contract. A registry stores schema versions and checks compatibility according to configured rules.
→ A registry is an ecosystem component, not the Kafka broker.

Ask who must read whose data
Backward compatibility means a new reader can read data written with the old schema. Forward compatibility means an old reader can read new data. Full requires both. Transitive modes compare against all prior registered versions.
→ Compatibility direction is about reader and writer versions.

Evolve deliberately
In Avro, adding a field with a suitable default can let a new reader consume older data. Changing a string field to an incompatible type can fail. Wire framing and schema-ID placement depend on the registry and serializer.
→ A compatible schema change can still change business meaning.

20. From a database to an event
=================================================================
CDC captures changes. An outbox gives them business intent.

Capture the database’s log
Change data capture reads committed database changes, often starting with a snapshot then streaming a transaction log. Inserts, updates and deletes are database facts, not automatically well-designed business events.
→ CDC is not the same as event sourcing.

Avoid the dual-write gap
Writing a database row and then publishing to Kafka creates a crash window. An outbox writes the business row and an event row in the same database transaction. A relay or CDC connector later publishes the outbox.
→ Atomic creation does not mean duplicate-free relay.

Preserve identity across retries
The outbox event ID survives relay retries. Consumers can deduplicate it. The lab uses PostgreSQL and a small polling relay so the crash boundary is visible; it is not a Debezium deployment.
→ An outbox solves atomic event creation; delivery still needs a policy.

22. Which minute does it belong to?
=================================================================
Event time, stream time, grace and joins.

Use the event’s clock
Processing time is when your code runs. Event time is when the event happened. Kafka Streams uses record timestamps by default. Its stream time advances with the maximum observed timestamp for the task; wall-clock waiting alone does not advance it.
→ Late arrival is measured relative to stream progress.

Give late events a budget
A tumbling window puts records into non-overlapping time buckets. Grace allows out-of-order events until the window closes relative to stream time. After that, a late record is dropped from the aggregation.
→ A longer grace period trades result finality for completeness.

Join on key and time
Stream-stream joins need matching keys and a time window. Stream-table joins enrich an event from table state under the chosen semantics. Co-partitioning and compatible key serializers matter. Unbounded waits create unbounded state.
→ A join is a state and time design, not just a SQL word.

23. Identity, permission, privacy
=================================================================
Authentication, authorization and encryption answer different questions.

Know who is connecting
TLS can encrypt connections and optionally authenticate clients with certificates. SASL authenticates a principal using mechanisms such as SCRAM or OAuth. A password on a plaintext connection is not confidentiality.
→ Authentication asks “who are you?”

Grant the smallest useful permission
ACLs decide whether a principal can perform an operation on a resource: read a topic, write a topic, use a group. Authentication alone does not authorize those operations.
→ Authorization asks “what may you do?”

Keep the lab boundary explicit
The main lab uses plaintext on an isolated Docker network and host ports bound to 127.0.0.1. The optional ACL broker uses SASL/PLAIN only on an internal network, with public demo credentials. It teaches authorization, not production security.
→ Production needs TLS, secret management, rotation and audited least privilege.

25. Scale the right dimension
=================================================================
Storage, throughput, partitions and consumers are separate budgets.

Estimate before provisioning
A first storage estimate is events per second × average serialized bytes × retention seconds × replication factor. Add indexes, metadata, headroom and uneven distribution; compression changes the actual footprint.
→ Estimate with units, then measure with your own payloads.

Find the hottest lane
Total topic throughput can hide a hot key. One key stays on one partition under the same partitioner and count. Splitting the key may increase parallelism but weaken the ordering boundary your application relies on.
→ A key design is also a capacity design.

Move replicas deliberately
Adding a broker does not by itself balance existing partitions onto it. Replica reassignment moves data and consumes network and disk capacity. Use throttling, monitor ISR and plan the rollback before large moves.
→ Capacity is usable only when data and work can reach it.

26. A second cluster is another system
=================================================================
Replication across clusters is a recovery design.

Distinguish replicas from mirrors
In-cluster replicas share a partition’s log identity. Cross-cluster replication copies events into another cluster with its own topic metadata and offsets. MirrorMaker 2 uses Kafka Connect to coordinate this work.
→ Offset 100 in one cluster need not be offset 100 in another.

Choose a recovery contract
RPO is the amount of data loss you can tolerate; RTO is how long recovery may take. Asynchronous replication can lag. Failover must handle client routing, group progress, schemas, permissions and application state.
→ A mirror without a failover drill is an untested assumption.

Make the lab’s limit visible
This lab runs a second single-broker cluster and a small one-shot copy client. It demonstrates offset independence and duplicates. It does not implement MirrorMaker 2 checkpoint translation, heartbeats or automatic failover.
→ Copying records is only one part of disaster recovery.

27. When work sharing is the goal
=================================================================
Share groups use record acknowledgments instead of partition ownership.

Change the unit of assignment
An ordinary consumer group assigns partitions to members. A share group can distribute records from the same partition among multiple consumers, with acquisition locks and acknowledgments.
→ Sharing a partition’s work changes processing-order assumptions.

Accept, release or reject
A shared record is temporarily acquired. Accept acknowledges completion; release makes it available for redelivery; reject marks it as not to be delivered again to that group. Failed or expired acquisitions can be redelivered.
→ A lock is not a successful business effect.

Respect the version boundary
In Kafka 4.1, the version this course pins, share groups are a preview that must be enabled; since Kafka 4.2 they are production-ready. Use the separate experimental broker; ordinary course labs use consumer groups.
→ A preview invites you to experiment; check the readiness of the version you run before relying on it.

docker compose run --rm http --fail-with-body -X POST http://spring:8080/orders/order-42 -H Content-Type:application/json --data-binary @/requests/order.json
docker compose run --rm http --fail-with-body http://spring:8080/received

Observe: After the listener catches up, two entries share the event ID and key but have different offsets.

5. Inspect committed progress
Wait until the populated partition has lag zero before the next step. Inspect application.yml: group-id, auto-offset-reset, enable-auto-commit and ack-mode.

docker compose exec kafka1 /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server kafka1:9092 --group spring-kitchen --describe

Observe: The populated partition has LAG 0. Empty partitions can show “-” (no committed offset). CURRENT-OFFSET is the next record to consume.

6. Restart the application
The in-memory observation list clears, but the group’s committed offsets stay in Kafka. earliest does not rewind a group that already has valid offsets.

docker compose restart spring
docker compose --profile spring up -d --wait spring
docker compose run --rm http --fail-with-body http://spring:8080/received

Observe: The list is [] after the restart: previously committed records are not replayed. Publish a new event to see the listener resume.

7. Stop and read the source
Stop the application when done. The complete project and a bilingual source walkthrough are in labs/spring/README.md. Design durable business deduplication before adding payments or another external effect.

docker compose --profile spring stop spring

Observe: The app stops; topic data and committed group offsets remain in the course broker volumes.

CHECKPOINT
1. KafkaTemplate.send succeeds. What does this prove?
A. The broker acknowledged the write under the producer settings
B. Every consumer processed the event
C. The business event can never be duplicated
Answer: A. The producer future describes the write. Consumer processing and business deduplication are separate concerns.

2. With enable-auto-commit=false and AckMode.RECORD, when is the next offset committed?
A. After the listener returns normally for that record
B. Before the listener runs
C. Every five seconds, by the broker
Answer: A. The container commits per record on a normal return. A crash between the effect and that commit can repeat the effect.

3. The listener throws. What does this example do?
A. Stops the listener and leaves the failed record uncommitted
B. Skips the record and commits
C. Sends the record to a dead-letter topic automatically
Answer: A. CommonContainerStoppingErrorHandler makes the failure visible and keeps the bookmark honest. Retries and a DLT are a separate design decision.
