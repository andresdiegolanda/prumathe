01. Tu primer clúster de Kafka
=================================================================
Un sistema chico y real. Un lugar para probar «¿qué pasa si…?».

Dale un trabajo a cada pieza
Un productor escribe eventos. Un broker los guarda. Un consumidor los lee. Docker ejecuta estos programas en contenedores aislados; un volumen conserva los datos cuando un contenedor se reinicia.
→ Un contenedor es un programa en ejecución. Una imagen es su receta.

Conectate desde el lugar correcto
Dentro de la red de Compose, los clientes usan kafka1:9092. Desde tu computadora, usan localhost:19092. Bootstrap encuentra el clúster; los listeners anunciados indican dónde conectarse después.
→ localhost dentro de un contenedor es ese mismo contenedor.

Hacé que el experimento se pueda repetir
El curso usa tres nodos con roles de broker y controlador, Kafka 4.1.2 y volúmenes con nombre. Los roles combinados achican el laboratorio; en producción se suelen separar los controladores. Todos los datos de ejemplo son ficticios.
→ Los diagramas simulan. Los laboratorios de Docker ejecutan Kafka real.

02. Un evento es un hecho
=================================================================
Guardá lo que pasó. Dejá que cada lector decida qué hacer.

Escribí en pasado
OrderPlaced registra algo que ya pasó. ShipOrder es un comando que pide una acción. Nuestro café ficticio publica cada pedido para que la caja y la cocina reaccionen por separado.
→ Un evento útil dice qué pasó, a qué entidad y cuándo.

Agregá; no sobrescribas
Una partición es un registro ordenado. Los mensajes nuevos van al final. Leer un mensaje no lo elimina: dos aplicaciones pueden leer la misma historia a velocidades distintas.
→ Consumir y borrar son decisiones distintas.

El replay tiene un límite
Un lector nuevo puede volver a leer los mensajes retenidos. No recupera lo que la retención ya borró. Releer un pago no debería cobrarlo de nuevo: los efectos externos necesitan su propia deduplicación.
→ Un log permite releer la historia; no deshace efectos externos.

03. Adentro de un mensaje
=================================================================
Clave, valor, timestamp y cabeceras. Cuatro trabajos distintos.

El sobre y el contenido
La clave suele identificar una entidad: order-42. El valor contiene el hecho. Kafka guarda bytes, sin exigir JSON; un serializador convierte los valores de la aplicación en esos bytes.
→ La clave no impone unicidad de mensajes.

El contexto viaja con el hecho
Las cabeceras pueden llevar un ID de traza o una versión de esquema. El timestamp puede ser de creación o de ingreso al broker, según la configuración. La hora del hecho dentro del valor puede ser otra.
→ Aclarale al lector qué reloj representa cada timestamp.

La dirección llega después
Kafka asigna un offset al agregar el mensaje. Tópico + partición + offset identifica una posición del log, no un evento de negocio universal. El mismo hecho puede publicarse otra vez en otra posición.
→ Usá un ID de evento propio si necesitás deduplicar hechos de negocio.

04. Un tópico, varios logs
=================================================================
La partición es la unidad de orden y trabajo paralelo.

Dale un nombre al flujo
Un tópico es un flujo con nombre, como orders. Se divide en particiones. Cada una tiene su secuencia de offsets: el offset 4 puede existir en la partición 0 y en la 1.
→ Un offset solo tiene sentido dentro de su partición.

Escalá repartiendo el trabajo
Los líderes de distintas particiones pueden vivir en distintos brokers. Los clientes pueden leer o escribir varias en paralelo. Más particiones también implican más metadatos, archivos, réplicas y trabajo de recuperación.
→ La cantidad de particiones es una decisión de diseño, no velocidad gratis.

No inventes un orden global
Kafka conserva el orden del log dentro de una partición. No promete orden entre particiones. Si dos eventos tienen que mantener su orden, diseñá las claves y el comportamiento del productor para la misma partición.
→ El offset 8 de la partición 0 no es «anterior» al 3 de la partición 1.

05. Las claves eligen un carril
=================================================================
Juntá los hechos relacionados sin concentrar toda la carga.

Calculá el hash de la clave serializada
El productor Java estándar aplica Murmur2 a los bytes de una clave no nula, toma un valor positivo y calcula módulo cantidad de particiones. Los mismos bytes van a la misma partición mientras esa cantidad no cambie.
→ Mismos bytes de clave + misma cantidad de particiones = misma partición.

Elegí el límite del orden
Un ID de pedido agrupa los eventos de ese pedido. Un ID de local agrupa todo el local y puede sobrecargar una partición. Una clave nula sigue la estrategia del cliente; no supongas round-robin.
→ Elegí la entidad más chica cuyos eventos necesiten orden.

Agregar carriles puede mover claves
Cambiar la cantidad de particiones cambia el resultado del módulo para muchas claves. Los mensajes anteriores quedan donde estaban. Una migración puede requerir un tópico nuevo y un corte planificado.
→ Agregar particiones no redistribuye mensajes anteriores.

06. La sala de espera del productor
=================================================================
Lotes, compresión, confirmaciones y tiempos de espera.

Armá un lote
send() suele dejar el mensaje en el buffer del productor. El productor arma lotes por partición de destino. batch.size y linger.ms influyen en cuánto se llena un lote antes del envío.
→ Llamar a send() no equivale a recibir una confirmación exitosa.

Intercambiá latencia por eficiencia
Lotes más grandes y compresión pueden reducir trabajo de red y disco. Esperar para llenar lotes puede agregar latencia. Medí con tu tamaño de evento, distribución de claves y presupuesto de latencia.
→ El throughput sin un objetivo de latencia es un resultado incompleto.

Atendé tanto el éxito como el error
Usá callbacks o futures para observar el resultado. acks controla la confirmación del broker; delivery.timeout.ms limita los intentos. Un timeout puede dejar un resultado incierto: la escritura pudo haber llegado a Kafka.
→ Un reintento necesita una estrategia para duplicados.

07. Un flujo, equipos independientes
=================================================================
Repartí trabajo dentro del grupo. Compartí historia entre grupos.

Dale un ID de grupo a la aplicación
Los consumidores con el mismo group.id cooperan. En un grupo común, cada partición se asigna a un solo miembro a la vez como máximo. Un miembro puede tener varias particiones.
→ El grupo es el suscriptor lógico.

El paralelismo tiene un techo
Tres particiones mantienen ocupados como máximo a tres miembros leyéndolas. El cuarto espera sin asignación. Los hilos que procesan después del poll son otro tema: exigen cuidar el orden y los commits.
→ Más consumidores que particiones no aumenta el paralelismo de lectura.

Sumá otro equipo
Cocina y caja usan IDs de grupo distintos. Cada grupo lee los pedidos retenidos por su cuenta y guarda su propio avance. No se sacan eventos entre sí.
→ Mismo grupo: reparten trabajo. Grupos distintos: lecturas independientes.

08. Un señalador, no un recibo
=================================================================
Posición, offset confirmado y lag son medidas distintas.

Seguí el próximo mensaje
La posición es el próximo offset que el consumidor va a buscar. El offset confirmado es el señalador durable para reiniciar. Confirmar 3 significa «retomá en 3», no «el mensaje 3 ya terminó».
→ Después de procesar el offset n, normalmente confirmás n + 1.

Medí la distancia
En un log simple, lag es offset final menos offset confirmado. Mide distancia en offsets, no segundos ni trabajo de negocio terminado. Los huecos por compactación o transacciones impiden que siempre sea un conteo exacto.
→ Puede haber poco lag y resultados de negocio incorrectos.

Reiniciá la posición con intención
auto.offset.reset se aplica si no hay un offset confirmado válido. No reemplaza un señalador válido. Para releer con un grupo, detené sus miembros y cambiá los offsets deliberadamente.
→ earliest no significa «empezá de cero siempre».

09. Cuando cambia el equipo
=================================================================
Miembros, asignación, latidos y tiempo de procesamiento.

Entrar, salir, reasignar
Cuando entran o salen miembros, el grupo redistribuye particiones. Un broker coordinador administra los miembros. Los offsets confirmados permiten que el nuevo dueño retome una partición.
→ La propiedad de una partición puede cambiar aunque el proceso siga vivo.

Estar vivo no es avanzar
Los latidos muestran que el miembro sigue presente. max.poll.interval.ms limita el tiempo entre polls. Un lote que tarda demasiado puede perder su asignación aunque la máquina esté sana.
→ Limitá el tiempo de procesamiento y manejá la revocación de particiones.

Sabé qué protocolo usás
Kafka 4.x permite el protocolo de grupos consumer, con asignación del lado del servidor. El cliente lo elige con group.protocol=consumer. La asignación cooperativa clásica es otro mecanismo; este laboratorio usa classic explícitamente.
→ Verificá versiones de cliente y broker antes de cambiar protocolos.

10. Copias que siguen a un líder
=================================================================
Una partición puede sobrevivir a la caída de un broker.

Un líder por partición
El líder recibe escrituras de una partición. Las réplicas seguidoras copian su log. Un factor de replicación de tres significa tres copias en tres brokers, no tres particiones.
→ Particionar reparte trabajo; replicar lo copia.

Seguí las réplicas sincronizadas
ISR es el conjunto de réplicas consideradas sincronizadas con el líder. Una seguidora lenta o caída puede salir. La ubicación de las réplicas y los dominios de falla determinan qué caídas soportás.
→ Tres copias en una laptop comparten el destino de esa laptop.

Promové una réplica elegible
Si cae el líder, Kafka puede elegir otra réplica elegible. Los clientes actualizan metadatos y reintentan. La disponibilidad depende del quórum de controladores y las réplicas elegibles restantes, no solo de contar copias.
→ La conmutación es un protocolo, no un cambio instantáneo.

11. ¿Qué significa «guardado»?
=================================================================
acks, ISR mínimo y el costo de seguir disponible.

Elegí la confirmación
acks=0 no espera respuesta del broker. acks=1 espera al líder. acks=all espera a las réplicas sincronizadas requeridas por el protocolo. Ninguno significa que un consumidor procesó el evento.
→ La confirmación al productor habla del almacenamiento, no del resultado de negocio.

Fijá un piso para las escrituras
Con acks=all, min.insync.replicas=2 exige al menos dos miembros en el ISR. Si quedan menos, las escrituras fallan. Con acks=1, esta configuración no obliga a confirmar desde dos réplicas.
→ acks=all y min.insync.replicas trabajan juntos.

Preferí un error explícito
Con tres réplicas e ISR mínimo de dos, se puede seguir escribiendo tras perder una réplica. Rechazar escrituras en condiciones peores protege la durabilidad elegida. No reemplaza backups ni recuperación probada.
→ Una escritura rechazada puede ser más segura que una pérdida confirmada como éxito.

13. La historia tiene un horizonte
=================================================================
Segmentos, tiempo de retención y primer offset legible.

Escribí en segmentos
Kafka agrega mensajes al segmento activo del log. Los segmentos anteriores pueden quedar habilitados para limpieza. La retención por tiempo y tamaño limita la historia; los límites de tamaño se aplican por partición.
→ El borrado trabaja con segmentos, no con cronómetros por mensaje.

Dejá que el comienzo avance
Cuando se borran segmentos viejos, avanza el primer offset disponible. Los offsets no se renumeran. Un consumidor cuyo señalador quedó atrás necesita una política de reset o una decisión de recuperación.
→ Un consumidor lento no impide el borrado por retención común.

Presupuestá tiempo para recuperarte
La retención tiene que cubrir caída, detección y puesta al día, con margen de crecimiento. El almacenamiento por niveles amplía opciones si se configura una implementación remota compatible; no es un backup automático.
→ La recuperación tiene que terminar antes de que desaparezca la historia.

14. Conservá el último valor conocido
=================================================================
Un log también puede reconstruir una tabla.

Interpretá las claves como filas
Un tópico compactado conserva eventualmente al menos el último valor de cada clave, sujeto al manejo de tombstones. Un consumidor reconstruye estado aplicando cambios en orden de partición. No se compacta al escribir.
→ La compactación es limpieza asíncrona, no una API de upsert.

Dejá una marca de borrado
Un mensaje con clave no nula y valor nulo es un tombstone. Le indica a una tabla en reconstrucción que borre la clave. El propio tombstone puede eliminarse después de delete.retention.ms. El texto "null" no es un valor nulo.
→ El borrado tiene que viajar antes de que desaparezca su marca.

Conservá las direcciones
La compactación deja huecos, pero conserva orden y offsets de los mensajes restantes. Con cleanup.policy=compact,delete, la retención también puede borrar segmentos, incluso el último valor de una clave.
→ Un log compactado es historia de cambios con una política de limpieza.

15. La caída entre dos acciones
=================================================================
Procesar, confirmar, caer. El orden cambia la garantía.

Confirmá antes del efecto
Si la aplicación confirma el offset y cae antes del efecto, al reiniciar saltea trabajo. Es el riesgo de como máximo una vez: un mensaje puede procesarse cero veces.
→ Un señalador adelantado al trabajo puede hacer perder trabajo.

Confirmá después del efecto
Si el efecto funciona y la app cae antes de confirmar, el mensaje se relee. Es el costo de al menos una vez: los duplicados tienen que ser seguros. Auto-commit no prueba que terminó el trabajo de negocio.
→ Un commit de offset y una escritura en una base son transacciones distintas.

Prepará el manejo de eventos problemáticos
Acotá los reintentos. Un tópico de fallas puede conservar eventos con contexto del error, pero su publicación y el commit de entrada necesitan coordinación. Saltear un evento puede romper el orden de la entidad; decidilo a propósito.
→ Un tópico de fallas necesita un responsable y un procedimiento de reproceso.

16. Dos clases distintas de duplicado
=================================================================
Reintentar en la red no es lo mismo que repetir un pedido de negocio.

Hacé seguros los reintentos del productor
Un productor idempotente usa identidad de productor y números de secuencia. Kafka reconoce el reintento del mismo lote y evita agregarlo dos veces dentro de ese protocolo. Requiere valores compatibles de acks, retries e in-flight.
→ Explicitá la idempotencia al enseñar o revisar una configuración.

Dos llamadas a send son dos escrituras
Llamar dos veces a send() con la misma clave y valor crea dos mensajes lógicos. Reiniciar la aplicación y reenviar un pedido de negocio tampoco queda deduplicado automáticamente por la idempotencia del productor.
→ La producción idempotente no deduplica el negocio.

Elegí una identidad de negocio
Un destino idempotente guarda un ID estable de evento junto con su efecto en una transacción atómica de base de datos. Una restricción única puede rechazar la reaplicación. Un set en memoria es solo una demo: desaparece al reiniciar.
→ El registro de deduplicación y el efecto tienen que funcionar juntos.

17. Hacé atómico el límite
=================================================================
Los mensajes de salida y offsets de entrada pueden confirmarse juntos.

Abrir, escribir, confirmar o abortar
Un productor transaccional puede escribir atómicamente en varias particiones. Un transactional.id estable bloquea una instancia anterior con la misma identidad. Los mensajes abortados pueden existir físicamente, pero read_committed los oculta.
→ Estar físicamente presente y ser visible como confirmado son cosas distintas.

Confirmá avance junto con salida
Un procesador de Kafka a Kafka escribe la salida y llama a sendOffsetsToTransaction con los próximos offsets de entrada y metadatos del grupo. La transacción confirma ambos o ninguno. Desactivá auto-commit en la entrada.
→ Procesar exactamente una vez requiere todo el protocolo de lectura, procesamiento y escritura.

Nombrá lo que queda afuera
Las transacciones de Kafka no incluyen un correo, una API de pagos ni una transacción de base arbitraria. read_committed espera detrás de transacciones abiertas en el último offset estable; eso afecta lag aparente y latencia.
→ «Exactamente una vez» siempre tiene que decir dentro de qué límite.

18. Un contrato que puede evolucionar
=================================================================
Los bytes necesitan un significado acordado.

Separá almacenamiento de significado
Los brokers aceptan bytes; no validan por sí solos los campos de negocio de tu JSON. Un esquema define el contrato. Un registro guarda versiones y comprueba compatibilidad según reglas configuradas.
→ Un registro es un componente del ecosistema, no el broker Kafka.

Preguntá quién tiene que leer qué
Compatibilidad hacia atrás significa que un lector nuevo puede leer datos del esquema viejo. Hacia adelante significa que un lector viejo puede leer datos nuevos. Full exige ambas. Los modos transitivos comparan contra todas las versiones registradas previas.
→ La dirección de compatibilidad depende de las versiones del lector y escritor.

Evolucioná a propósito
En Avro, agregar un campo con un valor por defecto adecuado puede permitir que el lector nuevo lea datos viejos. Cambiar un string a un tipo incompatible puede fallar. El formato y la ubicación del ID dependen del registro y serializador.
→ Un cambio compatible de esquema igual puede cambiar el significado de negocio.

19. Mové datos sin escribir otro loop

Cuatro piezas, cuatro funciones

20. De una base de datos a un evento
=================================================================
CDC captura cambios. Un outbox les da intención de negocio.

Capturá el log de la base
La captura de cambios lee cambios confirmados, a menudo empezando con un snapshot y siguiendo con el log transaccional. Altas, cambios y bajas son hechos de la base, no automáticamente buenos eventos de negocio.
→ CDC no es lo mismo que event sourcing.

Evitá el hueco de la doble escritura
Escribir una fila y después publicar en Kafka deja una ventana de falla. Un outbox escribe la fila de negocio y la del evento en la misma transacción de base. Un relay o conector CDC publica el outbox después.
→ Crear atómicamente no significa retransmitir sin duplicados.

Conservá la identidad al reintentar
El ID del evento de outbox se conserva en los reintentos. Los consumidores pueden deduplicarlo. El laboratorio usa PostgreSQL y un relay por polling para mostrar el límite de falla; no es un despliegue de Debezium.
→ El outbox resuelve crear el evento atómicamente; la entrega sigue necesitando una política.

22. ¿A qué minuto pertenece?
=================================================================
Hora del evento, hora del flujo, tolerancia y joins.

Usá el reloj del evento
La hora de procesamiento es cuando corre tu código. La del evento es cuando ocurrió el hecho. Streams usa por defecto los timestamps del mensaje. Su hora de flujo avanza con el máximo timestamp observado por la tarea; esperar al reloj de pared no la avanza.
→ La llegada tardía se mide contra el avance del flujo.

Dale un margen a lo tardío
Una ventana fija pone mensajes en intervalos sin solapamiento. La tolerancia permite desorden hasta que cierre la ventana respecto de la hora del flujo. Después, un mensaje tardío se descarta de la agregación.
→ Más tolerancia intercambia rapidez del resultado final por completitud.

Hacé joins por clave y tiempo
Un join entre flujos necesita claves coincidentes y una ventana. Un join flujo-tabla enriquece con el estado de la tabla según la semántica elegida. Importan el coparticionado y serializadores compatibles. Esperar sin límite acumula estado sin límite.
→ Un join requiere diseñar estado y tiempo; no alcanza con la palabra SQL.

23. Identidad, permiso, privacidad
=================================================================
Autenticación, autorización y cifrado responden preguntas distintas.

Sabé quién se conecta

25. Escalá la dimensión correcta
=================================================================
Almacenamiento, throughput, particiones y consumidores tienen presupuestos propios.

Estimá antes de asignar recursos
Una primera estimación es eventos por segundo × bytes serializados promedio × segundos de retención × factor de replicación. Sumá índices, metadatos, margen y distribución desigual; la compresión cambia el espacio real.
→ Estimá con unidades y después medí con tus propios mensajes.

Encontrá el carril más cargado
El throughput total puede esconder una clave caliente. Una clave queda en una partición con el mismo particionador y cantidad. Dividir la clave puede aumentar paralelismo, pero debilitar el orden que necesita tu aplicación.
→ Diseñar claves también es diseñar capacidad.

Mové réplicas a propósito
Agregar un broker no balancea por sí solo las particiones existentes hacia él. Reasignar réplicas mueve datos y consume red y disco. Usá límites de transferencia, observá el ISR y planificá la vuelta atrás.
→ La capacidad sirve si los datos y el trabajo pueden llegar a ella.

26. Un segundo clúster es otro sistema
=================================================================
Replicar entre clústeres requiere diseñar la recuperación.

Distinguí réplicas de espejos
Las réplicas dentro del clúster comparten la identidad del log. La replicación entre clústeres copia eventos a otro sistema con metadatos y offsets propios. MirrorMaker 2 usa Kafka Connect para coordinarlo.
→ El offset 100 de un clúster no tiene por qué ser el 100 del otro.

Elegí un contrato de recuperación
RPO es cuánta pérdida de datos tolerás; RTO es cuánto puede demorar la recuperación. La replicación asíncrona puede atrasarse. La conmutación tiene que resolver ruteo, avance de grupos, esquemas, permisos y estado de aplicaciones.
→ Un espejo sin ensayo de recuperación es una suposición sin probar.

Hacé visible el límite del laboratorio
El laboratorio levanta un segundo clúster de un broker y un cliente de copia de una sola pasada. Muestra offsets independientes y duplicados. No implementa traducción de checkpoints, latidos ni conmutación automática de MirrorMaker 2.
→ Copiar mensajes es solo una parte de recuperarse de un desastre.

27. Cuando el objetivo es repartir tareas
=================================================================
Los share groups confirman mensajes en lugar de asignar particiones enteras.

Cambiá la unidad de asignación
Un grupo común asigna particiones a miembros. Un share group puede repartir mensajes de una misma partición entre varios consumidores, con bloqueos de adquisición y confirmaciones.
→ Repartir el trabajo de una partición cambia los supuestos de orden de procesamiento.

Aceptá, liberá o rechazá
Un mensaje compartido se adquiere temporalmente. Accept confirma su finalización; release lo habilita para reentrega; reject indica que no se entregue de nuevo a ese grupo. Las adquisiciones fallidas o vencidas pueden reentregarse.
→ Un bloqueo no es un efecto de negocio exitoso.

Respetá el límite de versión
En Kafka 4.1, la versión fijada del curso, los share groups son una función preview que hay que habilitar; desde Kafka 4.2 son production-ready. Usá el broker experimental separado; el resto usa grupos comunes.
→ Una preview invita a experimentar; verificá la madurez de la versión que usás antes de apoyarte en ella.

29. Leé y escribí con Spring

Escribí con KafkaTemplate
POST /orders/order-42 recibe un evento JSON. OrderProducer llama a KafkaTemplate.send(topic, orderId, event). La clave es el ID del pedido; JsonSerializer convierte el record Java en bytes. La respuesta HTTP espera la confirmación del broker e incluye partición y offset.

KafkaConfig declara un NewTopic con tres particiones, tres réplicas e ISR mínimo 2. Otro pedido HTTP es un nuevo send, aunque tenga el mismo ID de evento. La lista /received en memoria solo sirve para observar. Ante un error, este ejemplo detiene el listener sin confirmar el mensaje fallido.

Leé la lista acotada en memoria y los logs. Si está vacía, reintentá tras un segundo. OrderConsumer.java muestra @KafkaListener y la clave, evento y offset consumidos.

docker compose run --rm http --fail-with-body http://spring:8080/received
docker compose logs --tail 15 spring

Observá: Aparece el evento con clave order-42. Los logs muestran RECEIVED y su partición/offset.

4. Repetí el mismo pedido
Mandá el mismo evento otra vez. La producción idempotente maneja reintentos de transporte; no deduplica dos pedidos HTTP. Compará los offsets de la lista.

Esperá lag cero en la partición con datos antes del siguiente paso. Mirá application.yml: group-id, auto-offset-reset, enable-auto-commit y ack-mode.

Observá: La partición con datos tiene LAG 0. Las vacías pueden mostrar «-» (sin offset confirmado). CURRENT-OFFSET es el próximo mensaje a consumir.

6. Reiniciá la aplicación
La lista en memoria se vacía, pero los offsets del grupo quedan en Kafka. earliest no rebobina un grupo que ya tiene offsets válidos.

docker compose run --rm http --fail-with-body http://spring:8080/received

Observá: La lista queda []: los mensajes ya confirmados no se releen. Publicá un evento nuevo para ver que el listener sigue activo.

Al terminar, detené la aplicación. El proyecto completo y el recorrido bilingüe del código están en labs/spring/README.md. Diseñá deduplicación durable antes de agregar pagos u otro efecto externo.
