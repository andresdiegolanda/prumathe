Qué hace Microsoft Entra ID
La identidad es un punto de partida. Una aplicación segura lleva esa evidencia a través de límites explícitos.

El proveedor de identidad en el dibujo
Microsoft Entra es una familia de productos de identidad y de acceso a la red. Este curso se concentra en Microsoft Entra ID en un tenant workforce y en la Microsoft identity platform que usan las aplicaciones. No recorre todos los productos de Entra.

Entra ID ayuda a una organización a administrar identidades, autenticar inicios de sesión y emitir tokens para aplicaciones. Nuestro cliente Angular usa esa plataforma de identidad para obtener evidencia para la API de Spring. La API decide qué puede hacer quien llama, y PostgreSQL hace cumplir los privilegios de la base de datos y la política de filas.

Pensá en una solicitud de compra: una empleada puede iniciar sesión y aun así no tener permiso para aprobarla. Un aprobador puede tener el rol correcto y aun así tener prohibido aprobar su propia compra. La distancia entre esas dos afirmaciones es donde este curso pone su atención.

Los nombres y los estándares que vas a encontrar
La documentación más vieja suele decir Azure Active Directory o Azure AD. Microsoft anunció el nombre Entra ID en 2023; ese cambio de nombre no lo convirtió en el Active Directory de Windows Server. OAuth y OpenID Connect son estándares aparte que usa el protocolo de la aplicación.

2012 OAuth 2.0: RFC 6749 define el marco de autorización, con los grants authorization code y client credentials.
2014 OIDC: OpenID Connect Core 1.0 define una capa de identidad sobre OAuth 2.0.
2015 PKCE: RFC 7636 especifica un mecanismo de prueba de posesión de una clave para el canje del authorization code.
2023 Entra ID: Microsoft anuncia el nombre nuevo de Azure Active Directory.
2025 OAuth BCP: RFC 9700 recoge la práctica recomendada actual de seguridad para OAuth.

Dónde encaja en esta aplicación
Estas son las responsabilidades que practica el curso.
Inicio de sesión workforce: Usá una identidad del tenant y sus políticas de inicio de sesión, en lugar de pedir la contraseña de la empresa dentro de la SPA.
Acceso específico a un recurso: Obtené acceso delegado a una API y validá el token en esa API.
Asignación administrada: Definí un vocabulario chico de app roles y asigná usuarios desde la administración de identidades de la organización.

Lo que este curso no le delega a Entra
Lo que sigue son decisiones de diseño de este curso, no la afirmación de que un producto de identidad resuelve todos los requisitos de una aplicación.
¿De quién es la solicitud 42?: La propiedad de un registro es un dato de la aplicación. Identidad validada más un predicado en la API o en la base de datos.
¿Una solicitud se puede aprobar sola?: Un rol no puede representar todas las relaciones y todos los estados. Una regla de negocio explícita, aplicada de forma atómica.
¿Puede conectarse JDBC?: La conexión a la base de datos tiene su propio principal y su propia credencial. Autenticación de la base de datos y permisos mínimos.
¿Este despliegue es seguro?: Un inicio de sesión exitoso no prueba el transporte, la cadena de suministro ni los controles de operación. Modelado de amenazas y evidencia del sistema desplegado.

01. Cuatro componentes, cuatro responsabilidades
=================================================================
Un pedido cruza límites; la confianza no viaja sola.
Recorrido de la evidencia: local

El navegador lo controla su usuario
Angular puede mejorar la navegación, ocultar las acciones que no están disponibles y mostrar el nombre de una cuenta. Un usuario también puede inspeccionar su bundle, cambiar su JavaScript o mandar un pedido HTTP sin él. El navegador es un cliente de la API, no una extensión protegida de la API. Todo lo que haga falta para hacer cumplir los permisos tiene que resistir que quien llama saltee la interfaz.
Regla: Un route guard es un control de usabilidad, no un límite de la API.

La decisión de negocio es de la API
Entra emite un token para un recurso según sus políticas de identidad y de consentimiento. Spring valida ese token y después aplica las reglas de la aplicación. Saber que Alice se autenticó no le dice a Entra si la solicitud de compra 42 es de Bob, si está pendiente o si esta compra supera un límite. Esos hechos son de la aplicación.
Regla: La evidencia de identidad es una entrada de la autorización, no su respuesta completa.

La base de datos ve una conexión
PostgreSQL autentica el rol de base de datos de la aplicación. No sabe por sí solo qué usuario del navegador causó una consulta. Nuestra API lleva el contexto validado de tenant y de sujeto a una transacción, y además restringe el SQL. Son conexiones distintas, con credenciales distintas. Un token enviado a la API no se reenvía como contraseña de PostgreSQL.
Regla: Nombrá el principal en cada salto.

02. Autenticación y autorización
=================================================================
¿A quién se representa? ¿Qué puede hacer quien llama?
Recorrido de la evidencia: local

Dos preguntas con evidencia distinta
La autenticación establece una identidad según un mecanismo y sus supuestos de confianza. La autorización evalúa si una acción está permitida. Al iniciar sesión, Entra autentica a la persona. En la API, Spring autentica el pedido bearer con un token validado. Ninguna de las dos operaciones prueba que la persona esté físicamente presente en cada pedido HTTP que sigue.
Regla: Un pedido bearer presenta evidencia: lo que cuenta es tenerla.

La política es una conjunción
Nuestro endpoint de aprobación exige un access token para esta API, el scope delegado Requests.Approve, el app role de usuario Approver, el tenant correcto, una solicitud de otra persona y un estado pendiente. Cada requisito aporta un hecho distinto. Si falta cualquier hecho necesario, la operación se tiene que rechazar, aunque todas las demás condiciones se cumplan.
Regla: Escribí la política como AND antes de escribir anotaciones.

La identidad es necesaria pero no alcanza
Alice puede estar autenticada y aun así no tener un rol. Un aprobador puede tener el rol y aun así no poder aprobar su propia solicitud. Una identidad correcta puede estar asociada a un registro de otro tenant. Muchas veces el rechazo es el funcionamiento correcto de un sistema seguro, no una falla de inicio de sesión que haya que arreglar ampliando permisos.
Regla: Un rechazo se tiene que explicar en el límite que lo produjo.

03. Tenant, aplicación, service principal
=================================================================
Separá la definición de la aplicación de su presencia en un directorio.
Recorrido de la evidencia: tenant

Un límite de directorio
Un tenant workforce contiene las identidades y la configuración de una organización. El tenant ID identifica ese directorio. Nuestra configuración base acepta un solo tenant, con un issuer explícito. Reemplazar ese issuer por common no es un atajo seguro hacia una aplicación multitenant: el alta de organizaciones, la validación del issuer y la partición de los datos necesitarían un diseño.
Regla: Un tenant es parte del límite de confianza, no solo una pista para el inicio de sesión.

Definición e instancia local
Un app registration crea un objeto de aplicación en su directorio de origen. Un service principal representa la aplicación en un tenant; Enterprise applications (Aplicaciones empresariales) es la vista de administración que se usa para muchas de esas configuraciones a nivel de tenant. El client ID de la aplicación identifica la app, mientras que los object IDs identifican objetos del directorio. Copiar el ID equivocado puede crear una configuración que parece razonable pero nombra otra cosa.
Regla: Application ID y object ID son identificadores distintos.

Una clave de identidad estable para la aplicación
El nombre visible o el email de una persona pueden cambiar y se pueden reutilizar. La API usa el par validado tid y oid como su clave de identidad local al tenant. Las identidades de invitados requieren atención: el objeto que las representa en el tenant del recurso no es intercambiable con un objeto del tenant de origen de la persona. Definí de forma explícita la baja de usuarios y la propiedad de los datos.
Regla: Los nombres legibles son etiquetas; la autorización usa identificadores validados.

04. Dos registros, una experiencia de aplicación
=================================================================
Angular es el cliente. Spring es el recurso.
Recorrido de la evidencia: tenant

Registrá al destinatario por separado
El registro de la API define el recurso: su Application ID URI, los scopes delegados y el app role de usuario Approver. El registro de la SPA define el cliente público y su redirect URI permitida. Mantenerlos separados deja a la vista el destinatario del token. Pedir api://API_CLIENT_ID/Requests.Read expresa a la vez un recurso y un permiso delegado.
Regla: La audiencia del access token nombra a la API, no a la interfaz.

Público quiere decir que no puede guardar un secreto
El client ID de la SPA y el tenant ID son configuración pública. Un client secret incrustado en JavaScript lo podría leer cualquier visitante; no convertiría a Angular en un cliente confidencial. Registrá una ruta de redirect de tipo Single-page application (Aplicación de página única). El ejemplo usa http://localhost:18094/redirect para el desarrollo local y un bridge de redirect de MSAL dedicado.
Regla: Una aplicación de navegador no tiene que depender de un client secret guardado.

Hacé explícito qué se espera del token
Configurá la API para que pida access tokens v2, con requestedAccessTokenVersion en 2. La API valida el issuer v2, su propio client ID como audiencia, el tenant, los scopes delegados y el cliente permitido. La versión del authorization endpoint, por sí sola, no elige el formato del access token del recurso. Un registro es configuración, no código de la API desplegado.
Regla: Un registro y el validador de un resource server tienen que coincidir.

05. Seguí el authorization code
=================================================================
Entendé el redirect sin implementar vos un protocolo de identidad.
Recorrido de la evidencia: local

Un pedido sale de la aplicación
MSAL crea un verifier nuevo y su challenge S256, y después navega al authorization endpoint del tenant con el cliente, la redirect URI y los scopes pedidos. Entra se ocupa del inicio de sesión y de las políticas que correspondan. La aplicación no recibe la contraseña de Entra. Volver a un callback registrado no significa, por sí solo, que cada operación posterior en la API esté autorizada.
Regla: Dejá que el proveedor de identidad maneje las credenciales.

El code se canjea
La respuesta de autorización trae un code de vida corta. El cliente lo canjea con el verifier original. Un code capturado sin el verifier no tendría que alcanzar. State relaciona la respuesta con la interacción que la inició; el nonce de OIDC ata la evidencia del ID token al pedido de autenticación. Estas defensas sirven para cosas distintas, y la biblioteca maneja su ciclo de vida.
Regla: PKCE ata el canje del code a la instancia del cliente que lo inició.

Conocé el límite de la defensa
PKCE le quita utilidad a un authorization code interceptado. 10. Inicio de sesión de Windows y Primary Refresh Token
=================================================================
En un dispositivo unido a Entra, Windows ya tiene un token antes de que la app pida uno.
Recorrido de la evidencia: tenant

Windows inicia sesión en Entra primero
En un dispositivo Windows unido a Entra, la pantalla de inicio de sesión hace más que desbloquear el escritorio. LogonUI le pasa las credenciales a la Local Security Authority, cuyo proveedor CloudAP se las pasa a su plugin de Microsoft Entra. El plugin obtiene un nonce de Entra, firma un pedido con la clave del dispositivo que guarda el TPM y lo manda. Entra verifica las credenciales, el nonce y el dispositivo, y después emite un Primary Refresh Token (PRT) y una session key cifrada para este dispositivo. El TPM desenvuelve la session key y la vuelve a envolver con su propia clave; CloudAP guarda los dos en su caché. Un inicio de sesión con Windows Hello for Business le agrega al PRT un claim de MFA.
Regla: El primer token de Entra del día es del intermediario de inicio de sesión del dispositivo, no de una aplicación.

El navegador usa la sesión prestada, nunca el PRT
Cuando MSAL manda la pestaña a /authorize, Edge con un perfil que tiene iniciada la sesión de la cuenta de trabajo, o Chrome con la extensión Microsoft Single Sign On, reconoce una URL de inicio de sesión de Entra y le pide a CloudAP una PRT cookie. CloudAP la arma con el nonce de esa URL y hace que el TPM la firme con la session key. El navegador la manda en el header x-ms-RefreshTokenCredential; los scripts de la página nunca la ven. Entra valida la firma, el nonce y el dispositivo, le inicia la sesión a Alice sin contraseña y fija su propia cookie de sesión, atada al dispositivo. Después siguen el code, PKCE y los tokens, como antes. Las ventanas privadas no usan el PRT.
Regla: El single sign-on cambia cómo Alice prueba quién es, no qué tokens recibe la app.

Cada credencial tiene su lugar y su reloj
Las claves del dispositivo quedan en el TPM. El PRT y su session key quedan en la caché de CloudAP; el PRT vale 90 días y CloudAP lo renueva al iniciar sesión en Windows cada 4 horas. Una PRT cookie existe para un solo pedido. La cookie de sesión de Entra vive en las cookies del navegador para login.microsoftonline.com. El ID token, el access token y el refresh token viven en el sessionStorage de la pestaña, y un refresh token emitido para una SPA dura 24 horas, en una ventana que no se corre. Borrar o deshabilitar el usuario o el dispositivo, o un cambio de contraseña cuando el PRT salió de la contraseña, invalida el PRT; nada de esto retira un access token ya emitido. Las aplicaciones nativas le piden a WAM, el intermediario de tokens de Windows, que guarda sus refresh tokens cifrados con DPAPI. Esta app de navegador no lo usa.
Regla: Para cada credencial, nombrá quién la emite, dónde espera y cuándo deja de servir.

11. Validá antes de confiar
=================================================================
Una firma es una verificación dentro de un contrato de resource server más amplio.
Recorrido de la evidencia: local

Empezá por la confianza configurada
Spring usa los metadatos y las claves públicas de firma del issuer configurado. No tiene que elegir un issuer de confianza ni una URL de claves solo a partir de un token no confiable. La firma protege los bytes firmados; la audiencia ata esos bytes a un destinatario; el issuer los ata a una autoridad. La rotación de claves es normal, así que el decoder usa una fuente de JWK en lugar de una clave permanente copiada a mano.
Regla: Una clave es de confianza por la configuración y el discovery, no porque el token la señale.

Validá el contrato completo
El ejemplo conserva los validadores de issuer y de tiempo de Spring, y después agrega audiencia, tenant, formato v2, el cliente SPA permitido y un oid bien formado. Regla: La validación propia tiene que sumarse a los valores por defecto, no reemplazarlos sin querer.

La validación tiene dependencias operativas

Un despliegue de producción necesita decisiones explícitas de timeout, monitoreo y disponibilidad.
Regla: Una caída no se puede convertir en un camino de autenticación que falla abierto.

17. Transacciones, pools y carreras
=================================================================
La autorización tiene que resistir la reutilización de conexiones y los pedidos concurrentes.
Recorrido de la evidencia: local

Un pool reutiliza conexiones físicas
Los pools de conexiones hacen eficiente el acceso a la base de datos reutilizando conexiones entre pedidos. Un setting de sesión para Alice podría quedar ahí cuando después Bob toma prestada esa conexión. Spring fija el contexto dentro de la misma transacción que la consulta, con set_config y la marca local en true. Cuando la transacción termina, ese setting local ya no autoriza la próxima transacción.
Regla: La vida del contexto de identidad tiene que coincidir con la transacción que lo usa.

Verificá y cambiá a la vez
Leer PENDING por separado y después hacer un update sin condiciones invita a una carrera: dos llamadas pueden ver las dos el estado viejo. El ejemplo usa un solo UPDATE con predicados de tenant, de no ser el dueño y de PENDING. Con el comportamiento normal de PostgreSQL que se usa acá, dos intentos concurrentes no pueden pasar los dos la misma fila de pendiente a aprobada. Uno lo logra; el otro no encuentra ninguna fila que califique.
Regla: Poné las condiciones de autorización que cambian dentro de la transición de estado atómica.

Definí el límite de la transacción
El update de SQL y el contexto de su fila comparten una transacción. Mandar un email o cobrar con una tarjeta sumaría un efecto externo que un rollback de la base de datos no puede deshacer por sí solo. Un servicio de aprobación real necesita una estrategia explícita, como un transactional outbox, idempotencia y una política de reintentos. Que una fila cambie bien de estado no prueba que el negocio entregue el efecto exactamente una vez.
Regla: La atomicidad de la base de datos termina en el límite de la transacción de la base de datos.

18. Vencimiento, renovación y cierre de sesión
=================================================================
Un token es una foto con límite de tiempo, no una consulta en vivo al directorio.
Recorrido de la evidencia: local

El token tiene un intervalo de validez
El resource server verifica los tiempos de vencimiento y de no-antes, con un desfasaje de reloj acotado. No fijes en la política de negocio una única duración universal de los access tokens de Entra. Las condiciones de emisión y los tipos de token pueden variar. El fixture usa tokens de vida corta para que el mecanismo se vea; sus valores de vencimiento son datos de enseñanza, no evidencia de los valores por defecto del tenant.

Regla: No prometas una revocación instantánea por un botón local de cierre de sesión.

21. Amenazas en el navegador y decisiones de arquitectura
=================================================================
Entendé qué cambia cada uno: CORS, PKCE y un BFF.
Recorrido de la evidencia: local

CORS es una regla de cooperación del navegador
Un pedido de navegador entre orígenes puede mandar primero un preflight OPTIONS. Nuestra API permite el origen exacto del frontend local, los métodos y el header Authorization. CORS no reemplaza la validación del token ni la autorización: alguien que llama desde la línea de comandos puede omitir Origin del todo y llegar igual a la API. Tiene que enfrentar las mismas verificaciones de autenticación y de negocio.
Regla: Un origen permitido no es un principal autenticado.

El script del navegador está dentro de la sesión del usuario
Un XSS puede ejecutarse dentro del origen de la aplicación y actuar con los poderes de la sesión. Una CSP, un renderizado seguro, el mantenimiento de las dependencias y un manejo cuidadoso de los tokens reducen el riesgo; PKCE no resuelve la ejecución de scripts maliciosos. El ejemplo usa headers bearer y ningún login con cookie, y por eso su API deshabilita la protección CSRF. Agregar autenticación con cookies cambiaría esa decisión.
Regla: Una configuración de seguridad vale solo bajo los supuestos de arquitectura que declara.

Un backend for frontend mueve el límite
Un BFF puede guardar los tokens de OAuth en el servidor y darle al navegador una cookie de sesión Secure y HttpOnly, con una política de SameSite y de CSRF deliberada. Eso reduce la exposición directa de los tokens al código del navegador, pero suma responsabilidades de sesión y de ciclo de vida del lado del servidor. Un XSS igual puede disparar acciones a través de una sesión autenticada. Elegí el patrón según el modelo de amenazas y la capacidad operativa.
Regla: Mover una credencial cambia los riesgos; no elimina la autorización.

GLOSARIO
Autenticación: Establecer una identidad con un mecanismo y una política de confianza definidos.
Autorización: Decidir si un principal puede hacer una acción sobre un recurso.
Principal: La identidad que se representa en un límite de seguridad: un usuario, una aplicación o un rol de base de datos.
Límite de confianza: Un punto donde un componente tiene que decidir qué afirmaciones externas acepta.
Tenant: Un límite de directorio para identidades y configuración de aplicaciones.
Objeto de aplicación: La definición de la aplicación en su tenant de origen.
Service principal: La representación de la aplicación dentro de un tenant concreto.
Client ID: El identificador público de la aplicación, distinto del object ID de un objeto del directorio.
Cliente público: Un cliente, como una SPA, que no puede mantener en secreto una credencial incrustada.
Cliente confidencial: Un cliente del lado del servidor capaz de proteger credenciales según los supuestos de su despliegue.
OAuth 2.0: Un marco de autorización para obtener acceso a recursos.
OpenID Connect: Una capa de identidad sobre OAuth 2.0, que incluye el ID token como resultado del inicio de sesión.
Authorization code: Un artefacto de vida corta que se canjea en el token endpoint, con PKCE en el flujo de la SPA.
PKCE: Un challenge y un verifier que atan el canje del code a la instancia del cliente que lo inició.
State: Un valor que relaciona una respuesta de autorización con la interacción que la inició.
Nonce: Un valor de OIDC que ata la evidencia del ID token al pedido de autenticación.
Redirect URI: El destino de callback registrado para una respuesta de autorización.
Primary Refresh Token (PRT): Un token que Entra le emite al intermediario de inicio de sesión del dispositivo cuando se inicia sesión en Windows, para el single sign-on; nunca se le entrega a una aplicación.
CloudAP: El proveedor de inicio de sesión de Windows dentro de LSA; su plugin de Entra obtiene el PRT, lo guarda en caché y lo renueva.
TPM: Un módulo de hardware que guarda las claves privadas del dispositivo y protege la session key del PRT.
Session key: La clave de prueba de posesión que se emite con el PRT; los pedidos que usan el PRT se firman con ella.
PRT cookie: Un valor que CloudAP firma para un único pedido de inicio de sesión; el navegador lo envía en x-ms-RefreshTokenCredential.
Single sign-on: Iniciar sesión en otra aplicación reutilizando una sesión ya establecida, en lugar de volver a ingresar credenciales.
WAM: Web Account Manager, el intermediario de tokens de Windows que usan las aplicaciones nativas; esta app de navegador no lo usa.
ID token: El resultado OIDC del inicio de sesión, destinado al cliente; no es la credencial de la API de compras.
Access token: Una credencial destinada a un recurso, que la valida y aplica su política.
Refresh token: Una credencial de renovación que se usa con el proveedor de identidad a través de la biblioteca del cliente.
Bearer: Una credencial cuya sola posesión permite presentarla; hay que protegerla de que se filtre.
JWT: Un formato de token con claims codificados y una firma; decodificar no es validar.
Issuer / iss: La autoridad que emitió el token, comparada con la confianza configurada.
Audiencia / aud: El destinatario previsto de un token; esta API acepta su propio identificador de recurso.
Tenant ID / tid: El identificador del directorio, que se valida y se usa en el límite de los datos.
Object ID / oid: La identidad del objeto dentro de un tenant; acá, junto con tid, forma la clave del usuario.
Authorized party / azp: El identificador de la aplicación cliente en un token v2, que verifica el contrato de esta API.
Scope / scp: Un valor de permiso delegado; varios valores van separados por espacios en scp.
Consentimiento: Un permiso que habilita el acceso de un cliente según la política del tenant, distinto de un derecho de negocio.
App role / roles: Un rol definido por la aplicación, otorgado a un principal y representado en roles.
Authority: Un texto de permiso que Spring evalúa después de convertir los claims aceptados.
JWK set: Un conjunto publicado de claves públicas para verificar firmas dentro de una política de issuer de confianza.
IDOR: La falta de un control de autorización por objeto; un identificador solo no es un permiso.
Row-level security: Políticas de la base de datos que filtran el acceso a filas para los roles que no las saltean.
BYPASSRLS: Un atributo privilegiado de un rol de PostgreSQL que saltea la seguridad de filas.
Pool de conexiones: Conexiones reutilizables a la base de datos que no pueden filtrar el contexto de identidad de un pedido.
Transaction-local context: Settings cuya vida efectiva termina con la transacción.
On-behalf-of: Un servicio intermedio que obtiene un token delegado para el servicio de abajo, en lugar de reenviar uno con la audiencia equivocada.
Client credentials: Acceso de una aplicación sin un usuario con sesión iniciada.
CORS: Un mecanismo del navegador para el acceso entre orígenes, no una autenticación de quien llama.
CSRF: Acciones autenticadas no deseadas, inducidas a través de cómo el navegador maneja las credenciales; importa para el diseño de sesiones.
XSS: La ejecución de un script malicioso dentro del origen de una aplicación.
BFF: Un backend for frontend que puede guardar los tokens de OAuth en el servidor y darle al navegador una sesión.
CAE: Continuous access evaluation para los recursos y escenarios compatibles; la validación local de un JWT no la trae sola.

PANORAMA
A. Inicio de sesión de Windows: el PRT
  1. Alice: Alice inicia sesión en Windows en un dispositivo unido al tenant, con su contraseña de trabajo o con Windows Hello for Business. Todavía no hay ninguna app abierta.
  2. Login de Windows: La pantalla de inicio de sesión, LogonUI, toma las credenciales y se las pasa a LSA, la Local Security Authority.
  3. CloudAP: Dentro de LSA, CloudAP se las pasa a su plugin de Microsoft Entra, que le pide un nonce a Entra y arma un pedido con las credenciales y el nonce.
  4. TPM: El pedido se firma con la clave privada del dispositivo, dentro del TPM. La clave nunca sale de ahí.
  5. Devices: Entra verifica las credenciales, el nonce y la firma contra la clave pública del dispositivo, y que el dispositivo sea válido en el tenant.
  6. Devices: Emite el PRT, y una session key cifrada con la clave pública de transporte del dispositivo.
  7. CloudAP: Los dos llegan a CloudAP. Solo este dispositivo puede abrir la session key: hace falta la clave privada de transporte.
  8. TPM: El TPM descifra la session key con la clave de transporte y la vuelve a envolver con su propia clave.
  9. CloudAP: CloudAP guarda el PRT y la session key envuelta en su caché, dentro de LSA. Al navegador no llegó nada.
  Antes de que se abra cualquier app, CloudAP tiene un PRT para Alice y una session key que solo este TPM puede usar. Ninguno de los dos llega nunca al navegador ni a la app: el recorrido B muestra lo que recibe el navegador en su lugar.
B. Abrir la app: sin contraseña

  6. Navegador: La PRT cookie vuelve al navegador, no a la página: MSAL y cualquier script inyectado nunca la ven.
  7. Endpoint de login: El pedido llega a /authorize con el cliente, los scopes y el challenge, y la PRT cookie en el header x-ms-RefreshTokenCredential.

  15. Controlador: Vuelve la fila. El COMMIT termina la transacción, y el contexto desaparece con ella.
  16. App Angular: HTTP 200 con la solicitud 41. La app la muestra; no decidió nada.
  Una lectura cruzó cuatro verificaciones independientes: el token, la operación, la consulta del endpoint y la política de filas. Sacar cualquiera de ellas es una prueba que tendría que fallar.
F. Aprobar la solicitud de un colega
  1. node lab.mjs: El lab pide el caso approver: la identidad de Alice, con el rol Approver.
  2. Emisor de tokens: El emisor lo firma con la clave del kit: scp trae los dos scopes, roles trae Approver.
  3. node lab.mjs: Salen dos POST /api/requests/42/approve en el mismo momento. La solicitud 42 es de Bob, y está PENDING.
  4. CORS y filtro bearer: Sin navegador no hay Origin ni preflight: CORS no participa. El filtro bearer toma el token.
  5. JwtDecoder: En modo fixture el decoder confía en la clave del kit, y solo en ella. Firma, issuer, tiempo y contrato: válidos.
  6. Conversor de authorities: SCOPE_Requests.Approve a partir de scp, y ROLE_Approver a partir de roles.
  7. Regla del método: Aprobar necesita SCOPE_Requests.Approve y ROLE_Approver, los dos. Un OR acá dejaría que un token app-only actúe como una persona.
  8. Controlador: Una sola sentencia verifica y cambia a la vez: UPDATE purchase_request SET status = 'APPROVED' WHERE id = 42 AND el tenant coincide AND owner_oid no es quien llama AND status = 'PENDING'.
  9. Política RLS: A través de una conexión app_runtime del pool. El WITH CHECK de la política deja que un aprobador cambie una fila de su tenant.
  10. purchase_request: El primer UPDATE pasa la 42 a APPROVED. El segundo no encuentra ninguna fila PENDING: cambian 0 filas.
  11. Controlador: Cambió una fila: 200 APPROVED. Ninguna fila: 404, la misma respuesta que para una solicitud que no existe.
  12. node lab.mjs: El lab ve exactamente un 200 y un 404, y PostgreSQL dice APPROVED. Aprobar su propia solicitud 41 también da 404: el dueño no puede aprobar.
  Un rol es una condición entre varias. La regla del método verifica scope y rol; una sola sentencia SQL verifica juntos el tenant, que no sea el dueño y PENDING, así que una carrera no puede aprobar dos veces.
G. 401: el token no se acepta
  1. node lab.mjs: El lab le pide al emisor tokens rotos, un caso por vez.
  2. Emisor de tokens: Cada caso rompe una sola cosa: vencido, válido solo en el futuro, firmado con la clave de un desconocido, otro issuer, otra audiencia, un ID token, otro cliente, sin oid, otro tenant.
  3. node lab.mjs: Cada uno sale como GET /api/requests/41.
  4. CORS y filtro bearer: El filtro bearer le pasa el token al decoder.
  5. JwtDecoder: Cada caso falla exactamente una verificación: firma, issuer, exp o nbf, aud (también el ID token: su audiencia es la SPA), tid, azp u oid.
  6. CORS y filtro bearer: La cadena de filtros responde 401 con WWW-Authenticate: Bearer. No se ejecutó ningún controlador y no se mandó ningún SQL.
  7. node lab.mjs: El lab espera 401 para cada caso, y sigue esperando 200 para el token válido de Alice.
  401 significa que la API no aceptó la credencial. Volver a iniciar sesión no arregla una audiencia equivocada: la arregla la configuración. Cada arreglo conserva su prueba negativa.
H. 403: aceptado, no permitido
  1. node lab.mjs: Dos tokens genuinos a los que les falta algo a cada uno: no-role tiene los scopes pero no Approver; app-only tiene Approver pero no scp, porque no inició sesión ningún usuario.
  2. Emisor de tokens: Los dos están firmados con la clave del kit, para la audiencia, el tenant y el cliente correctos.
  3. node lab.mjs: Cada uno pide aprobar la solicitud 42.
  4. CORS y filtro bearer: El filtro bearer toma el token.
  5. JwtDecoder: Los dos pasan todas las verificaciones. La autenticación se cumple.
  6. Conversor de authorities: no-role da solo authorities SCOPE_. app-only da ROLE_Approver y ningún SCOPE_.
  7. Regla del método: Aprobar necesita SCOPE_Requests.Approve y ROLE_Approver. A cada token le falta una de las dos.
  8. CORS y filtro bearer: La cadena de filtros convierte el rechazo en 403. El controlador nunca se ejecutó.
  9. node lab.mjs: Los dos reciben 403. Un token con solo Requests.Read recibe 403 para aprobar y sigue recibiendo 200 para leer: los scopes son por operación.
  403: la API sabe quién llama y rechaza esta operación. Un botón oculto nunca protegió nada; esta regla sí.
I. 404: Alice pide la solicitud de Bob
  1. App Angular: Alice escribe 42 en lugar de 41. La página la deja: el campo de texto no es el límite.
  2. CORS y filtro bearer: Un token genuino de Alice llega a la API.
  3. Regla del método: Válido, con SCOPE_Requests.Read: la operación está permitida. Tener permiso para leer no es tener permiso para leer todo.
  4. Controlador: El id sale de la URL; el tenant y el dueño salen solo del token: WHERE id = 42 AND tenant_id = tid AND owner_oid = el oid de Alice.
  5. Política RLS: Hasta una consulta que se olvidó el WHERE quedaría filtrada acá: la fila no es de Alice, y ella no es aprobadora.
  6. purchase_request: Ninguna fila coincide.
  7. Controlador: Ninguna fila: 404, la misma respuesta que para un número que no existe, así la API no revela qué solicitudes existen.
  8. App Angular: Alice ve 404. Bob, con su propio token, recibe 200 para la 42. La solicitud 43 vive en otro tenant: Alice recibe 404, y un token de ese tenant recibe 401.
  La propiedad es una regla de autorización, que se aplica con la identidad tomada del token validado y nunca del pedido. RLS la repite debajo.
J. RLS, el segundo límite
  1. node lab.mjs: El lab se conecta directo a PostgreSQL y pasa a app_runtime, el rol que usa la API.
  2. Política RLS: No se fijó ningún contexto, así que la política compara tenant_id con NULL: ninguna fila califica.
  3. purchase_request: SELECT count(*) devuelve 0. No es un error: es una respuesta vacía y segura.
  4. Política RLS: Ahora, dentro de una transacción con el tenant y el sujeto de Alice fijados, el lab ejecuta un SELECT sin ningún WHERE.
  5. purchase_request: Vuelve solo la fila 41. La 42 de Bob y la 43 del otro tenant siguen invisibles.
  6. Política RLS: Después del COMMIT, la misma conexión vuelve a ver 0 filas: set_config(name, value, true) era solo de esa transacción.
  7. app_runtime: Y el rol en sí no es superusuario ni BYPASSRLS, la tabla fuerza RLS, y app_runtime no puede reescribir owner_oid.
  RLS es un segundo límite, no el primero: confía en el contexto que fija la API. Lo que aporta es que un WHERE olvidado no devuelve nada en lugar de devolver todo.
K. Un rol quitado contra un token anterior
  1. Administrador: Ayer Alice aprobó solicitudes. Hoy el administrador le quita la asignación de Approver.
  2. Enterprise applications: La asignación ya no está en la enterprise application de la API. No se empuja nada a los tokens ya emitidos.
  3. Token endpoint: Entra va a dejar afuera roles: Approver en el próximo access token que emita para Alice.
  4. Caché de tokens: Mientras tanto, el access token de Alice en caché sigue diciendo roles: Approver, y vale hasta su exp.
  5. Regla del método: Su próxima aprobación llega con ese token. La API valida localmente: la firma, el tiempo y los claims están bien, y el rol viejo todavía pasa.
  6. MSAL Browser: Más tarde vence el access token. Antes de la próxima llamada, acquireTokenSilent lo nota y usa el refresh token.
  7. Token endpoint: Entra emite un access token nuevo. La asignación ya no está, así que roles viene vacío.
  8. MSAL Browser: MSAL guarda el token nuevo en caché y se lo da a la app.
  9. Regla del método: La misma aprobación ahora recibe 403: el token es válido, pero el rol no está en él.
  10. App Angular: Alice cierra sesión. logoutRedirect limpia la caché de MSAL para su cuenta.
  11. Endpoint de login: Entra termina su sesión en su endpoint de cierre de sesión. Los tokens ya emitidos no se retiran: siguen valiendo hasta que vencen.
  Tres cosas distintas: la vida de un token, una sesión y una asignación. La renovación las conecta; nada retira un token ya emitido, por eso las duraciones importan.
L. Configurar el tenant
  1. Administrador: En el Entra admin center, el administrador registra dos aplicaciones, no una: el destinatario del token tiene que quedar a la vista.
  2. App registrations: El registro de la API: Application ID URI api://API_CLIENT_ID, scopes delegados Requests.Read y Requests.Approve, el app role de usuario Approver, access tokens v2. El registro de la SPA: un cliente público con la redirect URI http://localhost:18094/redirect, sin secreto.
  3. Enterprise applications: Cada registro recibe un service principal en el tenant: su enterprise application.
  4. Enterprise applications: Ahí el administrador le asigna Approver a un usuario de prueba, y otorga el consentimiento si los usuarios no pueden consentir por su cuenta.
  5. Token endpoint: Desde ahora, un access token para ese usuario y esta API trae los scopes consentidos en scp y Approver en roles.
  6. Claves de firma: Spring va a verificar esos tokens con las claves publicadas para el issuer fijo del tenant.
  7. JwtDecoder: Con AUTH_MODE=entra, el decoder confía solo en https://login.microsoftonline.com/TENANT_ID/v2.0 y en sus claves. La clave del kit deja de ser de confianza.
  8. Emisor de tokens: Un token de prueba ahora recibe 401. La sonda prueba el cambio, no que una persona real haya iniciado sesión.
  Los registros son configuración, no prueba. El recorrido del tenant registra solo lo que observaste: un inicio de sesión, una lectura propia, un rechazo por rol y una aprobación permitida.
M. Lo que CORS y PKCE no frenan
  1. Script inyectado: Un script se mete en la página por un renderizado inseguro o una dependencia comprometida. Corre con el origen de la página.
  2. MSAL Browser: Le puede pedir un token a MSAL igual que la app. PKCE protegió el canje del code; no hace nada contra código que ya corre en la página.
  3. Script inyectado: Ahora tiene un access token válido.
  4. App Angular: O simplemente maneja el código propio de la app para mandar pedidos.
  5. CORS y filtro bearer: La API ve un token válido desde un origen permitido. Nada distingue este pedido de uno de la propia Alice.
  6. node lab.mjs: CORS es una regla que cumplen los navegadores. El lab llama sin ningún header Origin, y la API responde como le respondería a cualquiera: 401 sin token, 200 con uno válido.
  7. CORS y filtro bearer: Un preflight desde https://stranger.invalid recibe 403: un navegador bloquearía esa página. CORS nunca reemplazó al token.
  CORS y PKCE cierran una puerta cada uno. Ninguno protege la API de alguien que tiene un token válido: eso lo hacen la validación y la autorización, y la prevención deja afuera a los scripts.
N. Otra API, otra audiencia
  1. Controlador: Supongamos que el controlador tiene que leer el jefe de Alice desde Microsoft Graph.
  2. Otra API: Reenviar el token entrante falla: su audiencia es la API de compras, y Graph lo tiene que rechazar.
  3. Controlador: El diseño correcto: un servicio intermedio confidencial usa el flujo on-behalf-of en el token endpoint de Entra para obtener un token cuya audiencia sea Graph.
  4. Otra API: Ese token es para Graph, bajo el consentimiento de Graph. Un proceso nocturno sin usuario usaría en cambio client credentials y su propia política de endpoints.
  Un token es para una audiencia. Llegar a otra API en nombre del usuario es otro diseño, con su propio consentimiento y su propio modelo de amenazas; el kit lo deja como ejercicio.
