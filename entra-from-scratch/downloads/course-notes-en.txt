What Microsoft Entra ID does
Identity is a starting point. A secure application carries that evidence across explicit boundaries.

The identity provider in the picture
Microsoft Entra is a family of identity and network access products. This course focuses on Microsoft Entra ID in a workforce tenant and the Microsoft identity platform used by applications. It does not survey every Entra product.

Entra ID helps an organization manage identities, authenticate sign-ins and issue tokens for applications. Our Angular client uses that identity platform to obtain evidence for the Spring API. The API decides what the caller may do, and PostgreSQL enforces database privileges and row policy.

Think of a purchase request: an employee can sign in, yet lack permission to approve it. An approver can have the right role, yet be forbidden to approve their own purchase. The distance between those statements is where this course spends its attention.

The names and standards you will encounter
Older documentation often says Azure Active Directory or Azure AD. Microsoft announced the Entra ID name in 2023; that rename did not turn it into Windows Server Active Directory. OAuth and OpenID Connect are separate standards used in the application protocol.

2012 OAuth 2.0: RFC 6749 defines the authorization framework, including authorization-code and client-credentials grants.
2014 OIDC: OpenID Connect Core 1.0 defines an identity layer on OAuth 2.0.
2015 PKCE: RFC 7636 specifies a proof-key mechanism for authorization code exchange.
2023 Entra ID: Microsoft announces the new name for Azure Active Directory.
2025 OAuth BCP: RFC 9700 records updated OAuth security best current practice.

Where it fits in this application
These are the responsibilities practiced by the course.
Workforce sign-in: Use a tenant identity and its applicable sign-in policies rather than collecting a company password inside the SPA.
Resource-specific access: Acquire delegated access to an API and validate the token at that API.
Managed assignment: Define a small app-role vocabulary and assign users through the organization's identity administration.

What this course does not delegate to Entra
The following are design judgments of this course, not a claim that an identity product solves every application requirement.
Who owns request 42?: Record ownership is application data. Validated identity plus an API/database predicate.
May a request approve itself?: A role cannot represent every relationship and state. An explicit business rule enforced atomically.
May JDBC connect?: The database connection has a distinct principal and credential. Database authentication and least-privilege grants.
Is this deployment secure?: A successful login does not test transport, supply chain or operational controls. Threat modeling and evidence from the deployed system.

1. Which identities and tenants will this application accept?
2. Which component receives each token, and which audience must it validate?
3. What can the client do on behalf of the user, and what may that user do?
4. How will tenant, owner and mutable state constrain every data path?
5. What must happen when a role changes, a token expires or an identity service is unavailable?

01. Four components, four responsibilities
=================================================================
A request crosses boundaries; trust does not travel automatically.
Evidence route: local

The browser is controlled by its user
Angular can improve navigation, hide unavailable actions and display an account name. A user can also inspect its bundle, change its JavaScript or send an HTTP request without it. The browser is a client of the API, not a protected extension of the API. Anything necessary for permission enforcement must survive a caller bypassing the interface.
Rule: A route guard is a usability control, not an API boundary.

The API owns the business decision
Entra issues a token for a resource under its identity and consent policies. Spring validates that token and then applies the application's rules. Knowing that Alice authenticated does not tell Entra whether purchase request 42 is Bob's, whether it is pending, or whether this purchase exceeds a limit. Those facts belong to the application.
Rule: Identity evidence is an input to authorization, not its complete answer.

The database sees a connection
PostgreSQL authenticates the application's database role. It does not automatically know which browser user caused a query. Our API carries validated tenant and subject context into a transaction and also constrains the SQL. These are separate connections with separate credentials. A token sent to the API is not forwarded as a PostgreSQL password.
Rule: Name the principal at every hop.

02. Authentication and authorization
=================================================================
Who is represented? What is this caller allowed to do?
Evidence route: local

Two questions with different evidence
Authentication establishes an identity according to a mechanism and its trust assumptions. Authorization evaluates whether an action is permitted. At sign-in, Entra authenticates the person. At the API, Spring authenticates the bearer request using a validated token. Neither operation proves the human is physically present for every subsequent HTTP request.
Rule: A bearer request presents evidence; possession matters.

Policy is a conjunction
Our approval endpoint requires an access token for this API, a delegated Requests.Approve scope, the user app role Approver, the correct tenant, another person's request and a pending status. Each requirement contributes a distinct fact. Removing any necessary fact should deny the operation, even if every other condition is true.
Rule: Write the policy as AND before writing annotations.

Identity is necessary but insufficient
Alice can be authenticated and still lack a role. An approver can have a role and still be forbidden to approve their own request. A correct identity can be associated with a record in another tenant. Denial is often the correct operation of a secure system, not a sign-in defect to fix by broadening permissions.
Rule: A denial must be explained at the boundary that made it.

03. Tenant, application, service principal
=================================================================
Separate the application definition from its presence in a directory.
Evidence route: tenant

A directory boundary
A workforce tenant contains identities and configuration for an organization. The tenant ID identifies that directory. Our baseline accepts one tenant with an explicit issuer. Replacing that issuer with common is not a safe shortcut to a multitenant application: onboarding, issuer validation and data partitioning would all need a design.
Rule: A tenant is part of the trust boundary, not just a login hint.

Definition and local instance
An app registration creates an application object in its home directory. A service principal represents the application in a tenant; Enterprise applications is the administrative view used for many of those tenant-level settings. The application client ID identifies the app, while object IDs identify directory objects. Copying the wrong ID can create a configuration that looks plausible but names the wrong thing.
Rule: Application ID and object ID are different identifiers.

A stable application identity key
A person's display name or email can change and can be reused. The API uses the validated pair tid and oid as its tenant-local identity key. Guest identities need attention: the object represented in the resource tenant is not interchangeable with an object from the person's home tenant. Define deprovisioning and data ownership explicitly.
Rule: Readable names are labels; authorization uses validated identifiers.

04. Two registrations, one application experience
=================================================================
Angular is the client. Spring is the resource.
Evidence route: tenant

Register the recipient separately
The API registration defines the resource: its application ID URI, delegated scopes and the user app role Approver. The SPA registration defines the public client and its allowed redirect URI. Keeping them separate makes the token's recipient visible. Requesting api://API_CLIENT_ID/Requests.Read expresses both a resource and a delegated permission.
Rule: The access token audience names the API, not the interface.

Public means unable to keep a secret
The SPA client ID and tenant ID are public configuration. A client secret embedded in JavaScript would be readable by every visitor; it would not turn Angular into a confidential client. Register a Single-page application redirect path. The sample uses http://localhost:18094/redirect for local development and a dedicated MSAL redirect bridge.
Rule: A browser application must not rely on a stored client secret.

Make token expectations explicit
Configure the API to request v2 access tokens with requestedAccessTokenVersion set to 2. The API validates the v2 issuer, its own client ID as audience, tenant, delegated scopes and allowed client. The version of the authorization endpoint alone does not choose the resource's access-token format. A registration is configuration, not deployed API code.
Rule: A registration and a resource-server validator must agree.

05. Follow the authorization code
=================================================================
Understand the redirect without implementing an identity protocol yourself.
Evidence route: local

A request leaves the application
MSAL creates a fresh verifier and its S256 challenge, then navigates to the tenant's authorization endpoint with the client, redirect URI and requested scopes. Entra handles sign-in and applicable policies. The application does not collect the Entra password. Returning to a registered callback does not by itself mean every later API operation is authorized.
Rule: Let the identity provider handle the credentials.

The code is exchanged
The authorization response carries a short-lived code. The client redeems it with the original verifier. A captured code without the verifier should not suffice. State correlates the response with the initiated interaction; the OIDC nonce binds identity-token evidence to the authentication request. These defenses serve different purposes, and the library manages their lifecycle.
Rule: PKCE binds code redemption to the initiating client instance.

Know the defense's limit
PKCE reduces the usefulness of intercepted authorization codes. It does not encrypt browser storage, prevent malicious script from acting inside the origin, or make a stolen bearer access token unusable. The fixture does not implement this flow. Its hashing exercise demonstrates the challenge relationship only; the tenant workbook observes a real redirect and exchange.
Rule: A code-interception defense is not an XSS defense.

06. Three token jobs
=================================================================
Identity, resource access and renewal are different jobs.
Evidence route: local

ID token: a client sign-in result
An ID token belongs to the OIDC relationship between Entra and the client. It can help the client present the signed-in account. It is not the credential our API accepts. In the separate-registration design its audience identifies the SPA, which gives Spring a concrete reason to reject it even if the signature is genuine.
Rule: A genuine token can be the wrong token for this recipient.

Access token: evidence for a resource
Angular acquires an access token for the purchase API and sends it in the Authorization header. The API validates it and evaluates permissions. A Microsoft Graph token targets Microsoft Graph; the purchase API must reject it. The client should treat access tokens as opaque credentials rather than basing business decisions on their decoded contents.
Rule: Every access token has a recipient and a limited purpose.

Renewal belongs to the client library
A refresh token is used with the identity provider to obtain further tokens; it is not sent to the purchase API or database. MSAL manages the cache and renewal process. A JWT payload is base64url-encoded, not encrypted. Reading a payload proves neither its origin nor its validity. Keep raw tokens out of logs, URLs, screenshots and public decoding sites.
Rule: Decoding is inspection. Validation is a security decision.

07. Scopes and consent
=================================================================
Permission granted to a client is not unlimited authority over a person's data.
Evidence route: local

A delegated permission
A scope is a permission the resource exposes for a client acting with a signed-in user. Our two delegated scopes are Requests.Read and Requests.Approve. Entra puts granted delegated scopes in the access token's space-delimited scp claim. Spring maps them to SCOPE_ authorities. A scope is not an SQL row filter.
Rule: A delegated scope describes permitted client activity, not ownership.

Consent is a separate decision
Consent records permission for the client to request access under the relevant tenant policies. Some permissions or policies need administrator consent; others may permit user consent. A prompt being accepted does not make the user an approver or transfer ownership of every purchase request. Our API still evaluates role, tenant and record state.
Rule: Consent does not replace the application's authorization rules.

Request only what the operation needs
A production client can request scopes as features require them. The teaching client requests both course scopes so the experiment can isolate user roles and row rules. That choice is explicitly broader than a read-only feature needs. Removing an approval scope should deny approval while leaving a permitted read usable.
Rule: Evaluate the requested permission set, not just whether a prompt appeared.

08. Roles and resource rules
=================================================================
A role grants a category of power; a record still has its own constraints.
Evidence route: local

An application role
Approver is an app role defined on the API registration, with Users as its allowed member type for this course. Assign it to the practice approver through the API Enterprise application. The API-targeted access token can then carry Approver in roles. A tenant administrator role is a different kind of authority and does not automatically mean purchase approver.
Rule: Define roles in the resource whose policy consumes them.

Role membership is only one predicate
Our approver can approve a colleague's pending request in the same tenant. They cannot approve their own request or an already approved request. Spring checks the scope and role; SQL atomically checks the tenant, ownership relation and current state. This combination is a useful example of role-based and attribute-based conditions working together.
Rule: Role-based access still needs object-level authorization.

Groups are not a free substitute
Groups can help administrators assign roles. Building API policy directly around a long groups claim adds concerns such as overage and directory lookups. The course keeps the runtime contract small: one explicit user role. 16. Transactions, pools and races
=================================================================
Authorization must survive connection reuse and concurrent requests.
Evidence route: local

A pool reuses physical connections
Connection pools make database access efficient by reusing connections across requests. A session-wide setting for Alice could remain when Bob later borrows that connection. Spring establishes the context inside the same transaction as the query using set_config with the local flag true. On transaction completion, that local setting no longer authorizes the next transaction.
Rule: The lifetime of identity context must match the transaction that uses it.

Check and change together
A separate read of PENDING followed by an unconditional update invites a race: two callers can both observe the old state. The sample uses one UPDATE with tenant, not-owner and PENDING predicates. Under the normal PostgreSQL behavior used here, concurrent attempts cannot both change the same row from pending to approved. One succeeds; the other matches no eligible row.
Rule: Put mutable authorization conditions into the atomic state transition.

Define the boundary of the transaction
The SQL update and its row context share a transaction. Sending an email or charging a card would add an external effect that a database rollback cannot automatically undo. A real approval service needs an explicit strategy such as a transactional outbox, idempotency and retry policy. A successful row transition does not prove exactly-once business delivery.
Rule: Database atomicity ends at the database transaction boundary.

19. Users, workloads and downstream APIs

Choose the principal before choosing the grant.
Evidence route: local

A background job has no signed-in user

20. Browser threats and architecture choices
=================================================================
Understand what CORS, PKCE and a BFF each change.
Evidence route: local

CORS is a browser cooperation rule
A cross-origin browser request may first send an OPTIONS preflight. Our API permits the exact local frontend origin, methods and Authorization header. CORS is not a substitute for token validation or authorization: a command-line caller can omit Origin entirely and still reach the API. It must face the same authentication and business checks.
Rule: An allowed origin is not an authenticated principal.

Browser script is inside the user's session
XSS can execute within the application origin and act with the session's powers. CSP, safe rendering, dependency maintenance and careful token handling reduce risk; PKCE does not solve malicious script execution. The sample uses bearer headers and no cookie login, which is why its API disables CSRF protection. Adding cookie authentication would change that decision.
Rule: A security setting is valid only under its stated architecture assumptions.

A backend for frontend moves the boundary
A BFF can keep OAuth tokens on the server and give the browser a Secure, HttpOnly session cookie with a deliberate SameSite and CSRF policy. That reduces direct exposure of tokens to browser code, while introducing session and server-side lifecycle responsibilities. XSS can still issue actions through an authenticated session. Choose the pattern based on the threat model and operational capacity.
Rule: Moving a credential changes the risks; it does not remove authorization.

GLOSSARY
Authentication: Establishing an identity under a specified mechanism and trust policy.
Authorization: Deciding whether a principal may perform an action on a resource.
Principal: The identity represented at a security boundary: a user, application or database role.
Trust boundary: A point where one component must decide which external assertions it accepts.
Tenant: A directory boundary for identities and application configuration.
Application object: The application definition in its home tenant.
Service principal: The application representation inside a particular tenant.
Client ID: The public application identifier, distinct from a directory object ID.
Public client: A client such as a SPA that cannot keep an embedded credential secret.
Confidential client: A server-side client able to protect credentials under its deployment assumptions.
OAuth 2.0: An authorization framework for obtaining access to resources.
OpenID Connect: An identity layer on OAuth 2.0, including the ID token sign-in result.
Authorization code: A short-lived artifact redeemed at the token endpoint, with PKCE in the SPA flow.
PKCE: A challenge and verifier binding the code redemption to the initiating client instance.
State: A value used to correlate an authorization response with the initiated interaction.
Nonce: An OIDC value that binds identity-token evidence to the authentication request.
Redirect URI: The registered callback destination for an authorization response.
ID token: The OIDC sign-in result intended for the client; not the purchase API credential.
Access token: A credential intended for a resource, which validates it and enforces policy.
Refresh token: A renewal credential used with the identity provider through the client library.
Bearer: A credential whose possession permits its presentation; protect it from disclosure.
JWT: A token format containing encoded claims and a signature; decoding is not validation.
Issuer / iss: The authority that issued the token, checked against configured trust.
Audience / aud: The intended recipient of a token; this API accepts its own resource identifier.
Tenant ID / tid: The directory identifier, validated and used in the data boundary.
Object ID / oid: The object identity inside a tenant; paired with tid for the user key here.
Authorized party / azp: The client application identifier in a v2 token, checked by this API contract.
Scope / scp: A delegated permission value; multiple values are space-delimited in scp.
Consent: A grant enabling client access under tenant policy, distinct from business entitlement.
App role / roles: An application-defined role granted to a principal and represented in roles.
Authority: A permission string Spring evaluates after conversion from accepted claims.
JWK set: A published set of public keys used to verify signatures within a trusted issuer policy.
IDOR: A missing object-level authorization check; an identifier alone is not permission.
Row-level security: Database policies filtering row access for non-bypassing roles.
BYPASSRLS: A privileged PostgreSQL role attribute that bypasses row security.
Connection pool: Reusable database connections that must not leak request identity context.
Transaction-local context: Settings whose effective lifetime ends with the transaction.
On-behalf-of: A middle tier obtaining a downstream delegated token rather than forwarding the wrong audience.
Client credentials: Application access without a signed-in user.
CORS: A browser cross-origin access mechanism, not caller authentication.
CSRF: Unwanted authenticated actions induced through browser credential behavior; relevant to session design.
XSS: Malicious script execution within an application origin.
BFF: A backend for frontend that can retain OAuth tokens server-side and provide a browser session.
CAE: Continuous access evaluation for supported resources and scenarios, not automatically provided by local JWT validation.
