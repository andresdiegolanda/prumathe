01. Un proceso con límites
=================================================================
Un contenedor empieza con un proceso, no con una computadora pequeña.

El proceso principal
Un contenedor ejecuta un comando con una vista aislada de procesos, red y archivos. En Linux comparte el kernel del host. Docker Desktop ejecuta los contenedores Linux dentro de su entorno Linux.
→ El aislamiento no crea un kernel separado.

Una imagen se vuelve contenedor
La imagen aporta archivos y valores por defecto. Docker agrega configuración de ejecución y una capa escribible por contenedor. Dos contenedores de una imagen pueden tener nombres y archivos distintos.
→ La misma imagen no implica compartir estado escribible.

Un experimento acotado
Ejecutá id e inspeccioná los procesos dentro de la imagen. Nuestra aplicación usa UID 10001, no root. Eso reduce privilegios, pero no vuelve inofensivo al código no confiable ni reemplaza la seguridad del host.
→ Nombrá el límite que observaste.

LABORATORIO
1. Inspeccioná el usuario
Ejecutá un comando corto en vez del servidor por defecto. --rm borra este contenedor temporal cuando termina.

docker run --rm prumathe-signal:1.0.0 id

Observá: UID 10001, no root.

2. Mirá procesos aislados
Ejecutá ps en otro contenedor. La lista es su vista, no la de todas las aplicaciones del host.

docker run --rm prumathe-signal:1.0.0 ps

Observá: Una lista pequeña con ps; no aparecen aplicaciones del host.

3. Escribí en una capa temporal
Creá una marca dentro de este contenedor. El shell y la marca desaparecen cuando termina.

docker run --rm prumathe-signal:1.0.0 sh -c 'echo isolated > /tmp/marker; cat /tmp/marker'

Observá: Se imprime isolated.

4. Partí de la imagen otra vez
Revisá la misma ruta en otro contenedor nuevo. test comprueba ausencia e imprime PASS solo si se cumple.

docker run --rm prumathe-signal:1.0.0 sh -c 'test ! -f /tmp/marker && echo PASS'

Observá: PASS: el contenedor anterior no editó la imagen.

CONTROL
1. ¿Qué comparten los contenedores Linux en un host Linux?
A. El kernel
B. Todos los archivos escribibles
C. El mismo espacio de PID por defecto
Respuesta: A. Los namespaces aíslan vistas; no arrancan otro kernel.

2. Otro contenedor cambia /tmp. ¿Qué pasa con el primero?
A. Su /tmp siempre cambia también
B. Se reconstruye la imagen
C. Su capa escribible sigue separada
Respuesta: C. Solo un montaje compartido explícito cambia ese límite.

3. ¿Ejecutar sin root elimina todo riesgo?
A. Sí; la red está deshabilitada
B. No; limita un conjunto de privilegios
C. Sí; el kernel está separado
Respuesta: B. La aplicación todavía puede acceder a sus archivos y su red permitidos.


02. Arrancar, parar, borrar
=================================================================
Un contenedor detenido y uno borrado son estados distintos.

Run crea y arranca
docker run crea un contenedor y arranca su comando. docker start arranca uno existente que está detenido. Un proceso en primer plano mantiene vivo al contenedor; al terminar el comando principal, se detiene.
→ El contenedor vive mientras corre su proceso principal.

Parar cambia el ciclo de vida
docker stop solicita una terminación ordenada y fuerza la finalización si vence el plazo. El manejo de señales de la aplicación determina si termina bien el trabajo. Nuestro servidor didáctico atiende SIGTERM y termina enseguida; no drena los pedidos en curso.
→ Recibir una señal no equivale a terminar el trabajo.

Borrar termina esta capa escribible
Detener conserva la capa escribible. Borrar el contenedor elimina esa capa; los volúmenes tienen otro ciclo de vida. Inspeccioná el estado antes de borrar el contenedor de práctica.
→ Stop conserva; remove descarta la capa del contenedor.

LABORATORIO
1. Creá el proceso con nombre
Usá el nombre propio dk-life. Si repetís después de interrumpir, borrá solo dk-life con docker rm -f dk-life antes de este paso.

docker run -d --name dk-life prumathe-signal:1.0.0

Observá: Un ID de contenedor. El servidor queda en primer plano dentro.

2. Escribí y detené
Escribí una marca y detené el proceso. Inspeccioná el estado resultante.

docker exec dk-life sh -c 'echo retained > /tmp/life'
docker stop dk-life
docker inspect --format '{{.State.Status}} {{.State.ExitCode}}' dk-life

Observá: exited 0: el proceso atendió SIGTERM; 137 significaría que hubo que matarlo. El contenedor todavía existe.

3. Reiniciá el mismo contenedor
start reutiliza el contenedor y su capa. Leé la marca después.

docker start dk-life
docker exec dk-life cat /tmp/life

Observá: retained: detener no borró la capa.

4. Borrá esta instancia
Detené y borrá solo el contenedor de práctica. Uno temporal nuevo no ve su marca.

docker stop dk-life
docker rm dk-life
docker run --rm prumathe-signal:1.0.0 sh -c 'test ! -f /tmp/life && echo PASS'

Observá: PASS. La imagen sigue disponible.

CONTROL
1. ¿Cómo retomás un contenedor detenido?
A. docker run crea la misma identidad
B. docker build
C. docker start
Respuesta: C. start reutiliza el contenedor existente; run crea otro.

2. ¿Cuándo se detiene normalmente?
A. Cuando cambia el tag de la imagen
B. Cuando termina su comando principal
C. Cuando se leyeron todos los logs
Respuesta: B. El entorno sigue al proceso principal.

3. ¿Qué sobrevive a stop pero no al borrado sin montaje?
A. Archivos de la capa escribible
B. El proceso en ejecución
C. Una conexión TCP abierta
Respuesta: A. Los contenedores detenidos conservan archivos hasta que los borrás.


03. Imágenes y capas
=================================================================
Bloques de solo lectura, una capa escribible por contenedor.

Una imagen es el resultado de una receta
Una imagen contiene capas del sistema de archivos y configuración, como el comando y usuario por defecto. No es un proceso en ejecución. Un tag es una referencia legible, no una garantía de inmutabilidad.
→ Archivos más metadatos, antes de ejecutar.

Los cambios son del contenedor
Escribir un archivo durante la ejecución no edita la imagen. Otro contenedor nuevo parte de la imagen otra vez. Borrar un archivo en una capa posterior puede ocultarlo sin quitar sus bytes de las capas anteriores.
→ Nunca metas secretos en una capa.

Inspeccioná lo que distribuís
docker image history muestra la historia de construcción; image inspect muestra configuración e identificadores. El ID local describe configuración; un digest de registro identifica un objeto del registro. No supongas que son el mismo hash.
→ Inspeccioná contenido e identidad aparte del nombre.

LABORATORIO
1. Leé los valores por defecto
Inspeccioná usuario y comando sin arrancar un proceso.

docker image inspect --format '{{.Config.User}} {{json .Config.Cmd}}' prumathe-signal:1.0.0

Observá: 10001:10001 y el comando del servidor Python.

2. Inspeccioná la historia
Leé los pasos de imagen. Las instrucciones solo de metadatos no necesitan agregar archivos.

docker image history prumathe-signal:1.0.0

Observá: Instrucciones de build, tamaños y metadatos.

3. Cambiá una capa de ejecución
Escribí un archivo temporal y comprobá que existe ahí.

docker run --rm prumathe-signal:1.0.0 sh -c 'echo runtime > /tmp/image-test; test -f /tmp/image-test && echo PASS'

Observá: PASS.

4. Comprobá el artefacto original
Un contenedor nuevo arranca sin ese archivo de ejecución.

docker run --rm prumathe-signal:1.0.0 sh -c 'test ! -f /tmp/image-test && echo PASS'

Observá: PASS: no se modificó la imagen.

CONTROL
1. ¿Escribir dentro de un contenedor actualiza su imagen?
A. No, cambia su capa escribible
B. Sí, para todos los contenedores nuevos
C. Solo al usar exec
Respuesta: A. La imagen sigue siendo el punto de partida.

2. Copiás un secreto y lo borrás en otra capa. ¿Está protegido?
A. Sí; history cifra los archivos
B. No; una capa anterior puede conservarlo
C. Sí; borrar reescribe todas las capas
Respuesta: B. Usá montajes de secretos de build si necesitás credenciales.

3. ¿Un tag puede apuntar a otra imagen después?
A. No, los tags son hashes
B. Solo si paran todos los contenedores
C. Sí
Respuesta: C. Usá un digest para identificar contenido inmutable del registro.


04. Construí una imagen
=================================================================
Convertí archivos fuente en un paquete explícito y repetible.

El contexto de build
docker build usa un directorio como contexto. COPY lee archivos de ese contexto; .dockerignore excluye archivos innecesarios o sensibles. Nuestro Dockerfile copia solo server.py y probe.py y no instala paquetes de Python.
→ Controlá lo que entra al build.

La caché sigue a los insumos
Una instrucción sin cambios y con los mismos insumos puede reutilizar resultados. Cambiar el código copiado invalida ese paso y los dependientes posteriores. Dejá la preparación estable antes del código que cambia seguido.
→ Ordená las capas según cuánto cambian.

Los valores por defecto son parte del artefacto
USER elige el usuario de ejecución. CMD aporta el comando por defecto; la forma exec evita un shell extra. EXPOSE documenta un puerto pero no lo publica. Fijamos el digest base y APP_VERSION es un argumento de build sin secretos.
→ La configuración del build no es la de ejecución.

LABORATORIO
1. Construí desde un contexto explícito
El argumento final app elige el contexto. Leé app/Dockerfile y app/.dockerignore antes.

docker build -t prumathe-signal:1.0.0 app

Observá: Un build exitoso.

2. Repetí los mismos insumos
Repetí el build. Buscá pasos en caché; el tiempo solo no prueba reutilización.

docker build --progress=plain -t prumathe-signal:1.0.0 app

Observá: Los pasos sin cambios elegibles informan CACHED.

3. Cambiá un argumento sin secretos
Construí otro artefacto con distinto valor de versión. El tag 1.0.0 sigue disponible.

docker build --build-arg APP_VERSION=1.1.0 -t prumathe-signal:1.1.0 app

Observá: Otra imagen con el tag 1.1.0.

4. Inspeccioná el resultado
Leé el entorno de cada artefacto. Son valores por defecto antes de reemplazos de ejecución.

docker run --rm prumathe-signal:1.0.0 printenv APP_VERSION
docker run --rm prumathe-signal:1.1.0 printenv APP_VERSION

Observá: 1.0.0 y después 1.1.0.

CONTROL
1. ¿Qué puede leer COPY acá?
A. Cualquier archivo de cualquier host
B. Solo archivos de contenedores activos
C. Archivos del contexto que no fueron excluidos
Respuesta: C. El contexto define el límite de entrada.

2. ¿Qué hace EXPOSE 8080?
A. Documenta el puerto previsto
B. Publica 8080 en el host
C. Crea un Service de Kubernetes
Respuesta: A. Publicar requiere configuración explícita de ejecución.

3. ¿Por qué copiar código después de la preparación estable?
A. Para ejecutar sin imagen
B. Para reutilizar pasos anteriores de caché
C. Para cifrar código
Respuesta: B. Editar código no necesita repetir la preparación estable.


05. Datos que sobreviven al contenedor
=================================================================
Separá la vida del proceso de la vida de sus datos.

Tres lugares para escribir
La capa escribible pertenece a un contenedor. Docker administra un volumen con nombre y permite volver a montarlo. Un bind mount expone una ruta del host; importan su organización y sus permisos.
→ Elegí almacenamiento según su dueño y duración.

Reemplazá el proceso
Compose monta signal-data en /data. Escribí una marca, reemplazá el contenedor y leela. El reemplazo usa el mismo volumen. Montar almacenamiento no coordina automáticamente escrituras simultáneas.
→ La persistencia es independiente de la identidad del proceso.

Retener no es respaldar
docker compose down conserva volúmenes con nombre por defecto; down -v elimina los del proyecto. Ni un volumen ni un bind mount son un respaldo. El lab nunca te pide purgar recursos de Docker ajenos.
→ Conocé qué se borra antes de limpiar.

La app corre como UID 10001 y es dueña de /data. Guardá una marca.

docker compose exec -T app sh -c 'echo volume-survived > /data/marker'

Observá: La escritura funciona sin root.

3. Reemplazá el contenedor
Recreá solo app conservando el volumen.

Observá: Una app reemplazada llega a healthy.

4. Leé datos conservados
Revisá la marca y el tipo de montaje. No uses down -v salvo que quieras borrar datos de práctica.

Observá: volume-survived y un volumen montado en /data.

2. ¿Qué hace que un bind mount dependa del host?

B. Su estado HTTP
C. Su ruta de origen y sus permisos
Respuesta: C. El host aporta los archivos montados.

06. Nombres en una red
=================================================================
Encontrá un servicio sin memorizar la dirección del contenedor.

Una red tiene un alcance
Compose crea una red para el proyecto. Los contenedores conectados encuentran servicios por nombre. app se resuelve dentro de esa red; no se vuelve automáticamente un nombre de tu laptop.
→ Los nombres DNS pertenecen a un ámbito de red.

Localhost significa acá
Dentro del contenedor toolbox, localhost apunta al propio toolbox. Usá app:8080 para llegar a la aplicación. Reemplazarla puede cambiar su dirección, mientras el nombre de servicio sigue siendo útil.
→ Un servicio remoto no es tu dirección de loopback.

Conectividad no es autorización
Una red compartida permite comunicar; no autentica pedidos de la aplicación. El lab revisa DNS y HTTP por separado para no confundir una falla de resolución con un error de aplicación.
→ Diagnosticá nombre, conexión y después respuesta.

LABORATORIO
1. Arrancá el servicio de práctica
Desde labs, después de la lección 00. Arranca solo el proyecto Compose del curso.

docker compose up -d --wait app

Observá: La aplicación está healthy. No se reinicia otro proyecto.

2. Resolvé el nombre
Usá un contenedor temporal de la red. Reemplazar entrypoint permite inspeccionar DNS con la misma imagen. Desde el host, el nombre app no resuelve: el nombre existe solo dentro de la red de Compose.

docker compose run --rm --no-deps --entrypoint python toolbox -c "import socket; print(socket.gethostbyname('app'))"

Observá: Una IP interna que no tenés que fijar.

3. Consultá el endpoint interno
La URL de toolbox es http://app:8080. No interviene el puerto del host.

docker compose run --rm --no-deps toolbox

Observá: hello-compose y PASS.

4. Inspeccioná miembros de red
Leé solo la red del curso. Las direcciones son detalles de ejecución, no configuración durable.

docker network inspect prumathe-dk_default

Observá: La app está conectada a la red del proyecto.

1. ¿Adónde apunta localhost dentro de toolbox?
A. Al propio toolbox
B. Al host Docker automáticamente
C. Al servicio app
Respuesta: A. Cada espacio de red tiene su loopback.

2. ¿Qué dirección debería usar otro servicio acá?
A. Una IP fija de contenedor
B. localhost:18080
C. app:8080

3. ¿Compartir red autentica un pedido?

07. Publicá un puerto a propósito
=================================================================
Distinguí escuchar, declarar y publicar.

La aplicación escucha
Signal escucha en 0.0.0.0:8080 dentro del contenedor. Escuchar solo en 127.0.0.1 interno impediría que otros contenedores lleguen a ese socket. El proceso tiene que escuchar aunque la imagen declare EXPOSE.
→ Un puerto declarado no es un socket abierto.

El host reenvía tráfico
Compose publica 127.0.0.1:18080 hacia el puerto 8080 del contenedor. Tu navegador usa el puerto del host; otros contenedores usan el interno. Vincularlo a loopback limita ese punto publicado al host local.
→ El puerto del host y el del contenedor son coordenadas distintas.

Seguí el salto que falla
Revisá el mapeo y consultá la URL publicada y la interna. Un puerto ocupado impide un nuevo enlace. No resuelvas una colisión exponiendo todas las interfaces sin entender el alcance.
→ Seguí la ruta antes de cambiar el enlace.

LABORATORIO
1. Arrancá el servicio de práctica
Desde labs, después de la lección 00. Arranca solo el proyecto Compose del curso.

docker compose up -d --wait app

Observá: La aplicación está healthy. No se reinicia otro proyecto.

2. Leé la dirección publicada
Consultá a Compose qué dirección del host mapea al puerto interno.

docker compose port app 8080

Observá: 127.0.0.1:18080.

3. Seguí el lado interno
Este pedido sale desde la app. Abrí http://127.0.0.1:18080 aparte en tu navegador del host para comparar.

docker compose exec -T app python /app/probe.py http://127.0.0.1:8080 hello-compose

Observá: El mismo contenido y PASS. La URL del host devuelve ese servicio también.

4. Inspeccioná el enlace explícito
Revisá HostIp y HostPort en vez de suponer que EXPOSE publicó algo.

docker inspect --format '{{json .HostConfig.PortBindings}}' prumathe-dk-app-1

Observá: 8080/tcp mapea a 127.0.0.1 y 18080.

CONTROL
1. ¿Qué puerto usa el navegador del host?
A. 8080 siempre
B. El ID de proceso del contenedor
C. 18080
Respuesta: C. El mapeo lleva 18080 del host a 8080 del contenedor.

2. ¿EXPOSE puede arrancar un listener?
A. No
B. Sí
C. Solo en Linux
Respuesta: A. El proceso abre el socket.

3. ¿Qué limita 127.0.0.1 en este mapeo?
A. El tamaño de imagen

Respuesta: B. Vincula el lado del host a loopback.


08. Describí el sistema local
=================================================================
Servicios, redes y volúmenes en un archivo legible.

De comandos a un modelo
Compose nombra servicios y su configuración. La aplicación y toolbox opcional comparten red; solo app publica un puerto. El proyecto prumathe-dk delimita los recursos creados por el kit.
→ Leé la configuración antes de arrancarla.

Corriendo versus healthy
up -d --wait espera estado running o healthy. El health check de la imagen consulta /health. No prueba toda operación de negocio, y el orden de arranque común no equivale a readiness de dependencias.
→ Definí qué mide healthy.

Un ciclo de vida local
config muestra la configuración resuelta; ps muestra estado; logs muestra salida; down elimina contenedores y redes del proyecto. Compose en este host no aporta un plano de control distribuido de Kubernetes.
→ Usá una herramienta dentro de su alcance.

09. Configuración y secretos
=================================================================
Mantené estable el artefacto mientras cambia la configuración.

Entradas de ejecución
MESSAGE es una variable de entorno leída al arrancar el proceso. Dos contenedores de una imagen pueden mostrar mensajes distintos. No hace falta reconstruir para cambiar ese valor de ejecución.
→ Separá la versión de su entorno.

Los secretos no son argumentos de build

11. Tags, digests y distribución
=================================================================
Mové un artefacto sin confundir su nombre con su identidad.

Los tags son referencias
docker tag le da otro nombre a una imagen. No copia ni modifica sus capas. Un registro guarda contenido para pull y push; este curso usa imágenes locales y no publica en cuentas remotas.
→ Un tag nuevo no es un build nuevo.

Fijá contenido para reproducir
Un digest identifica contenido del registro. La imagen base y la de nodos de kind incluyen digests. Un tag como 1.0.0 comunica intención, pero reproducir requiere conservar el artefacto y sus insumos.
→ Los nombres son cómodos; la identidad del contenido es más fuerte.

Local no es estar en cada nodo
Una imagen en Docker de tu laptop no está automáticamente en el runtime del nodo Kubernetes. kind load docker-image copia el artefacto al clúster indicado. Usamos imagePullPolicy: Never para que se vea si falta importarlo.
→ Distribuir es un paso explícito.

14. El límite del Pod
=================================================================
Kubernetes planifica Pods, que contienen contenedores.

Una unidad de scheduling
Un Pod agrupa uno o más contenedores que comparten espacio de red y pueden compartir volúmenes declarados. Corren juntos en un nodo. Nuestro primer Pod tiene un contenedor para ver la relación entre proceso y Pod.
→ El Pod es la unidad desplegable mínima acá.

La identidad es temporal
Un Pod recibe nombre, UID y dirección de red. Reemplazarlo crea una identidad nueva aunque reutilices el nombre. No uses la IP de un Pod como dirección durable de clientes.
→ Reemplazar no es resucitar.

Los Pods sueltos no tienen controlador de reemplazo
El kubelet puede reiniciar un contenedor según su política. Borrar este Pod suelto elimina el objeto; no existe un Deployment que lo recree. Después agregamos el controlador que mantiene réplicas.

17. Una entrada estable
=================================================================
Un Service lleva tráfico a endpoints listos que coinciden.

Elegí por label
Un Service selecciona Pods mediante labels. Su nombre e IP virtual estables separan clientes de reemplazos de Pods. Nuestro Service recibe en 80 y envía a targetPort 8080.

Observá endpoints
Los EndpointSlices registran direcciones y readiness de los destinos. Un Service con selector incorrecto puede existir sin destinos útiles. Una respuesta DNS no prueba salud de la aplicación.
→ Revisá selectores y readiness si el tráfico no tiene destino.

Interno no significa público
Nuestro Service es ClusterIP, accesible dentro del clúster. Para depurar localmente, port-forward crea un túnel temporal mientras corre el comando. Un Ingress o Gateway necesita infraestructura adicional y queda fuera de este lab.
→ Un Service no publica automáticamente en internet.

20. Vivo, listo, arrancado
=================================================================
Elegí la pregunta correcta antes de elegir una sonda.

Readiness habilita tráfico
Una sonda de readiness fallida marca el Pod no listo. El Service normalmente excluye endpoints no listos; el contenedor puede seguir corriendo. Usala para decidir si la instancia puede atender ahora.
→ No listo significa dejar de enviar tráfico normal del servicio.

Liveness dispara reinicio
Fallas repetidas de liveness provocan reinicio del contenedor por el kubelet según la política. Una caída de dependencia suele ser una mala prueba de liveness: reiniciar todo puede empeorar la recuperación.
→ Reiniciá cuando reiniciar pueda ayudar.

Startup da tiempo de inicialización
Una startup probe demora readiness y liveness hasta tener éxito. Su umbral y período definen un presupuesto de inicialización. En el lab fallás readiness, observás el estado de tráfico y lo restaurás sin reiniciar el proceso.

21. Requests, limits y ubicación
=================================================================
El scheduler necesita un presupuesto de recursos declarado.

Requests reservan capacidad de scheduling
El scheduler usa requests para ubicar un Pod, junto con restricciones como taints y selección de nodo. CPU 50m significa 0,05 CPU; memoria 32Mi son 32 mebibytes. Un uso actual bajo no borra los requests declarados.
→ La ubicación usa necesidades declaradas, no deseos.

Limits restringen ejecución
Un límite CPU puede restringir ejecución; exceder memoria puede provocar terminación OOM. Requests y limits hacen trabajos distintos. Los límites solos no garantizan latencia ni protección ante cualquier falla del nodo.
→ El presupuesto de scheduling y el techo de ejecución son distintos.

Pending es evidencia
El Pod no-room pide 1000 CPU, deliberadamente más de lo que ofrece este clúster de estudio. describe muestra FailedScheduling y su causa. Diagnosticá la restricción antes de cambiar requests o agregar nodos.
→ Pending es un estado para explicar, no para reiniciar a ciegas.
