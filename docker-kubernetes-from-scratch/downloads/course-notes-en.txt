DOCKER & KUBERNETES FROM SCRATCH. COURSE NOTES
Kubernetes 1.37.0 | 2026-10-18 | v1.3.1

WHAT DOCKER AND KUBERNETES ARE
=================================================================
What they are, where they came from, where they fit and where they do not. Read it once; the lessons do the rest.

An isolated process and a declared state
A container is a process that the Linux kernel isolates with namespaces (its own view of processes, network and filesystem) and limits with cgroups (CPU and memory), and that shares the host kernel with every other container. It is not a virtual machine: there is no guest operating system, only a process with the files it needs. Those files travel as an image, immutable and made of layers. Docker is the tool that builds that image from a Dockerfile, runs it as a container and distributes it through a registry; Compose describes several containers on one host in a single file.
Kubernetes is a platform for running many containers across many machines. You declare the desired state as objects of its API: a Deployment with three replicas of an image, a Service in front of them. Controllers compare that declaration with what exists and act on the difference; the scheduler places each Pod on a node; a Service gives the Pods a stable name and address while they come and go; a rollout replaces instances a few at a time. Kubernetes does not need Docker to run containers: it talks to a runtime through the Container Runtime Interface, usually containerd. The image you built with Docker is the same one that runtime pulls.
→ Docker runs a container; Kubernetes keeps a declared state.

Where they came from
Docker was shown in public in March 2013, in a talk at PyCon by Solomon Hykes, from the team at dotCloud, which already used Linux containers. The kernel pieces existed: namespaces had been in Linux since 2008 and control groups with them, and LXC and union filesystems were in use. What Docker added was the image, the Dockerfile, the registry and one command line to build, run and share. In June 2015 Docker donated its container format and its runtime, runC, to the Open Container Initiative, formed under the Linux Foundation; the image and runtime specifications that came out of it are why an image built with Docker runs under any CRI runtime.
Kubernetes came out of Google in 2014, written by engineers who had built and operated Borg, the system that had run Google's containers for more than a decade. Version 1.0 arrived on July 21, 2015, and on the same day Google, the Linux Foundation and a group of companies formed the Cloud Native Computing Foundation and seeded it with Kubernetes. Since then the changes that matter most to how it is used are the ones on the timeline.
2013 Docker: Solomon Hykes shows Docker in public at PyCon on March 15, built on namespaces and control groups the kernel had had since 2008.
2014 Kubernetes: Google open sources Kubernetes, built on what it had learned with Borg.
2015 OCI and CNCF: June 22: the Open Container Initiative is formed and Docker donates runC. July 21: Kubernetes 1.0 and the Cloud Native Computing Foundation.
2020 Compose spec: April: the Compose file format becomes an open specification. Late in the year, Kubernetes 1.20 announces that dockershim, the direct integration with Docker Engine, will be removed.
2022 Kubernetes 1.24: Dockershim is removed from the kubelet; a cluster needs a CRI runtime such as containerd or CRI-O. Images built with Docker keep working.
2026 Today: Kubernetes 1.37 is the current minor release and kind 0.33.0 runs it as its default node image. The course pins both.

Where they fit
The official documentation describes what each one is for. These are the cases you will meet in event driven systems and enterprise integration.
- One artifact with its dependencies: The runtime, the application and the files it expects, built once into an image that runs the same on a laptop and on a server.
- The same environment for the whole team: A Compose file with the application, its database and its broker; everyone starts the same versions with one command, and so does the test suite.
- Continuous integration: The image built from a commit is the one that passes the tests, goes to staging and reaches production; what changes between stages is configuration, not the artifact.
- Many services that must stay up: Kubernetes places each instance, restarts or replaces the ones that fail, and rolls out a new version without taking the service down.
- Scaling across nodes: More replicas of a consumer when the lag grows, spread over several machines, with requests and limits that say how much each one may take.
- One way to operate across teams: The same declarations, the same hooks for logs and metrics and the same permission model (RBAC) for every service, whoever wrote it.

Where they do not fit
This part is the course's judgment, not official documentation. Each row says what to use instead.
- One application on one machine: A control plane, a node agent and a network layer to run one process is cost without return; most of what Kubernetes gives you solves problems you do not have yet. Use instead: Docker or Compose on that machine, or a service managed by the operating system.
- A team with nobody to operate it: The official documentation says Kubernetes is not a traditional, all-inclusive PaaS: upgrades, networking, storage, certificates and monitoring are your choices and your work. Use instead: A managed Kubernetes service from your provider, or a platform as a service that takes the image and runs it.
- Desktop and GUI applications: Containers are made for processes that serve over the network; a window, a graphics session or a sound card need the host in ways the model does not cover well. Use instead: A native installer or a package for the operating system.
- Workloads tied to a kernel, hard real time or specific hardware: A container shares the host kernel: it cannot bring its own, cannot guarantee a latency the kernel does not guarantee, and reaches devices only through what the host passes in. Use instead: A virtual machine or a dedicated machine with the kernel and drivers the workload needs.
- Databases and stateful systems without the experience: Kubernetes replaces instances freely; a database needs ordered failover, backups, storage with known performance and someone who has done it before, usually through an operator. Use instead: A managed database, with the application in the cluster pointing at it.
- Small, sporadic jobs: A report at night or a cleanup once a week does not justify a cluster that runs all day waiting for it. Use instead: A function in your provider, or a cron entry on a machine you already have; a CronJob later, if the cluster already exists.

How to decide
1. Will more than a handful of services and instances run?
2. Will they need more than one host?
3. Is there someone to operate the platform, with the time it takes?
4. Do you need automatic replacement of failed instances and updates without downtime?
5. Is there a managed Kubernetes offering you can start from, instead of building the cluster yourself?
Three yes answers and Kubernetes is worth learning for real; Docker you will need either way. Lesson 00 shows how the course works and leaves Docker ready.

01. A process with boundaries
=================================================================
A container starts with a process, not a miniature computer.

The main process
A container runs a command with an isolated view of processes, networking and files. On Linux it shares the host kernel. Docker Desktop runs Linux containers inside its Linux environment.
→ Isolation does not create a separate kernel.

An image becomes a container
The image supplies files and defaults. Docker adds runtime configuration and a writable layer for each container. Two containers from one image can have different names and different files.
→ Same image does not mean shared writable state.

A bounded experiment
Run id and inspect the process list inside the image. Our app uses UID 10001, not root. That reduces privileges but does not make untrusted code harmless or replace host security.
→ Name the boundary you actually observed.

LAB
1. Inspect the runtime user
Run a short command instead of the default server command. --rm removes this temporary container after exit.

docker run --rm prumathe-signal:1.0.0 id

Observe: UID 10001, not root.

2. See isolated processes
Run ps inside a new container. The process list is the container view, not a list of every host application.

docker run --rm prumathe-signal:1.0.0 ps

Observe: A small process list containing ps; host applications are absent.

3. Write to a temporary layer
Create a marker inside this container. The shell and marker disappear when this --rm container exits.

docker run --rm prumathe-signal:1.0.0 sh -c 'echo isolated > /tmp/marker; cat /tmp/marker'

Observe: isolated is printed.

4. Start from the image again
Check the same path in another new container. test asserts absence and prints PASS only when the assertion holds.

docker run --rm prumathe-signal:1.0.0 sh -c 'test ! -f /tmp/marker && echo PASS'

Observe: PASS: the previous container did not edit the image.

CHECKPOINT
1. What is shared by Linux containers on one Linux host?
A. The kernel
B. Every writable file
C. The same process ID namespace by default
Answer: A. Namespaces isolate views; they do not boot another kernel.

2. A second container changes /tmp. What happens to the first?
A. Its /tmp always changes too
B. The image is rebuilt
C. Its own writable layer stays separate
Answer: C. Only an explicitly shared mount changes this boundary.

3. Does non-root eliminate all risk?
A. Yes; the network is disabled
B. No; it limits one set of privileges
C. Yes; the kernel is separate
Answer: B. The application can still access its granted files and network.


02. Start, stop, remove
=================================================================
A stopped container and a deleted container are different states.

Run means create and start
docker run creates a container and starts its command. docker start starts an existing stopped container. A foreground process keeps the container alive; completing the main command stops it.
→ A container is alive while its main process runs.

Stop is a lifecycle event
docker stop requests graceful termination, then forcibly kills the process if its timeout expires. Application signal handling determines whether work finishes cleanly. Our teaching server handles SIGTERM and exits at once; it does not drain in-flight requests.
→ Receiving a signal is not the same as finishing work.

Removal ends this writable layer
Stopping preserves the container writable layer. Removing the container removes that layer; volumes have their own lifecycle. Inspect status before removing the named practice container.
→ Stop preserves; remove discards the container layer.

LAB
1. Create the named process
Use the course-only name dk-life. If repeating after interruption, remove just dk-life with docker rm -f dk-life before this step.

docker run -d --name dk-life prumathe-signal:1.0.0

Observe: A container ID. The server stays in the foreground inside it.

2. Write and stop
Write a marker, then stop the process. Inspect the resulting lifecycle state.

docker exec dk-life sh -c 'echo retained > /tmp/life'
docker stop dk-life
docker inspect --format '{{.State.Status}} {{.State.ExitCode}}' dk-life

Observe: exited 0: the process handled SIGTERM; 137 would mean it had to be killed. The container still exists.

3. Restart the same container
start reuses the container and its layer. Read the marker after restart.

docker start dk-life
docker exec dk-life cat /tmp/life

Observe: retained: stopping did not delete the layer.

4. Remove this instance
Stop and remove only the named practice container. A fresh temporary container cannot see its marker.

docker stop dk-life
docker rm dk-life
docker run --rm prumathe-signal:1.0.0 sh -c 'test ! -f /tmp/life && echo PASS'

Observe: PASS. The image is still available.

CHECKPOINT
1. How do you resume a stopped container?
A. docker run creates the same identity
B. docker build
C. docker start
Answer: C. start reuses the existing container; run creates another.

2. When does the container stop normally?
A. When its image tag changes
B. When its main command exits
C. When all logs have been read
Answer: B. The runtime tracks the main process.

3. What survives stop but not removal without a mount?
A. Files in the writable layer
B. The running process
C. An open TCP connection
Answer: A. Stopped containers keep their files until removed.


03. Images and layers
=================================================================
Read-only building blocks, one writable layer per container.

An image is a recipe result
An image contains filesystem layers and configuration, such as its default command and user. It is not a running process. A tag is a human-readable reference to an image, not an immutable guarantee.
→ Files plus metadata, before execution.

Changes belong to the container
Writing a file while running does not edit the underlying image. Another new container starts from the image again. Deleting a file in a later image layer can hide it without removing its bytes from earlier layers.
→ Never bake secrets into a layer.

Inspect what you ship
docker image history shows build history; image inspect shows configuration and identifiers. The local image ID describes image configuration, while a registry digest identifies a registry object. Do not assume they are the same hash.
→ Inspect content and identity separately from names.

LAB
1. Read image defaults
Inspect the configured user and command without starting a process.

docker image inspect --format '{{.Config.User}} {{json .Config.Cmd}}' prumathe-signal:1.0.0

Observe: 10001:10001 and the Python server command.

2. Inspect build history
Read the image steps. Metadata-only instructions need not add filesystem bytes.

docker image history prumathe-signal:1.0.0

Observe: Build instructions, sizes and metadata entries.

3. Change one runtime layer
Write a temporary file and prove it exists in that container.

docker run --rm prumathe-signal:1.0.0 sh -c 'echo runtime > /tmp/image-test; test -f /tmp/image-test && echo PASS'

Observe: PASS.

4. Check the original artifact
A new container starts without that runtime file.

docker run --rm prumathe-signal:1.0.0 sh -c 'test ! -f /tmp/image-test && echo PASS'

Observe: PASS: no image mutation occurred.

CHECKPOINT
1. Does writing inside a container update its image?
A. No, it changes its writable layer
B. Yes, for all new containers
C. Only when using exec
Answer: A. The image remains the starting point.

2. A secret is copied then deleted in a later layer. Safe?
A. Yes; history encrypts files
B. No; earlier layer bytes may retain it
C. Yes; delete rewrites all layers
Answer: B. Use build secret mounts when a build needs credentials.

3. Can a tag point to another image later?
A. No, tags are cryptographic hashes
B. Only if all containers stop
C. Yes
Answer: C. Use a digest to identify immutable registry content.


04. Build an image
=================================================================
Turn source files into an explicit, repeatable package.

The build context
docker build sends a selected directory as context. COPY can read files from that context; .dockerignore excludes unnecessary or sensitive files. Our Dockerfile copies only server.py and probe.py and installs no Python packages.
→ Control what enters the build.

Cache follows inputs
An unchanged instruction with unchanged inputs can reuse cached results. Changing copied source invalidates that step and following dependent steps. Keep stable setup before frequently changing source.
→ Order layers by their rate of change.

Defaults are part of the artifact
USER selects the runtime user. CMD supplies the default command; exec form avoids an extra shell. EXPOSE documents a port but does not publish it. We pin the base image digest and set APP_VERSION as a non-secret build argument.
→ Build configuration is not runtime configuration.

LAB
1. Build from explicit context
The final argument app selects the context directory. Inspect app/Dockerfile and app/.dockerignore before running.

docker build -t prumathe-signal:1.0.0 app

Observe: A successful image build.

2. Repeat unchanged inputs
Run the same build. Look for cached steps; timing alone does not prove cache reuse.

docker build --progress=plain -t prumathe-signal:1.0.0 app

Observe: Eligible unchanged steps report CACHED.

3. Change a non-secret build argument
Build a second artifact with a different version value. The original 1.0.0 tag stays available.

docker build --build-arg APP_VERSION=1.1.0 -t prumathe-signal:1.1.0 app

Observe: A second image tagged 1.1.0.

4. Inspect the result
Read the environment in each artifact. These are defaults before runtime overrides.

docker run --rm prumathe-signal:1.0.0 printenv APP_VERSION
docker run --rm prumathe-signal:1.1.0 printenv APP_VERSION

Observe: 1.0.0 then 1.1.0.

CHECKPOINT
1. What can COPY read here?
A. Any file on any host
B. Only files in running containers
C. Files in the build context that are not excluded
Answer: C. The context defines the input boundary.

2. What does EXPOSE 8080 do?
A. Documents the intended port
B. Publishes 8080 on the host
C. Creates a Kubernetes Service
Answer: A. Publishing requires explicit runtime configuration.

3. Why copy source after stable setup?
A. To run without an image
B. To reuse the earlier cached steps
C. To encrypt source code
Answer: B. A source edit need not rerun stable setup.


05. Data that outlives a container
=================================================================
Separate the lifetime of a process from the lifetime of its data.

Three places to write
The writable layer belongs to one container. A named volume is managed by Docker and can be mounted again. A bind mount exposes a specified host path; host layout and permissions now matter.
→ Choose storage by its owner and lifetime.

Replace the process
Compose mounts signal-data at /data. Write a marker, replace the app container, then read it. The same volume is attached to the replacement. Mounting storage does not automatically coordinate concurrent writers.
→ Persistence is independent of process identity.

Retention is not backup
docker compose down preserves named volumes by default; down -v removes project volumes. Neither a volume nor a bind mount is a backup. The lab never asks you to prune unrelated Docker resources.
→ Know the deletion boundary before cleaning up.

LAB
1. Start the practice service
From labs, after lesson 00. This starts only the course Compose project.

docker compose up -d --wait app

Observe: The app is healthy. No other project is reset.

2. Write to the mounted volume
The app runs as UID 10001 and owns /data. Store a marker there.

docker compose exec -T app sh -c 'echo volume-survived > /data/marker'

Observe: The write succeeds without root.

3. Replace the app container
Recreate only app while retaining the named volume.

docker compose up -d --wait --force-recreate app

Observe: A replacement app becomes healthy.

4. Read retained data
Check the marker and the mount type. Do not use down -v unless you intend to delete practice data.

docker compose exec -T app cat /data/marker
docker inspect --format '{{json .Mounts}}' prumathe-dk-app-1

Observe: volume-survived and a volume mounted at /data.

CHECKPOINT
1. What survives replacing this app container?
A. Its process ID
B. The named volume
C. All writable layer files
Answer: B. The replacement mounts the same volume.

2. What makes a bind mount host-dependent?
A. Its image tag
B. Its HTTP status
C. Its source path and permissions
Answer: C. The host supplies the mounted files.

3. Does persistence prove recoverability after disk loss?
A. No; you need a tested backup strategy
B. Yes, Docker replicates every volume
C. Yes, down always takes a backup
Answer: A. This experiment only replaces the container, not the storage device.


06. Names on a network
=================================================================
Find a service without memorizing its container address.

A network has a scope
Compose creates a network for its project. Containers on it can find services by service name. app resolves inside that network; it is not automatically a hostname on your laptop.
→ DNS names belong to a network scope.

Localhost means here
Inside the toolbox container, localhost points back to the toolbox. Use app:8080 to reach the app container. Replacing the app can change its address while the service name remains usable.
→ A remote service is not your loopback address.

Connectivity is not authorization
A shared Docker network permits communication; it does not authenticate application requests. The lab checks DNS and HTTP separately so a name-resolution failure is not confused with an application error.
→ Diagnose name, connection, then response.

LAB
1. Start the practice service
From labs, after lesson 00. This starts only the course Compose project.

docker compose up -d --wait app

Observe: The app is healthy. No other project is reset.

2. Resolve the service name
Use a one-off peer on the Compose network. Overriding entrypoint lets us inspect DNS with the same image. From the host, the name app does not resolve: the name exists only inside the Compose network.

docker compose run --rm --no-deps --entrypoint python toolbox -c "import socket; print(socket.gethostbyname('app'))"

Observe: An internal IP address, which you do not hardcode.

3. Request the internal endpoint
The toolbox default URL is http://app:8080. The host port is not involved.

docker compose run --rm --no-deps toolbox

Observe: hello-compose and PASS.

4. Inspect network membership
Read only this course network. Container addresses are runtime details, not durable configuration.

docker network inspect prumathe-dk_default

Observe: The app is attached to the project network.

1. Where does localhost point inside toolbox?
A. To toolbox itself
B. To the Docker host automatically
C. To the app service

2. Which address should a peer use here?
A. A hardcoded container IP
B. localhost:18080
C. app:8080
Answer: C. The service name resolves on the Compose network.

3. Does shared network access authenticate a request?
A. Yes, by container ID

07. Publish a port deliberately
=================================================================
Distinguish listening, exposing and publishing.

The application listens
Signal listens on 0.0.0.0:8080 inside the container. Listening only on 127.0.0.1 inside it would prevent peers from reaching that socket. The process must actually listen even if the image declares EXPOSE.
→ A declared port is not an open socket.

The host forwards traffic
Compose publishes 127.0.0.1:18080 to container port 8080. Your browser uses the host port; peers use the internal port. Binding to loopback limits this published endpoint to the local host.
→ Host port and container port are different coordinates.

Follow the failed hop
Check the port mapping, then request the published URL and the internal URL. A port already in use prevents a new bind. Do not solve a collision by exposing every interface without understanding the scope.
→ Trace the route before changing the binding.

LAB
1. Start the practice service
From labs, after lesson 00. This starts only the course Compose project.

docker compose up -d --wait app

Observe: The app is healthy. No other project is reset.

2. Read the published address
Ask Compose which host address maps to the internal port.

docker compose port app 8080

Observe: 127.0.0.1:18080.

3. Trace the internal side
This request originates inside the app container. Open http://127.0.0.1:18080 separately in your host browser to compare the host side.

docker compose exec -T app python /app/probe.py http://127.0.0.1:8080 hello-compose

Observe: The same application payload and PASS. The host URL returns that service too.

4. Inspect the explicit binding
Check HostIp and HostPort rather than assuming the image EXPOSE published anything.

docker inspect --format '{{json .HostConfig.PortBindings}}' prumathe-dk-app-1

Observe: 8080/tcp maps to 127.0.0.1 and 18080.

CHECKPOINT
1. Which port does the host browser use?
A. 8080 always
B. The container process ID
C. 18080
Answer: C. The mapping forwards host 18080 to container 8080.

2. Can EXPOSE start a listener?
A. No
B. Yes
C. Only on Linux
Answer: A. The process opens the socket.

3. What does 127.0.0.1 in this mapping limit?
A. The container image size
B. The host interfaces used by the published endpoint
C. The app CPU
Answer: B. It binds the host side to loopback.


08. Describe the local system
=================================================================
Services, networks and volumes in one readable file.

From commands to a model
Compose names services and their runtime configuration. Our app and optional toolbox share a network; only app publishes a port. The project name prumathe-dk scopes the resources created by this kit.
→ Read the configuration before starting it.

Running versus healthy
up -d --wait waits for running or healthy service state. The image health check probes /health. This check does not test every business operation, and ordinary start order is not the same as dependency readiness.
→ Define what healthy actually measures.

A local lifecycle
config renders the resolved configuration; ps shows state; logs shows output; down removes project containers and networks. Compose on this host does not provide a distributed Kubernetes control plane.
→ Use a tool within its operating boundary.

09. Configuration and secrets
=================================================================
Keep the artifact stable while runtime settings change.

Runtime inputs
MESSAGE is an environment variable read when the process starts. Two containers from one image can print different messages. The image does not need rebuilding for this runtime setting.
→ Separate the release from its environment.

Secrets are not build arguments
Build arguments and ordinary environment variables are poor hiding places for credentials. The Compose fixture mounts a deliberately fake token at /run/secrets/demo_token. Local Compose secrets are file mounts, not an automatic encrypted vault.
→ A secret delivery mechanism still needs protection.

Change and restart deliberately
Editing an environment source does not rewrite an already running process environment. Recreate the container with the new configuration. Do not print real credentials while inspecting a system.
→ Know when the application reads each setting.

LAB
1. Start the practice service
From labs, after lesson 00. This starts only the course Compose project.

docker compose up -d --wait app

Observe: The app is healthy. No other project is reset.

2. Override a runtime value

Observe: runtime-value.

Assert the file exists without printing its contents. The fixture is deliberately not a real credential.

docker compose exec -T app sh -c 'test -s /run/secrets/demo_token && echo PASS'

Observe: PASS: a readable nonempty file was delivered.

10. Health and resource limits
=================================================================
A status signal and a resource budget solve different problems.

Probe one property
Our Docker health check sends an HTTP request to /health. The /tmp/fail-live file makes that endpoint return 503 for an intentional exercise. An unhealthy container can still have a running main process.
→ Unhealthy is not synonymous with stopped.

Bound consumption
Compose sets 0.5 CPU and 128 MiB memory for the app. CPU limits constrain execution time; memory exhaustion can kill processes. A limit does not make the application efficient or prove adequate capacity.
→ A limit is a boundary, not a performance target.

Observe recovery
Remove the failure file and wait for the health check to recover. Docker health status alone does not restart an unhealthy container. Restart policies concern process exit and require separate configuration.
→ A detector and a recovery mechanism are separate.

11. Tags, digests and delivery
=================================================================
Move an artifact without confusing its name with its identity.

Tags are references
docker tag gives an existing image another name. It does not copy or modify its layers. A registry stores image content for pull and push; this course uses local images and does not publish to a remote account.
→ A new tag is not a new build.

Pin content for reproduction
A digest addresses registry content. Our base image and kind node image include digests. A tag such as 1.0.0 communicates intent, but reproducibility requires preserving the actual artifact and its inputs.
→ Names are convenient; content identity is stronger.

Local is not on every node
An image in Docker on your laptop is not automatically in a Kubernetes node runtime. kind load docker-image copies the local artifact into the named cluster. We use imagePullPolicy: Never to make missing imports visible.
→ Delivery is an explicit step.

14. The Pod boundary
=================================================================
Kubernetes schedules Pods, which contain containers.

One scheduling unit
A Pod groups one or more containers that share a network namespace and can share declared volumes. They run together on one node. Our first Pod has one container, so the process-to-Pod relationship stays visible.
→ A Pod is the smallest deployable unit here.

Identity is temporary
A Pod gets a name, UID and network address. Replacing a Pod creates a new identity, even if you reuse its name. Do not use a Pod IP as a durable client address.
→ Replacement is not resurrection.

Bare Pods have no replacement controller
The kubelet can restart a container according to its restart policy. Deleting this standalone Pod removes the object; no Deployment exists to recreate it. Later we introduce the controller that maintains replicas.
→ Container restart and Pod replacement are different.

15. Desired and observed state
=================================================================
Describe an outcome; watch the control loop approach it.

Declare the object
A manifest describes API objects with a kind, metadata and specification. apply submits that desired state. Successful acceptance means the API stored the request, not that all Pods are ready.
→ Accepted and achieved are different milestones.

Reconciliation repeats
Controllers compare desired and observed state and take actions to reduce the difference. Scheduling, image availability and health can delay convergence. The loop keeps working after kubectl exits.
→ The controller is a loop, not a one-time script.

Keep the source consistent
An imperative scale changes live desired state. Applying a manifest that still declares two replicas can restore two. For durable changes, update the owned manifest and review the difference before applying.

18. Inject runtime configuration
=================================================================
Use API objects to deliver settings, with clear update semantics.

Separate ordinary values
A ConfigMap stores non-confidential configuration. set env --from adds references to its keys in the Deployment template. The new Pods read MESSAGE when they start; changing the ConfigMap alone does not change an existing process environment.

Secrets have a different access boundary
A Secret stores sensitive values with specific API access controls, but base64 is encoding, not encryption. Kubernetes Secrets are not encrypted in etcd by default. The example uses only a clearly fake token.

Delivery mode changes update behavior
ConfigMap and Secret volumes can receive eventual updates, with exceptions such as subPath mounts. Applications still need to reread files. This lab uses environment import explicitly, so you observe a rollout instead of assuming live reload.

19. Storage beyond a Pod
=================================================================
A claim asks for storage; it does not promise a backup.

Claim and volume
A PersistentVolumeClaim requests storage with size and access requirements. A PersistentVolume represents supplied storage. A StorageClass can enable dynamic provisioning; kind includes a local provisioner for this exercise.
→ The request and the storage are different objects.

Reattach after replacement
The writer Pod mounts the notebook claim at /data. Write a marker, delete only the Pod, then recreate it with the same claim. ReadWriteOnce means read-write mounting by a single node, not necessarily a single Pod.
→ Deleting the Pod does not itself delete its claim.

Local storage has local limits
This provisioned volume lives in the local kind environment. Deleting the cluster loses it. PVC deletion and the volume reclaim policy affect storage deletion; inspect them before cleanup. This is not a replicated database or backup exercise.
→ Persistence must name its failure boundary.

20. Alive, ready, started
=================================================================
Choose the right question before choosing a probe.

Readiness gates traffic
A failing readiness probe marks the Pod not ready. Normal Service routing excludes unready endpoints; the container can keep running. Use readiness for whether the instance can serve traffic now.
→ Not ready means stop sending normal service traffic.

Liveness triggers restart
Repeated liveness failures cause the kubelet to restart the container according to restart policy. A dependency outage is often a poor liveness test: restarting every instance may make recovery worse.
→ Restart only when restarting can help.

Startup grants initialization time
A startup probe holds readiness and liveness probing until it succeeds. Its failure threshold and period define an initialization budget. In this lab, fail readiness, observe routing state, then restore it without restarting the process.
→ Use separate signals for separate recovery decisions.

21. Requests, limits and placement
=================================================================
The scheduler needs a declared resource budget.

Requests reserve scheduling capacity
The scheduler uses requests when deciding where a Pod fits, along with constraints such as taints and node selection. CPU 50m means 0.05 CPU; memory 32Mi is 32 mebibytes. Live low usage does not erase declared requests.
→ Placement uses declared needs, not wishful thinking.

Limits constrain execution
A CPU limit can throttle execution; exceeding a memory limit can lead to OOM termination. Requests and limits do different work. Limits alone do not guarantee latency or protection from every node failure.
→ Scheduling budget and runtime ceiling differ.

Pending is evidence
The no-room Pod requests 1000 CPUs, deliberately more than this learning cluster provides. describe shows FailedScheduling and its reason. Diagnose the unsatisfied constraint before changing requests or adding nodes.
→ Pending is a state to explain, not a reason to restart blindly.

22. Change versions with a way back
=================================================================
A rollout is a transition you must observe.

A new template revision
Changing the Deployment image updates its Pod template and creates a new ReplicaSet. A rolling update gradually replaces instances, governed by maxSurge and maxUnavailable. Our manifest allows one extra and zero unavailable replicas.
→ Strategy controls the transition, not application compatibility.

Watch for convergence
Build version 1.1.0, load it into kind, then set the image. rollout status waits for completion or a timeout. With imagePullPolicy: Never, forgetting the import leaves new Pods unable to start.
→ An update request is not a successful release.

Rollback has a boundary
rollout undo restores a previous Pod template revision. It does not undo database migrations, restore external data or revert an independent ConfigMap. Verify both the deployed version and application behavior after reverting.
→ Rollback restores a template, not the whole world.

23. Grant only the needed verbs
=================================================================
Identity, permissions and binding are separate objects.

Identify the caller
A ServiceAccount gives workloads an identity for Kubernetes API access. Our observer is a practice identity. Most course Pods do not need API access, so their automatic service account token mount is disabled.
→ Do not mount API credentials without a need.

Bind verbs to resources
A Role grants get, list and watch on Pods inside dk-lab. A RoleBinding attaches that Role to observer. It does not grant secret access or Pod deletion. RBAC permissions are additive; there is no deny rule here.
→ Scope the subject, verbs, resources and namespace.

Check authorization
auth can-i asks whether an action is authorized. The lab administrator impersonates observer to check one allowed and two denied actions; impersonation itself requires permission. Authorization says nothing about network reachability or application login.
→ An authorization check tests one action for one identity.

2. Check the permitted action

Observe: yes.

3. Check a denied destructive action
This only asks for authorization; it does not delete a Pod. A no response and nonzero exit are expected.

Deploy two replicas of Signal 1.0.0. Require ready Pods, a Service with ready endpoints and an HTTP response containing the expected version. These checks measure different layers of success.
