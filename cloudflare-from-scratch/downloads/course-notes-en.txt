WHAT CLOUDFLARE IS
=================================================================
What it is, where it came from, where it fits and where it does not. Read it once; the lessons and the big picture do the rest.

A network in front of your application, and a place to run code in it
Cloudflare runs a global network of data centers, 348 cities on its network map when this course was checked. For a domain you add to it, its DNS answers with addresses of that network, so requests from your users reach a nearby data center first. There the edge ends TLS, applies your rules, serves what it has cached and forwards the rest to your server, the origin. Your origin keeps doing its work; the edge decides what reaches it.
The same network runs your code. A Worker is JavaScript or TypeScript, or Python, Rust and other languages through WebAssembly, that runs in a V8 isolate in each data center, with bindings to storage of its own: KV, D1, R2, Durable Objects, Queues, Workflows, and Hyperdrive to reach your own database. Java does not run in Workers, so in this course Java stays where it belongs: in the origin.
→ The edge decides what reaches your origin; Workers decide what the edge does.

From a spam trap to a platform
Cloudflare grew out of Project Honey Pot, started in 2004 by Matthew Prince and Lee Holloway to find out where email spam came from. With Michelle Zatlyn they founded Cloudflare in 2009 and launched it in public in 2010. The first product protected and sped up websites by standing in front of them; running code in that same position came seven years later.
2009 Founded: Matthew Prince, Michelle Zatlyn and Lee Holloway, after Project Honey Pot.
2010 Public launch: 27 September, at TechCrunch Disrupt in San Francisco.
2017 Workers: 29 September: JavaScript at the edge, on V8, with an API like Service Workers.
2019 Listed: 13 September, on the New York Stock Exchange as NET.
2020 Durable Objects: 28 September: state with a single owner, at the edge.
2026 cf: 28 September: a command line for the whole API, in open beta; Wrangler will follow it.

Where it fits
Cases where putting Cloudflare in front, or running code on it, pays off.
- A public site or API: TLS, cache of what is the same for everyone, rules and rate limits before your servers, with the origin address out of DNS.
- An origin with no open ports: A tunnel publishes a service from a private network, and Access asks for identity in front of internal tools.
- Logic close to the user: Redirects, headers, A/B tests, authentication checks and small APIs that answer from the data center that received the request.
- Webhooks and bursts: Accept at once, queue, and process at your own pace with retries and a dead letter queue.
- State per thing: Counters, sessions, rooms and live status, one Durable Object per entity.
- Files to many readers: Objects in R2 served from the edge, with no egress fees.

Where it does not
The course judgment, from the limits in the documentation: cases where something else does the job better.
- Heavy or long computation: A request gets 10 ms of CPU on the free plan and 5 minutes at most on the paid one. Instead: Your servers or containers, fed by a queue.
- Your Java and Spring code: Java does not run in Workers. Instead: The origin, with the edge in front.
- A large relational database: D1 is SQLite per database, with a single primary for writes. Instead: Your PostgreSQL or MySQL, reached through Hyperdrive.
- Counters and coordination in KV: KV is eventually consistent and has no atomic operations. Instead: A Durable Object per counter.
- Anything personal in a shared cache: The default cache key has no user in it. Instead: private or no-store, and cache only what is the same for everyone.

Five questions before you put it in front
1. Which requests must never reach my origin, and which must always?
2. What is the same for everyone, and can be cached, and what is personal?
3. Can someone reach my origin without going through the edge?
4. What does each piece of state need: speed of reading, one owner, SQL or files?
5. What fits the free plan, and what would I pay for?
The course answers each one with a command you can run, on your machine.

01. A request goes through the edge
=================================================================
One address announced from many places, and the data center that answers you.

One address, many places
Anycast: Cloudflare announces the same IP addresses from all its data centers, and internet routing takes each client to one of them, usually a nearby one. What it is: a way of routing, not a server. What it is for: to answer from close by and to spread load and attacks over the whole network. What it does not do: promise the geographically closest city; the routes of the networks in between decide.
→ The address is the same everywhere; the data center that answers is not.

The edge answers first
Your TLS connection ends at that data center, which runs every product of the zone on the request before it goes anywhere else. Each request gets a Ray ID, sent to the origin in the cf-ray header; Cloudflare says Ray IDs are not guaranteed to be unique. /cdn-cgi/trace on a site behind Cloudflare shows which data center answered, in its colo field.
→ Log the Ray ID: it is how you find one request in Cloudflare.

Your edge in the kit
wrangler dev runs workerd, the open source runtime of Workers, on your machine. It is one place, not a network: no anycast and no other data centers. request.cf, the object where the edge describes the client, is fetched once from Cloudflare when wrangler starts and describes your own connection; on Cloudflare each request carries its own.
→ The kit runs the same code; it does not reproduce the network.

02. DNS with or without the proxy
=================================================================
The same record can send the request to the edge or straight to your server.

Proxied: the edge answers
Cloudflare DNS hosts the records of your zone. A record marked proxied is answered with Cloudflare anycast addresses, so HTTP and HTTPS requests reach the edge first and the address of your origin is not published. Only A, AAAA and CNAME records can be proxied; the dashboard turns the proxy on by default for them. Proxied records have a fixed TTL of 300 seconds.
→ Proxied means the request meets the edge before your server.

DNS only: Cloudflare only answers DNS
A DNS-only record is answered with the real address you wrote. Requests go straight to that server: no cache, no WAF, no Workers on the way, and only DNS analytics. The address is visible to anyone who asks for the record. MX and TXT records are always DNS only.
→ A DNS-only record skips every product of the zone.

What the proxy does not hide
The proxy hides the origin address in DNS, not everywhere. An old DNS-only record, a mail server on the same machine or a direct link can reveal it, and whoever knows it can skip the edge. Two defenses come later: an origin with no open port, lesson 04, and an origin that checks who sent the request, lesson 15.
→ Hiding an address is not the same as closing a door.

03. TLS in two legs
=================================================================
The visitor connects to the edge, and the edge connects to your origin: two connections, one setting.

Two connections
The first leg goes from the visitor to the edge, with a certificate Cloudflare manages for your zone. The second goes from the edge to your origin, and the SSL/TLS encryption mode of the zone decides how: Off, Flexible, Full, Full (strict) or Strict. It applies to the whole zone; a configuration rule can change it for one hostname. The default is Automatic SSL/TLS, which picks the most secure mode it can and never lowers yours.
→ A padlock in the browser only speaks for the first leg.

What each mode checks
Flexible encrypts the first leg and sends the second in plain HTTP. Full uses HTTPS to the origin without validating its certificate, so a self-signed one is accepted, and so is any server that answers with one. Full (strict) validates it against a public certificate authority or Cloudflare Origin CA. Strict always connects to the origin over HTTPS with validation, whatever the visitor used. Cloudflare strongly recommends Full or Full (strict).
→ Encrypting is not authenticating: Full encrypts, Full (strict) also checks who answers.

The second leg, in the kit
lab tls plays the edge on the second leg. The origin has a certificate signed by a test CA of the kit, generated when its image is built; an impostor service has a self-signed one for the same name. The kit CA stands for the authorities Full (strict) trusts. It is test material: it is not trusted anywhere else.
→ Test which server answers, not only whether the line is encrypted.

04. An origin with no open ports
=================================================================
The origin dials out to Cloudflare, and requests come back through that connection.

Nothing listens on the internet
Cloudflare Tunnel: cloudflared, a small program next to your service, opens outbound connections to Cloudflare, and the edge sends the requests for your hostname through them. Each tunnel keeps four long-lived connections to two data centers. What it is for: publishing a service with no open inbound port and no public IP. It is available on all plans.
→ Outbound only: the firewall of the origin can stay closed.

Quick tunnel and named tunnel
A quick tunnel needs no account: cloudflared gets a random name under trycloudflare.com, for testing, with limits such as 200 requests in flight and no server-sent events. A named tunnel belongs to your account, survives restarts and maps hostnames of your zone to local services; with Access in front, lesson 15, only identified people reach them.
→ Quick tunnels are for trying; named tunnels are for running.

The door you forgot
A tunnel adds a way in; it does not close the others. If the origin still listens on a public address, anyone who finds it skips the edge, with its cache, WAF and Access. With a tunnel, the origin can listen only on its private network, as it does in the kit.
→ The tunnel protects only if it is the only way in.

05. An isolate, not a container
=================================================================
Your code runs in a V8 isolate inside a process that runs many others, and global state is a guess.

Isolates instead of machines
A Worker does not get a virtual machine or a container: it gets a V8 isolate inside a runtime process that already exists, and one instance of the runtime runs hundreds or thousands of isolates. An isolate starts around a hundred times faster than a Node process in a container and uses an order of magnitude less memory, which removes the cold start of the virtual machine model.
→ Many isolates per process: cheap to start, nothing to keep.

Global state is not yours to keep
Isolates are not necessarily long lived: they can be evicted for resource limits and other reasons, and two requests of the same user may reach different instances, in the same data center or in another. A variable at module level survives between some requests and not others. Cloudflare recommends not using or mutating global state; state goes to a binding, unit 5.
→ A counter in a global variable counts one isolate, for a while.

CPU, memory and the free plan
The limit that matters is CPU time, not wall time: waiting for fetch or a binding does not count. The free plan gives 10 ms of CPU per request and 100,000 requests per day; the paid plan, 30 seconds by default and up to 5 minutes. Each isolate has 128 MB of memory, and a request can make 50 subrequests on the free plan. The runtime also refuses random values, timers and I/O at global scope: they belong in a handler.
→ Budget CPU, not seconds.

06. Wrangler and the configuration
=================================================================
One file says what the Worker is and what it can reach; secrets stay out of it.

wrangler.jsonc
Wrangler is the command line for Workers: dev, deploy, tail, migrations, secrets. Its configuration file names the Worker, its entry point and its compatibility date, which pins the behavior of the runtime to that day; flags such as nodejs_compat turn on more APIs. Each binding is a name in env pointing to a resource: a KV namespace, a D1 database, a queue. Locally the ids only name local stores; on the account they name real resources.
→ A binding is a capability: if it is not in the file, the Worker cannot reach it.

Vars and secrets
vars in the configuration are plain values, committed with the code; the documentation says not to put sensitive information there. Secrets go to the account with wrangler secret put and, for local development, in a .dev.vars file or a .env file next to the configuration, never both and never committed. wrangler dev reads .dev.vars when it starts. wrangler types generates the TypeScript type of env from the file.
→ If it is in the repository, it is not a secret.

Wrangler 4 and cf
The course pins Wrangler 4.162.0. Since 28 September 2026, cf, a new command line for the whole Cloudflare API, is in open beta; when the beta ends, Wrangler gets a last major version that points to cf, with 18 months of maintenance. The concepts of the course are the same in both: configuration, bindings, versions.
→ Pin the tool; learn the model behind it.

07. A Worker in front of your API
=================================================================
The Worker sees each request first: it answers, rewrites, refuses or forwards.

A handler for every request
The fetch handler receives a Request, the env with the bindings and a context, and returns a Response. In between it can answer by itself, call the origin with fetch and change what comes back. In Rumbo, the gateway adds x-rumbo-request-id and x-rumbo-edge on the way in, and x-rumbo-via on the way out.
→ The Worker owns the request until it returns a Response.

Decide before the origin
Some answers never need the origin. A CORS preflight is answered at the edge, only for the shop that is allowed. A route of the admin API is refused with 403: the origin gets no load from it and never sees it. Each decision taken at the edge is one the origin does not have to take, and one it cannot get wrong.
→ Refuse as early as you can.

After the answer
ctx.waitUntil keeps work going after the response is sent, for up to 30 seconds: the gateway records the last request in KV without making the client wait. Service bindings let one Worker call another without going through the public internet; the course does not use them.
→ What the client does not need, do after answering.

09. Deploy and observe

Versions and deployments
A version is the code and configuration of a Worker, uploaded and kept. A deployment says which versions serve requests, and in what share. wrangler deploy does both at once: it uploads a version and deploys it to 100%. 10. What the edge keeps
=================================================================
Two caches you can put in front: the one of the zone and the one of the Worker.

The cache of a zone
For a proxied zone, Cloudflare caches by file extension, not by MIME type: CSS, JS, images, PDF and a long list more. HTML and JSON are not cached by default. It does not cache when Cache-Control says private, no-store, no-cache or max-age=0, when the response has Set-Cookie, or when the method is not GET. A cache rule can make more content eligible. When a Worker runs on a route, its fetch to the origin goes through this cache.
→ By default the edge keeps files, not pages.

A cache in front of the Worker
Workers Cache puts a cache in front of the Worker itself: "cache": {"enabled": true} in wrangler.jsonc, on workers.dev too. It follows the Cache-Control of the responses of the Worker, and a hit does not run the Worker, so it uses no CPU. It has no price of its own, but every request still counts as a Worker request, hit or not. A 200 with no Cache-Control is kept for 7,200 seconds by heuristic; private, no-store and Set-Cookie bypass it; the version of the Worker is part of the key, so each deployment starts empty.
→ A response with no Cache-Control is a decision too.

Reading cf-cache-status
The header says what the cache did: MISS, not there, now stored; HIT, served from it; EXPIRED, REVALIDATED, UPDATING and STALE, the lifecycle of a stored copy; BYPASS, the response said not to keep it; DYNAMIC, in a zone, not eligible at all. The kit cannot show this part: wrangler dev does not run Workers Cache, so these steps use your account.
→ Read cf-cache-status twice: the second request tells the truth.

11. The cache key and its traps
=================================================================
Two people ask the same URL: the cache cannot tell them apart unless you do.

What the key is made of
The default cache key of a zone is the scheme, the host and the path with its query string, plus a few headers such as Origin. It is not the user: two people asking the same URL get the same stored entry. Cache rules can change the key; options such as headers, cookies or the user in the key are Enterprise only, while ignoring or sorting the query string is on every plan.
→ The cache answers the URL, not the person.

The trap
A response built for one user and marked public is stored under a key that does not include that user. The next person who asks the same URL gets it: their address, their orders, their name. The fix is in the response, not in the cache: private or no-store for anything personal, and public only for what is the same for everyone.
→ Never mark personal data public.

Purge
Purging removes stored copies. Every plan, the free one included, can purge by URL, by hostname, by tag, by prefix and everything; the free plan allows 800 URLs per second, and 5 requests per minute for the other kinds. Purging fixes the past; only a correct Cache-Control fixes the future.
→ Purge, then fix the header, or it comes back.

12. Cache from a Worker
=================================================================
The Cache API stores and purges from code, one data center at a time.

match, put, delete
caches.default is the Cache API: match looks for a stored Response for a Request, put stores one and delete removes it. put refuses a response whose Cache-Control says not to keep it. In Rumbo, /lab/cache/rate keeps the rate of a zone for 60 seconds with the zone in the key.
→ The key is the Request you choose.

One data center at a time
The contents of the Cache API do not replicate outside the data center where they were stored, and cache.delete purges only that data center. It is independent of Workers Cache, which runs in front of the Worker, and of the cache that the fetch of a Worker goes through. It works on custom domains; dashboard previews do nothing with it, and it is not available for Workers behind Access.
→ A delete from code is a local purge.

When to use it
Use it for results you compute at the edge and can rebuild, such as a rate, a rendered fragment or an answer of a slow API, when you need a key of your own. For a purge that must reach every data center, use the purge of the zone or Workers Cache purge by tag. Locally there is one data center, so local and global look the same.
→ Cache what you can rebuild.

13. WAF: rules on the request
=================================================================
Rules that look at each request and stop it before your code, in a fixed order.

Managed and custom rules
The WAF of a zone runs rules on each request. Managed rules are written by Cloudflare against known attacks; the free plan gets the Free Managed Ruleset. Custom rules are yours, with an expression of the Rules language, such as starts_with(http.request.uri.path, "/api/admin"), and an action such as Block, Managed Challenge or Skip: 5 on the free plan, with every action except Log.
→ A rule is an expression and an action.

In a fixed order
The security phases run in sequence: DDoS protection, custom rules, rate limiting rules, managed rules, Super Bot Fight Mode. A terminating action, such as Block, ends the request: later phases and your Worker never see it. Before the rules, URL normalization can make /%68ello and /hello the same path; letter case is not part of what the documentation says it changes.
→ A rule compares text: normalize what it compares, lower() included.

The rule in code, and its event
The kit has no zone, so the gateway plays the custom rule: a path that starts with /api/admin gets 403 before the origin. A WAF block is also recorded as a security event with its Ray ID; events are sampled, so a missing one does not prove nothing happened. A rule in the zone runs before any Worker; a rule in code runs only where your Worker runs.
→ Block in the zone what no code should ever see.

14. Rate limiting
=================================================================
Count requests by something stable, in a window, and answer 429 past the limit.

Count by what, in which window
A rate limit counts requests that share a characteristic, in a window, and acts past a threshold. The binding of Workers counts by the key your code gives, any string: an API key, a user, a tenant, a path. The documentation advises against the IP address, because many users can share one. The window is 10 or 60 seconds.
→ Count what identifies a client, not where it connects from.

Approximate, per location
The binding counts separately in each Cloudflare location and the counts are eventually consistent, so requests can go over the limit before the counters agree. A call that returns success: false does not add to the count. For a strict limit across all locations, the documentation points to Durable Objects, lesson 19.
→ A rate limit protects capacity; it is not an exact quota.

In the zone or in the Worker
Rate limiting rules of the WAF run in their own phase, before managed rules and before any Worker; the free plan includes one such rule. The binding runs inside your Worker, where it knows things a rule cannot, such as the tenant behind an API key. In Rumbo, the gateway allows 5 requests per 10 seconds per x-api-key and answers 429 with retry-after: 10. Locally the windows are fixed, aligned every 10 seconds.
→ Limit in the zone what is anonymous; in code, what has a name.

15. Access: identity before the origin
=================================================================
The edge asks who you are; the origin still checks the proof it receives.

Identity at the edge
Cloudflare Access puts a login in front of an application: a hostname of your zone, or a Worker with its workers.dev name and previews. A person signs in with an identity provider, a policy decides, and the edge adds a signed JWT to the requests that pass, in the Cf-Access-Jwt-Assertion header and the CF_Authorization cookie. Cloudflare Zero Trust, which includes Access, is free for up to 50 users.
→ Access decides at the edge; it does not close your origin.

The origin validates
An origin that trusts the header without checking it lets in anyone who sends one. It validates the signature with the public keys of the team at https://<team>.cloudflareaccess.com/cdn-cgi/access/certs, the aud claim against the AUD tag of the application, the iss against the team domain, and the expiry. The keys rotate about every six weeks, so they are fetched, not copied. For a Worker behind Access, ctx.access gives the identity directly.
→ Check signature, audience, issuer and expiry, every time.

The test issuer of the kit
The kit has no Access: the edge serves a test issuer of the course, with its own ES256 key, its certs and tokens with the same claims as Access. The origin uses Spring Security as a resource server, reading the token from the Cf-Access-Jwt-Assertion header, and checks the same four things. With Access, only three values change: the certs URL, the issuer and the audience.
→ Test the checks with tokens that should fail.

16. KV: fast reads, eventual writes
=================================================================
A key-value store cached close to every reader, where a write takes time to arrive.

Central stores, local copies
Workers KV writes to a small number of central data centers and caches the values in the data centers that read them; popular values stay cached where they are asked for. What it is for: data read much more than written, such as configuration, feature flags, allow and deny lists, user preferences. Rumbo keeps its maintenance flag and the key of its test issuer there.
→ KV is for reading a lot and writing a little.

Eventual means later
KV is eventually consistent: a write is usually visible at once where it was made, and can take up to 60 seconds or more to be visible elsewhere. A missing key is cached too, so a new key can take as long to appear. cacheTtl, 60 seconds by default, sets how long a read keeps its copy. The free plan gives 100,000 reads and 1,000 writes per day.
→ Design as if the next reader sees the old value.

Not a counter
KV has no atomic operations: read a number, add one and write it back from 50 requests at once, and most increments are lost, because each request read the same old value. The documentation also warns against writing the same key tens or hundreds of times per second, and points to Durable Objects for this. Locally there is one store, so what the lab loses comes from reading and writing in parallel; on Cloudflare, eventual consistency adds to it.
→ Read-modify-write needs one place that decides.

17. D1: SQLite at the edge
=================================================================
A managed SQL database with migrations, read by the Worker through a binding.

A database per binding
D1 is a managed, serverless database with the SQL of SQLite. The Worker uses prepared statements with bind, and gets rows back. Rumbo keeps its zones and quotes there: what the edge computes and records without asking the origin. The free plan allows 10 databases, 5 GB in total, 5 million rows read and 100,000 rows written per day.
→ Always bind values; never build SQL with strings.

Migrations
The schema changes with numbered SQL files in migrations, applied with wrangler d1 migrations apply, locally with --local and on the account with --remote. D1 records the applied ones in the d1_migrations table, so applying twice does nothing. The kit applies them every time the edge starts.
→ The schema is code: versioned, reviewed and applied in order.

One primary, read replicas
A D1 database has a primary that takes the writes. Read replication, in beta, adds copies in other regions for reads; the Sessions API, with a bookmark, lets a request read at least what an earlier one wrote. The Local Explorer of wrangler dev, at /cdn-cgi/local/explorer on the port of the edge, shows and edits the local tables.
→ Replicas are for reads; a bookmark is for reading your own writes.

18. R2: objects without egress fees
=================================================================
Store files by key and serve them from the edge, with no egress fees.

Objects in buckets
R2 is object storage: buckets with objects addressed by key, each with metadata and an etag. A Worker reaches it through a binding, and other programs through an API compatible with S3. Rumbo stores the proofs of delivery there, under proofs/<shipment>.txt.
→ A key is a name, not a folder.

No egress fees
Reading data out of R2 has no egress charge; the charges are storage and operations. The free tier, for Standard storage, gives 10 GB-month of storage, 1 million Class A operations, such as writes, and 10 million Class B operations, such as reads, per month. Enabling R2 on an account asks for a payment method: NOT VERIFIED in the documentation, it comes from a status incident.
→ With R2, reading is cheap; count the operations.

From the Worker
The binding has put, get, head, list and delete, and the bodies are streams: a Worker can pass a request body to put and an object body to a Response without loading it in memory. writeHttpMetadata copies the stored content type to the response. A bucket can also be public, through a custom domain, and notify a queue when objects change, configured on the account.
→ Stream bodies; do not buffer them.

19. Durable Objects: one place per thing
=================================================================
An object with an id, in one place, that handles its requests one at a time.

One object per id
A Durable Object is a class you write; each instance has a unique id or name and lives in one place. Every request for that id, from any data center, reaches the same instance. It handles them one at a time, so code that reads, changes and writes its own state does not race with itself. In Rumbo there is one object per shipment, and one per counter.
→ One id, one instance, one decision at a time.

Storage that is consistent
Each object has its own storage, strongly consistent: after a write, every later read of that object sees it. On the free plan only the SQLite backend is available, with 5 GB in total for the account. The same 50 increments that KV lost, the object keeps, because they arrive one after the other.
→ Coordination needs a single owner.

What it is not for
One object is one place: a soft limit of 1,000 requests per second each, and every caller waits its turn. For more load, split the state into more objects, one per shipment, per room, per user. Use them for coordination and per-entity state: counters, locks, live sessions, strict rate limits; not as one global table everyone writes to.
→ Many small objects scale; one big object queues.

20. Durable Objects over time
=================================================================
An object that wakes itself up and keeps sockets open while it sleeps.

An alarm per object
A Durable Object can schedule one alarm at a time with setAlarm; a new call replaces the pending one, and deleteAlarm cancels it. When the time comes, its alarm handler runs, at least once, never twice at the same time. If it throws, it is retried with exponential backoff from 2 seconds, up to 6 times.
→ An alarm is a promise to look again later.

Sockets that outlive the object in memory
With the WebSocket Hibernation API, the object accepts sockets with ctx.acceptWebSocket. When it is idle it is evicted from memory while the clients stay connected to the Cloudflare network; a message wakes it in webSocketMessage. Billable duration does not accrue while it hibernates. The standard WebSocket API prevents hibernation.
→ Hibernate between messages; pay for the work, not the wait.

A live shipment
In Rumbo each shipment object holds the live status, pushes every change to the browsers watching it and sets an alarm: if no movement arrives in 8 seconds, it marks itself delayed and tells them. A final status, delivered or returned, cancels the alarm. In production the wait would be hours; in the kit it is seconds so the lab can see it.
→ Let the object notice the silence.

21. Hyperdrive: your Postgres from the edge
=================================================================
A pool of connections near your database and a cache of read queries, behind a connection string.

A connection string that goes through Cloudflare
Hyperdrive sits between Workers and a PostgreSQL or MySQL database you already run. The Worker uses an ordinary driver, postgres.js in Rumbo, with env.PG.connectionString. The connection setup happens at the edge, close to the Worker, and the pool of database connections lives in the regions closest to your database. The free plan gives 100,000 queries per day.
→ Many Workers, few connections to your database.

Cached reads, and what they cost
Hyperdrive caches the results of read queries for a configured max_age. It does not invalidate them when your application writes, so a read right after a write can return the old row. It does not move or replicate your data: every query that is not cached reaches your server.
→ A cached query is a promise to accept old data.

In the kit, and for a private database
Locally there is no pool and no cache: Hyperdrive connects straight to the database with localConnectionString, or the variable CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_<BINDING>. What the kit shows is the path, not the speed. A database without a public address is reached through a Tunnel; the documentation now recommends Workers VPC, in beta.
→ The kit proves the code path; the account proves the speed.

22. Queues: at least once
=================================================================
Answer the carrier at once and do the work later, ready for a message that comes twice.

Producer, queue, consumer
A Worker sends a message to a queue through its binding and answers right away; a consumer Worker receives the messages in batches, by default up to 10 messages or 5 seconds, whichever comes first, with maximums of 100 and 60 seconds. Each message can be acknowledged with ack or sent back with retry, on its own, and carries attempts, the number of deliveries so far. The free plan includes 10,000 operations per day, with messages kept 24 hours.
→ Answer now; work later; acknowledge each message.

At least once
Queues delivers each message at least once and, on rare occasions, more than once. The consumer must therefore be idempotent: the same message twice must leave the same result as once. The documentation suggests a unique id per message used as a primary key or as an idempotency key; in Rumbo, the event id of the carrier is the primary key of the movements table at the origin.
→ Expect every message twice; store it once.

Retries and the dead letter queue
A message that is retried comes back in a later batch, up to max_retries, 3 by default; then it is deleted, or written to a dead letter queue if one is configured. A message can be delayed up to 24 hours. The kit uses max_retries 2 and a batch timeout of 2 seconds so the lab sees it in seconds: a status the origin rejects is tried three times and ends in movements-dead.
→ A dead letter queue is where you look, not where you forget.

23. Workflows: steps that survive
=================================================================
A process of many steps, each retried on its own, that can wait days for a person.

Steps with memory
A Workflow is a class with a run method that receives an event and a step object. Each step.do is a unit of work: its result is stored, so when the workflow resumes after a failure or a wait, finished steps are not run again. A failing step is retried on its own, by default up to 5 times, with a delay that starts at 10 seconds and grows exponentially, each try with a timeout of 10 minutes; NonRetryableError stops it.
→ Retry the step, not the process.

Waiting is a step
step.sleep and step.sleepUntil wait a time or until a date; step.waitForEvent waits for an event of a type, with a timeout, sent from outside with instance.sendEvent. While a workflow waits nothing runs and nothing is lost. In Rumbo, a return is registered, waits for the approval of a person, then refunds and notifies; the refund fails on purpose the first time.
→ Let the platform hold the wait.

Instances and limits
Each run is an instance with an id; creating one with an id that exists is refused, which makes a duplicate request harmless. The free plan shares the 100,000 daily requests of Workers and adds 3,000 steps per day and 1 GB-month of storage. Locally the status of an instance that waits for an event shows running.
→ An id per process makes starting it idempotent.

24. Cron and platform events
=================================================================
Work that starts at a time, or when the platform says something changed.

Cron Triggers
A Cron Trigger runs the scheduled handler of a Worker on a cron expression, in UTC, declared in triggers.crons of the configuration. In Rumbo, 0 3 * * * computes the daily close: shipments by status, stored in KV.

25. An edge you can defend
=================================================================
Rumbo, decided piece by piece, with a command behind each decision.

What is cached, and why
The public tracking page is the same for everyone: public, max-age=60. The API answers per shipment and changes: no-store. A profile is personal: private, no-store, never public, whatever the key. The rate of a zone is computed at the edge and kept per data center with the Cache API. Each decision is a header you can read.
→ Every cached answer has a reason written in its headers.

What protects what
The origin listens on no public port: a tunnel is its way in. The admin API is refused at the edge, as a custom rule would. The API is limited by API key. The panel needs identity at the edge and a token the origin validates itself, so reaching the origin directly does not skip the check. TLS to the origin is Full (strict).
→ Defend in layers; each layer assumes the one before failed.

What each store guarantees
KV for flags: read everywhere, eventual. A Durable Object per shipment and per counter: one place, one call at a time. D1 for quotes, with migrations. R2 for proofs, with no egress fees. A queue for movements, at least once, with an idempotent consumer and a dead letter queue. A workflow for returns, which wait for people. All of it fits the free plan for a small load, except what the zone needs, and R2 asks for a payment method.
→ Choose the store by its guarantee, not by its speed.

BIG PICTURE
=================================================================
One request, from DNS to your origin, and what the edge decides on the way

A. Through the edge
  1. Shop app: The lab plays a client of the API: GET /api/shipments/R-1042, to the edge of the kit on 127.0.0.1:18097.
  2. DNS: On Cloudflare the hostname is a proxied record: DNS answers with anycast addresses of Cloudflare, not with the address of the origin.
  3. Anycast: The same addresses are announced from every data center, and routing takes the request to one, usually nearby. /cdn-cgi/trace names it in colo.
  4. TLS: Leg 1 ends here, with a certificate Cloudflare manages for the zone. The encryption mode of the zone decides how leg 2 reaches the origin.
  5. WAF: Custom, rate limiting and managed rules run in fixed phases. Nothing matches, so the request goes on.
  6. Cache: No Access policy on this hostname. The API answers no-store, so no cache on the way may keep it.
  7. Worker: The gateway of Rumbo, in a V8 isolate. The admin API would be refused here; this route goes on.
  8. Rate limit: The budget of the key: 5 requests every 10 seconds. Without an x-api-key, every client shares the anonymous one.
  9. cloudflared, Tunnel: In production the request reaches the origin through connections cloudflared opened from inside. In the kit the Worker calls origin:8080 on the Compose network.
  10. API of Rumbo: The origin sees x-rumbo-edge and x-rumbo-request-id, added by the Worker. Called directly, with lab origin /echo, it sees neither.
  11. Worker: On the way out the Worker adds x-rumbo-via: edge. After the answer, ctx.waitUntil records the last request in KV without making the client wait.
  12. TLS: Back over leg 1. A site behind Cloudflare answers with server: cloudflare and a cf-ray, the Ray ID of the request.
  → Every request meets the edge first, in the data center where it arrived: TLS, the rules, the cache and the Worker decide before the origin is called, and each leaves something you can read in a header.

B. Around the edge
  1. Someone else: Someone nobody invited: a bot, an attack, or a person who found the address of the origin.
  2. DNS only: An old DNS-only record leaks it: Cloudflare answers with the real address, and requests go straight to that server, with no cache, no WAF and no Worker on the way.
  3. Open port: If the origin still listens on a public port, this path never meets the edge. A tunnel adds a way in; it does not close the others.
  4. API of Rumbo: The origin still asks for proof: its panel validates the token itself, so skipping the edge does not skip the check.
  5. API of Rumbo: In the kit the origin publishes no port: port 8080 has no address on your machine. Only the edge does.
  6. cloudflared, Tunnel: A way in from the inside: cloudflared, next to the service, opens outbound connections to Cloudflare, and the edge sends the requests for the hostname through them.
  7. cloudflared, Tunnel: A quick tunnel, with no account: a trycloudflare.com name answers with server: cloudflare and the body of rumbo-origin. In the validation runs it took 14 to 41 seconds.
  8. cloudflared, Tunnel: Registered tunnel connection: an outbound connection to a data center. A named tunnel keeps four, to two data centers, and survives restarts.
  → The proxy hides the origin in DNS only. With no open port and an origin that checks who calls, finding its address is not enough.

C. TLS in two legs
  1. TLS: Leg 1, from the visitor to the edge, with a certificate Cloudflare manages for the zone. The padlock says nothing about leg 2.
  2. TLS: Leg 2 depends on the encryption mode of the zone: Off, Flexible, Full, Full (strict) or Strict. lab tls plays the edge on that leg; an impostor answers with a self-signed certificate for the same name.
  3. API of Rumbo: Flexible: leg 2 in plain HTTP. Whoever sits between the edge and the origin can read and change it.
  4. API of Rumbo: Full: HTTPS without validating the certificate. A self-signed one is accepted, and so is any server that answers with one: encrypted, to the wrong server.
  5. API of Rumbo: Full (strict) validates the certificate of the origin, signed by the test CA of the kit, which stands for the authorities it trusts.
  6. API of Rumbo: The impostor under strict: rejected, DEPTH_ZERO_SELF_SIGNED_CERT. The name was right; nobody trusted signed it.
  → Encrypted is not enough: leg 2 must also check who answers. Full (strict) validates the certificate of the origin; Full accepts any.

D. A Worker in front
  1. Wrangler: wrangler.jsonc names the Worker, its entry point, its compatibility date and nine bindings: COUNTERS, DB, FLAGS, LIMITER, MOVES, PG, PROOFS, RETURNS and SHIPMENTS.
  2. Worker: vars are committed with the code; secrets go to the account, and locally to .dev.vars, read when wrangler dev starts. The lab prints only the length.
  3. Worker: A V8 isolate inside a runtime that already runs: a module variable survives some requests. Restart the edge and the id changes: global state is not yours to keep.
  4. Worker: A CORS preflight is answered at the edge, only for the shop that is allowed.
  5. Worker: For another page there is no access-control-allow-origin: a browser there will not let its script read the answer.
  6. Worker: The admin API is refused at the edge: the origin gets no load from it and never sees it.
  7. KV: After an answer, ctx.waitUntil keeps working for up to 30 seconds: the gateway records the last request in KV. The refused and the preflight requests never got that far.
  8. The kit: Tests run inside workerd with the bindings simulated: health, the admin API, CORS, maintenance, the forward to the origin and the 502 of a dead origin.
  9. The kit: The origin is not part of the test: vi.spyOn replaces the global fetch, to answer as the origin would or to fail as a dead one.
  → Each decision taken at the edge is one the origin does not have to take, and one it cannot get wrong. Global state is not yours to keep, and the tests run in the same runtime.

E. Deploy and versions
  1. The kit: A second Worker, rumbo-edge-demo, with no bindings so it fits the free plan: --dry-run builds it and stops.
  2. Wrangler: With labs/.env, your account id and a token that can edit Workers. Optional, and never printed.
  3. Worker: wrangler deploy uploads a version and deploys it to 100%: the Worker answers on workers.dev, with no zone of your own.
  4. Worker: versions upload keeps a new version without serving it. A deployment can use only the last 100 uploaded versions.
  5. Worker: versions deploy splits the traffic by percentage. Running it again moves the split, or rolls back.
  6. TLS: Each request is routed on its own: most get v1, a few v2, and one user can see both, unless version affinity keeps a key on one.
  → A version is code and configuration, kept; a deployment says which versions serve requests and in what share. Moving the split is how you roll forward or back.

F. What the edge keeps
  1. Browser: A customer opens the public tracking page, GET /track/R-1042: the same page for everyone who follows that shipment.
  2. Worker: The page answers cache-control: max-age=60, public: the same for everyone, safe to share for a minute. A zone would not keep it by default, because it is HTML; Workers Cache would.
  3. Cache: Workers Cache sits in front of the Worker and follows the Cache-Control of its answers: MISS, then HIT. A HIT does not run the Worker, so it uses no CPU, though it still counts as a request. wrangler dev does not run it, so this needs an account.
  4. Cache: private, no-store or a Set-Cookie: nothing is kept. A 200 with no Cache-Control is kept by heuristic, for up to two hours.
  5. Worker: A profile is personal, but this route marks it public, and the cache key is the URL: it does not include the user. Ana's profile is now stored.
  6. Cache API: Beto asks for the same URL and gets the stored entry: Ana's profile, with her address. The kit plays the trap with the Cache API; the cache of a zone falls into it the same way.
  7. Cache API: profile-safe answers private, no-store: nothing is kept, and each person gets their own answer.
  8. Cache API: caches.default from the Worker: match, put and delete, under a key it chooses. The rate of a zone is kept for 60 seconds.
  9. Cache API: delete purges only this data center: the Cache API does not replicate. To reach every data center, purge the zone, or Workers Cache by tag.
  → The response decides what is kept: public only for what is the same for everyone, private or no-store for anything personal. Purging fixes the past; only a correct Cache-Control fixes the future.

G. Rules and budgets
  1. Shop app: GET /api/admin/users: a route no client should reach.
  2. WAF: On a zone, a custom rule starts_with(http.request.uri.path, "/api/admin") with Block ends the request here: later phases and the Worker never see it. Blocks are sampled as security events.
  3. Worker: The kit has no zone, so the gateway plays the rule: 403 before the origin, answered by the Worker alone.
  4. Worker: /API/admin/users passes: the rule compares exact text, case included, and Spring Boot answers 404. A WAF expression that ignores case uses lower(http.request.uri.path).
  5. Rate limit: A budget per x-api-key: 5 requests every 10 seconds. k1 gets five 200s, then 429 with retry-after: 10.
  6. Rate limit: k2 has its own budget. The counts are per location and eventually consistent: approximate, not exact.
  7. WAF: A rate limiting rule of the WAF runs in its own phase, before any Worker; the free plan includes one. The binding knows what a rule cannot, such as the tenant behind a key.
  → A rule in the zone runs before any Worker; a rule in code runs only where your Worker runs, and both compare text exactly as written. A budget per key counts what a rule of the zone cannot see.

H. Identity before the origin
  1. Employee: Ana, of operations, opens the internal panel, from home, with no VPN.
  2. Access: Cloudflare Access asks who she is: she signs in with the identity provider, and a policy allows the people of operations.
  3. Access: The edge adds a signed JWT to the requests that pass: the Cf-Access-Jwt-Assertion header and the CF_Authorization cookie.
  4. API of Rumbo: The kit has no Access. Without a token, the origin asks for one.
  5. Worker: The edge of the kit serves a test issuer with its own ES256 key and the claims of Access: iss, aud rumbo-panel, Ana's email, and an expiry five minutes later.
  6. API of Rumbo: Spring Security, as a resource server, validates four things: the signature with the published keys, the audience, the issuer and the expiry.
  7. API of Rumbo: A token of another application, expired or changed gets 401, and the reason: the audience, Jwt expired, Invalid signature.
  8. API of Rumbo: Called directly, skipping the edge, the origin still asks for proof. With Access only three values change: the URL of the keys, the issuer and the audience.
  → Access checks who the person is at the edge; the origin validates the signed token itself. Reaching the origin another way does not skip the check.

I. A flag and a counter
  1. KV: Workers KV keeps the maintenance flag of Rumbo: written to central stores, cached in the data centers that read it.
  2. Worker: The gateway reads the flag: on, so it answers 503, maintenance, and the origin is not called.
  3. KV: Delete it and the next request reaches the origin. Locally the change is seen at once; on Cloudflare, other data centers can take a minute or more.
  4. KV: Not a counter: 50 requests read the same old number, add one and write it back. KV has no atomic operations, and most increments are lost.
  5. Durable Object: A Durable Object per counter, through the binding COUNTERS, lives in one place and handles one call at a time: the 50 increments arrive one after the other.
  6. Durable Object: Its storage is strongly consistent. One object is one place, though, with a soft limit near 1,000 requests a second: split the state into more objects for more load.
  7. Durable Object: An object exists because it was asked for: shipment R-1043, no movements yet, nobody watching.
  → KV is for data read much more than written, and eventual. A counter needs one place that takes one call at a time: a Durable Object.

J. Data next to the Worker
  1. Worker: The edge computes a shipping quote by itself, without asking the origin.
  2. D1: D1 is SQLite at the edge, with prepared statements and bind. Madrid, 2.5 kg: 12.0 + 1.6 x 2.5 = 16, stored as a new quote.
  3. D1: The schema changes with numbered migrations, recorded in d1_migrations: applying twice does nothing.
  4. R2: R2 keeps the proof of delivery as an object, proofs/R-1043.txt, with its etag. Bodies are streams: the Worker passes them on without loading them.
  5. R2: Reading it out has no egress fee; storage and operations are what count. R-1044 has no proof: 404.
  6. Hyperdrive: /direct reads the shipment from PostgreSQL through Hyperdrive, with an ordinary driver: Spring Boot is not involved.
  7. PostgreSQL 18: The same database the origin uses. On Cloudflare, Hyperdrive pools connections near it and caches reads without invalidating them on writes; in the kit there is no pool and no cache.
  8. API of Rumbo: The same status through the origin: two paths to one database, and the edge chooses.
  → Each store has its own guarantee: SQL with migrations in D1, objects with no egress fees in R2, and your own Postgres through Hyperdrive, without moving the data.

K. A carrier's webhook
  1. Carrier: A carrier reports a movement: POST /webhooks/movement, event m-1, R-1042, delivered.
  2. Worker: The Worker sends the movement to the queue and answers 202 at once: the carrier does not wait for the work.
  3. Queue: At least once. The kit delivers a batch every 2 seconds, with max_retries 2 and a dead letter queue, movements-dead.
  4. Worker: The queue handler of the same Worker takes the batch and posts each movement to the origin.
  5. API of Rumbo: The event id is the primary key of the movements table: saved once.
  6. Durable Object: The object of shipment R-1042 takes the new status and pushes it over its WebSocket to the browsers watching it.
  7. API of Rumbo: The same message twice: the origin answers already saved, and nothing changes. The consumer has to be idempotent.
  8. Queue: A status the origin rejects with 422: retried, three attempts, then movements-dead, in about eight seconds.
  9. Durable Object: No movement in 8 seconds: the alarm of the object marks the shipment delayed and tells its watchers. A final status, delivered, cancels the alarm.
  → The carrier gets 202 at once and the work happens later, at least once. The event id makes a repeat harmless, a dead letter queue keeps what failed, and the object of the shipment notices silence.

L. A return that waits
  1. Shop app: A return is requested for shipment R-1043: POST /returns/r-1.
  2. Worker: The Worker creates an instance of the Workflow of returns with the id r-1.
  3. Workflow: step.do stores the registration; step.waitForEvent waits for approved. While it waits, nothing runs and nothing is lost.
  4. Workflow: Status running, output null: the instance waits for a person, for days if needed.
  5. Workflow: Ana approves: an approved event with her name. The refund fails once on purpose, and only that step is retried.
  6. Workflow: Registered, refunded, approved by ana, notified: the output of every step is stored.
  7. Worker: The same id again is refused: instance.already_exists. A duplicate request is harmless.
  → Each step of a Workflow stores its result, so waiting for a person or retrying a failed step loses nothing, and the id of an instance makes a repeated request harmless.

M. The close at 03:00
  1. Cron Trigger: A Cron Trigger, 0 3 * * *, in UTC: the daily close of Rumbo. After a change, the new schedule can take up to 15 minutes to reach the network.
  2. Worker: wrangler dev does not fire Cron Triggers by itself: lab cron asks the Local Explorer to run the scheduled handler.
  3. Hyperdrive: The handler reads the shipments by status from PostgreSQL, through Hyperdrive.
  4. PostgreSQL 18: Three shipments, counted by status.

  → A Cron Trigger runs the scheduled handler of the Worker at a time in UTC, with the same bindings as a request. Locally you run it by hand.

N. An edge you can defend
  1. Cache: What is cached, and why: the public page max-age=60, the API no-store, a profile private, the rate of a zone in the Cache API of each data center.
  2. Worker: The admin API is refused at the edge, as a custom rule would, and the API is limited per key.
