WHAT GIT AND GITHUB ARE
=================================================================
What they are, where they came from, where they fit and where they do not. Read it once; the lessons do the rest.

Snapshots you keep, changes you agree on
Git is a distributed version control system. Each commit is a complete snapshot of the project, identified by the hash of its content and linked to the commit or commits it came from; a branch is a movable pointer to one of them. Every copy of the repository holds the whole history, so recording, comparing and branching happen on your machine, without a network.
GitHub is a service that hosts Git repositories and adds what a team needs to agree on changes: issues, pull requests and reviews, rules on branches, Actions to automate, releases. It does not replace Git; it hosts it. A commit you record locally does not exist on GitHub until you publish it, and nothing on GitHub reaches your copy until you fetch it.
→ Git records history; GitHub is where people agree on it.

Where they came from
Git was written by Linus Torvalds in April 2005 for the development of the Linux kernel, after the project lost the use of BitKeeper, the proprietary tool it had relied on since 2002. The goals were set from the start: speed, a simple design, strong support for non-linear development with thousands of parallel branches, fully distributed, and able to handle a project the size of the kernel. Within months Torvalds handed maintenance to Junio Hamano, who has led the project since.
GitHub was built by Tom Preston-Werner, Chris Wanstrath and PJ Hyett and launched in April 2008: hosting for Git repositories, with the collaboration around them on the web. Microsoft completed its acquisition in October 2018, with the commitment that GitHub would operate independently. It grew into the place where a large part of open source is published, and the tools around a change, issues, pull requests, Actions and releases, grew with it. The timeline keeps the changes that still shape how it is used.
2005 Git: Linus Torvalds records the first commit on 7 April; version 1.0 follows in December.
2008 GitHub: Public launch in April: hosting for Git repositories with collaboration on the web.
2018 Microsoft: Microsoft completes the acquisition of GitHub in October, committing that it will operate independently and remain an open platform.
2019 Actions: GitHub Actions is generally available in November: workflows that run on events in the repository.
2020 main: Git 2.28 adds init.defaultBranch in July; in October, main becomes the default name of the first branch in new GitHub repositories.
2023 Rulesets: Repository rules (rulesets) are generally available in July: protections for branches and tags, visible to everyone who collaborates.

Where they fit
The official documentation of both describes what they are for. These are the cases you will meet in everyday development.
- Source code and any text that changes bit by bit: Configuration, documentation, infrastructure as code: anything written in lines, where a diff tells you what changed.
- Parallel work without stepping on each other: Each line of work on its own branch; merge or rebase joins them when they are ready, and conflicts are shown instead of lost.
- Agreeing on a change before integrating it: A pull request puts the proposal, the discussion, the review and the automatic checks in one place, before the change reaches the main branch.
- A history you can audit and recover from: Who changed what and when; revert undoes a change with a new commit; bisect finds the commit that broke something.
- Automation that runs with every change: Actions runs workflows on a push, on a pull request or on a schedule: build, tests, checks, deployment.
- Deliveries you can name: A tag fixes a point in history; a release adds notes and files to it, so everyone knows which version was delivered.

Where they do not fit
This part is the course's judgment, not official documentation. Each row says what to use instead.
- Large binary files that keep changing: Videos, datasets and compiled artifacts have no useful diff, and every version stays in every clone. GitHub blocks files over 100 MiB and recommends keeping repositories small, ideally under 1 GB. Use instead: Git LFS for the files that must travel with the code; an artifact store or object storage for the rest.
- Secrets and credentials: Once committed they are in the history of every clone and fork, and rewriting history does not reach other people's copies. The first step is always to revoke the secret. Use instead: A secrets manager, values injected at deploy time, and rotation.
- Generated artifacts: Build output is rebuilt from the code; versioning it doubles the history and produces a conflict on every build. Use instead: An artifact registry (Maven, npm, container images) or the files attached to a release.
- Business data and databases: Git versions files, not rows: no queries, no concurrent writers, no transactions. Use instead: The database, plus versioned migrations in the repository so the schema has a history.
- Editing a document together in real time: Git integrates finished changes; it does not merge keystrokes. Two people in the same paragraph at the same time end in conflicts. Use instead: A collaborative editor for the writing; Git for the result, once it is text worth keeping.
- As the deployment or backup tool itself: A repository says which version exists, not that it is running or safe: no environments, no rollback of state, no retention policy. Use instead: Git as the source for both: a pipeline that deploys from a tag, and backups of the repository and of the data it does not hold.

How to decide
1. Does it change bit by bit, and is it text?
2. Does more than one person work on it at the same time?
3. Does someone need to agree before a change is integrated?
4. Do you need to go back, and to know who changed what?
5. Does something have to run with every change: tests, checks, a deployment?
Three yes answers and you are in the right place. Lesson 00 shows how the course works and what your machine needs.

01. Git and GitHub
=================================================================
One records history. The other gives a team a place to collaborate.

The repository is more than a folder
A working folder contains the files you edit. A Git repository also records versions and relationships between them. Saving guide.txt changes a file; recording a commit adds a historical checkpoint. These are separate acts.
→ A saved file is not necessarily recorded history.

Local first
Git can record and inspect history without GitHub. GitHub hosts repositories and adds issues, pull requests and review. A local commit does not appear on GitHub until you transfer it. You can have several copies of a repository.
→ Recording and sharing are different events.

Who sees the change?
Ana records new library hours on her laptop. Bruno still sees the old version in his copy. Even when Ana publishes her branch, Bruno must obtain the new history. Treat each copy as a separate place with its own current knowledge.
→ Always name the copy you are talking about.

02. Commits: snapshots with a reason
=================================================================
A version is content plus context and ancestry.

A coherent checkpoint
Imagine photographing the whole library guide after correcting its hours. A commit records a snapshot of the tracked project, a message and metadata, with links to parent commits. Unchanged content can be reused internally; this is not a new full disk copy every time.
→ Think snapshot first; a diff compares snapshots.

The graph explains the story
An arrow from a commit to its parent says which recorded state it follows. The initial commit has no parent. A typical commit has one; a merge commit can have more. Commit identifiers name objects, not a sequence of revision numbers.
→ Read ancestry, not just timestamps.

A reason helps the next reader
“Fix hours after winter schedule change” helps a reviewer understand why a line moved. “Update file” does not. Group changes by purpose so a future teammate can explain, review or reverse one decision without untangling unrelated edits.
→ One intelligible decision is a useful unit of history.

03. Three places for a change
=================================================================
Editing, preparing and recording are separate decisions.

Your desk
The working tree is the set of files you currently edit. Ana corrects the hours and starts an unfinished note. Both changes are on her desk. She wants to record only the finished correction.
→ What is edited can exceed what should be committed.

The next snapshot
The staging area, also called the index, holds the content selected for the next commit. It is a prepared version, not just a list of filenames. If you stage 10:00 then edit the file to 11:00, the prepared content is still 10:00 until you stage again.
→ Preparing captures content at that moment.

Read both comparisons
The ordinary diff compares your working files with the index. The staged diff compares the index with the current commit. In our example, one shows 10:00 to 11:00; the other shows 09:00 to 10:00. A normal commit records the index.
→ Ask which two states the comparison uses.

04. Branches are movable names
=================================================================
A parallel line of work starts with a pointer.

Two names, one starting point
main names our accepted history. Creating hours from main gives another name to the same commit. No new historical version is required just to create that branch. The names can move independently as work continues.
→ A branch points to a commit; it is not a folder copy.

Where is the next commit going?
HEAD usually identifies the current branch. While hours is checked out, a new commit advances hours and leaves main where it was. Switching branches changes the selected history and updates files as needed; Git can refuse if local edits would be overwritten.
→ Know your current branch before recording work.

Names are agreements
main is a convention, not a built-in quality guarantee. A branch named production can contain broken work. The team decides what each branch means and what evidence is needed to advance it. A branch is not access isolation.
→ The name communicates intent; policy enforces it.

05. Merging histories
=================================================================
Combine work using its shared starting point.

One path is already inside another
If main has not moved since hours branched off, main can advance to the tip of hours. This fast-forward needs no new merge commit. The existing commits already describe a continuous path.
→ Fast-forward moves a name along existing history.

Two paths have advanced
Ana changes the hours while Bruno adds a contact file. The branches diverge. Git uses a shared ancestor and both tips to combine changes. A usual merge commit records the result with both tips as parents.
→ A merge preserves both lines of ancestry.

Text fits; behavior may not
Ana changes the opening hour to 10:00. Bruno advertises a workshop at 09:30 in another file. Git can combine those edits without a textual conflict. The resulting guide still contradicts itself. Test the meaning after combining the text.
→ No textual conflict does not mean no problem.

06. Conflicts are unanswered questions
=================================================================
The tool finds ambiguity; people decide the meaning.

One line, two intentions
From the same 09:00 starting point, Ana writes 10:00 and Bruno writes 11:00. Both change the same line. Git cannot decide the library schedule. A conflict marks a choice that automatic text integration cannot safely make.
→ A conflict is information, not proof that history is lost.

Three versions matter
Read the shared base, the current side and the incoming side. “Ours” and “theirs” depend on the operation, not on who is morally right. Ask each author what they intended before editing the combined result.
→ Compare intentions against the common base.

Resolve, then verify
After deciding on 10:30, replace the conflict markers with the agreed text, prepare that result and finish the merge. Removing markers alone is not enough: confirm the guide is consistent. Aborting an unfinished merge is another choice when you need to reconsider.
→ Resolution is a new decision with its own evidence.

07. Remotes and independent copies
=================================================================
A remote is an address with a local nickname.

Clone makes another repository
A usual clone copies repository history and checks out a working version. It is not a live shared folder. Editing the clone does not edit the source. Special shallow or partial clones can copy less; our experiments use ordinary complete clones.
→ A clone is an independent place to work.

origin is a nickname
A remote configuration associates a name such as origin with an address. That address can be on GitHub, another host or even a local disk. Naming it origin does not make it the official project or grant permission to write.
→ Location, authority and permission are separate facts.

Your last observation
origin/main is normally a local remote-tracking reference: your last recorded view of main at origin. It can be stale while someone else publishes new work. Your local main, origin/main and the server’s main are three distinct references.
→ A remote-tracking reference is knowledge, not a live window.

08. Fetch, integrate, publish
=================================================================
There is no single magical “sync” operation.

Learn what changed
Fetching obtains objects and updates configured remote-tracking references. In the usual workflow it does not merge them into your current branch or edit your working files. You can inspect the new history before choosing how to integrate it.
→ Obtaining information and adopting it are separate.

Choose the integration
Pull combines fetching with an integration step, whose policy may be fast-forward, merge or rebase depending on options and configuration. First ask whether your histories diverged. A fast-forward-only policy stops rather than silently resolving a divergence.
→ Understand the policy behind a convenience button.

Publish without discarding others
A normal push proposes updating a remote reference with your history. If the remote has commits absent from your proposed path, a non-fast-forward rejection protects that work. Fetch, inspect and integrate; forcing is not the default remedy.
→ A rejection can preserve someone else’s work.

09. Fork, clone and branch
=================================================================
Three forms of separation answer different needs.

A branch stays in one repository
A branch gives a line of work a name within a repository. Teammates with suitable access can publish branches in the same GitHub repository. This is useful when the team shares the repository’s governance.
→ A new branch is not a new owner.

A fork creates another hosted home
A GitHub fork is another repository linked to the original in a fork network. You can propose a change from a branch in your fork without having write access to the original. Fork availability and permissions depend on repository visibility and organization policy.
→ Permission to propose does not imply permission to integrate.

A clone gives you a local workspace
You can clone your fork and configure origin to point to it, with upstream pointing to the original. Those names are conventions. Updating your fork or clone does not automatically update the original project.
→ Draw the repositories before drawing branches inside them.

13. Same files, different histories
=================================================================
Merge, squash and rebase preserve different kinds of context.

Keep the meeting point
A merge commit joins histories with multiple parents. You can see where the feature line met main and retain its individual commits. This helps when the sequence of decisions on that line matters to future readers.
→ Merge keeps the topology of the collaboration.

Keep the resulting decision
Squashing records the proposal’s combined change as one new commit on the destination. The original feature commits are not ancestors through that integration. This can make main easier to read when a feature contains many temporary corrections.
→ Squash trades intermediate history for one coherent result.

Replay onto another base
Rebase replays changes onto a new base, producing new commits when ancestry changes. Coordinate before rewriting work others use. GitHub’s rebase-and-merge creates new commit SHAs; its behavior is not identical to every local rebase case. Choose based on the history you want to maintain.
→ Equal final files do not imply equal ancestry.

14. Undo without losing the story
=================================================================
First identify whether the mistake is edited, recorded or shared.

Undo which state?
An unfinished edit, a prepared change and a shared commit are different problems. Restoring a working file can discard unrecorded work. Removing a change from staging can leave the edit intact. State the desired result before choosing an undo operation.
→ “Undo” is a goal, not one universal operation.

Add a corrective decision
Revert records a new commit that reverses an earlier commit’s effect. The original remains in history, explaining what happened. Reverting can conflict if later work depends on the changed content. It is useful for published work because it does not require moving the shared branch backward.
→ Correcting history and erasing history are different intentions.

Moving a reference
Reset can move the current branch and, depending on mode, change the index and working files. A hard reset can discard edits. Reflogs record local reference movements for a limited time; they are not permanent backup. Our lab uses only an isolated soft reset to compare mechanisms.

15. Actions: automated evidence
=================================================================
An event starts work whose result has a defined scope.

Event, workflow, job, step
A workflow describes automation. An event such as a pull request update can trigger it. Jobs run on runners, the machines executing the work. Steps within a job run in sequence; jobs can be independent or have dependencies. These names describe a flow of work.
→ Trace why the run started and what it actually executed.

A meaningful failing example
Our example checks that README contains 10:00. First try 09:00 and observe failure, then fix the text. A green run means that this assertion passed for that run’s revision. It does not establish opening hours in the real world or deploy the guide.
→ A useful check can demonstrate both failure and success.

Automation has authority
A workflow executes code with permissions and possibly secrets. Keep permissions narrow and review changes to workflows like other code. Untrusted contributions must not gain privileged secrets merely by opening a proposal. This course uses a small workflow with read-only repository contents permission.

16. Rules: turn agreements into gates
=================================================================
Access, review and checks answer different questions.

Who may do what?
Repository permissions control capabilities. Authentication establishes who you are; authorization determines what you may do. Being able to read a public repository does not mean you can push to it. A review approval is not a new repository permission.
→ Identity and permission are different questions.

Require evidence at the destination
Repository rules can require pull requests, approvals or status checks before a target branch updates. Define which branch the rule targets and which check is required. Availability depends on plan and repository type; inspect your repository rather than assuming every option exists.
→ A passing check and an enforced required check are different.

The exception is part of the rule
Bypass permissions, rule activation and branch patterns affect enforcement. A configuration that targets another branch does not protect main. Review who may bypass a requirement and why; describe the actual boundary rather than claiming the repository is simply “protected”.
→ State the target, requirement and exceptions together.

17. Tags, releases and deployments
=================================================================
Naming a version, explaining it and running it are different events.

A name for a chosen point
A tag such as v1.0 names a chosen point in history. Unlike a branch, it does not automatically advance with new commits. Teams usually treat published version tags as stable agreements, even though Git has operations that can move or delete tags. An annotated tag is an object with author, date and message; a lightweight tag is only a name.
→ Stability is a publishing policy, not an impossibility of change.

Explain the delivered version
A GitHub release is based on a tag and can add notes and downloadable assets. Explain the user-visible changes, known limits and upgrade considerations. The tag names the source point; the release adds delivery context.
→ A version number is less useful without its meaning.

Running is another step
A deployment puts a chosen artifact into an environment. Publishing a release does not by itself prove anything was deployed; a separately configured automation may connect them. Record the deployed revision and the environment so people can answer what is actually running.
→ Source version, downloadable artifact and running system are distinct.

18. History remembers what you remove
=================================================================
Ignoring a file and erasing exposure are different problems.

Choose what belongs in history
Build outputs, local settings and credentials usually do not belong in a shared source history. A .gitignore rule guides which untracked files Git normally ignores. It does not automatically untrack a file already recorded.

Deletion is a new snapshot
Deleting a file and recording that deletion removes it from the new snapshot. Earlier commits can still contain it. A private repository also has readers and possible copies; privacy is not a substitute for keeping credentials out of source history.
→ Absent now does not mean absent from history.

If a real credential is exposed, revoke or rotate it first. Then follow the host’s documented cleanup process and coordinate affected clones and forks. Rewriting one repository cannot guarantee removal from every copy. Our lab uses only an unmistakably fake marker.
