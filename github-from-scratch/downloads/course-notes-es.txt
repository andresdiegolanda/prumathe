QUÉ SON GIT Y GITHUB
=================================================================
Qué son, de dónde salieron, dónde encajan y dónde no. Se lee una vez; el resto lo hacen las lecciones.

Instantáneas que guardás, cambios que acordás
Git es un sistema de control de versiones distribuido. Cada commit es una instantánea completa del proyecto, identificada por el hash de su contenido y enlazada al commit o commits de los que viene; una rama es un puntero móvil a uno de ellos. Cada copia del repositorio tiene toda la historia, así que registrar, comparar y ramificar pasan en tu máquina, sin red.
GitHub es un servicio que aloja repositorios Git y agrega lo que un equipo necesita para ponerse de acuerdo sobre los cambios: issues, pull requests y revisiones, reglas sobre las ramas, Actions para automatizar, releases. No reemplaza a Git; lo aloja. Un commit que registrás en tu máquina no existe en GitHub hasta que lo publicás, y nada de GitHub llega a tu copia hasta que hacés fetch.
→ Git registra la historia; GitHub es donde la gente se pone de acuerdo.

De dónde salieron
Git lo escribió Linus Torvalds en abril de 2005 para el desarrollo del kernel de Linux, después de que el proyecto perdió el uso de BitKeeper, la herramienta propietaria con la que trabajaba desde 2002. Los objetivos estaban fijados desde el principio: velocidad, diseño simple, soporte fuerte para desarrollo no lineal con miles de ramas en paralelo, totalmente distribuido y capaz de manejar un proyecto del tamaño del kernel. A los pocos meses Torvalds pasó el mantenimiento a Junio Hamano, que lleva el proyecto desde entonces.
GitHub lo construyeron Tom Preston-Werner, Chris Wanstrath y PJ Hyett y se lanzó en abril de 2008: alojamiento de repositorios Git, con la colaboración alrededor en la web. Microsoft completó la compra en octubre de 2018, con el compromiso de que GitHub operaría de forma independiente. Creció hasta ser el lugar donde se publica buena parte del open source, y las herramientas alrededor de un cambio, issues, pull requests, Actions y releases, crecieron con él. La línea de tiempo conserva los cambios que todavía marcan cómo se usa.
2005 Git: Linus Torvalds registra el primer commit el 7 de abril; la versión 1.0 llega en diciembre.
2008 GitHub: Lanzamiento público en abril: alojamiento de repositorios Git con colaboración en la web.
2018 Microsoft: Microsoft completa la compra de GitHub en octubre, con el compromiso de que opere de forma independiente y siga siendo una plataforma abierta.
2019 Actions: GitHub Actions queda disponible en general en noviembre: workflows que corren con eventos del repositorio.
2020 main: Git 2.28 agrega init.defaultBranch en julio; en octubre, main pasa a ser el nombre por defecto de la primera rama en los repositorios nuevos de GitHub.
2023 Rulesets: Las reglas de repositorio (rulesets) quedan disponibles en general en julio: protecciones para ramas y tags, visibles para quien colabora.

Dónde encajan
La documentación oficial de los dos describe para qué sirven. Estos son los casos que vas a encontrar en el desarrollo de todos los días.
- Código fuente y cualquier texto que cambia de a poco: Configuración, documentación, infraestructura como código: todo lo que se escribe en líneas, donde un diff te dice qué cambió.
- Trabajo en paralelo sin pisarse: Cada línea de trabajo en su propia rama; merge o rebase las juntan cuando están listas, y los conflictos se muestran en lugar de perderse.
- Acordar un cambio antes de integrarlo: Un pull request junta la propuesta, la conversación, la revisión y los controles automáticos en un solo lugar, antes de que el cambio llegue a la rama principal.
- Una historia auditable y recuperable: Quién cambió qué y cuándo; revert deshace un cambio con un commit nuevo; bisect encuentra el commit que rompió algo.
- Automatización que corre con cada cambio: Actions corre workflows con cada push, con un pull request o por calendario: build, tests, controles, despliegue.
- Entregas identificables: Un tag fija un punto de la historia; una release le agrega notas y archivos, así todos saben qué versión se entregó.

Dónde no encajan
Esta parte es criterio del curso, no documentación oficial. Cada fila dice qué usar en su lugar.
- Archivos binarios grandes que cambian: Videos, datasets y artefactos compilados no tienen un diff útil, y cada versión queda en cada clon. GitHub bloquea archivos de más de 100 MiB y recomienda repositorios chicos, idealmente de menos de 1 GB. Usá en su lugar: Git LFS para los archivos que tienen que viajar con el código; un almacén de artefactos u object storage para el resto.
- Secretos y credenciales: Una vez en un commit quedan en la historia de cada clon y cada fork, y reescribir la historia no llega a las copias de los demás. El primer paso siempre es revocar el secreto. Usá en su lugar: Un gestor de secretos, valores inyectados al desplegar y rotación.
- Artefactos generados: Lo que produce el build se reconstruye desde el código; versionarlo duplica la historia y genera un conflicto en cada build. Usá en su lugar: Un registro de artefactos (Maven, npm, imágenes de contenedores) o los archivos adjuntos a una release.
- Datos de negocio y bases de datos: Git versiona archivos, no filas: sin consultas, sin escritores concurrentes, sin transacciones. Usá en su lugar: La base de datos, más migraciones versionadas en el repositorio para que el esquema tenga historia.
- Edición simultánea de un documento en tiempo real: Git integra cambios terminados; no mezcla pulsaciones. Dos personas en el mismo párrafo al mismo tiempo terminan en conflictos. Usá en su lugar: Un editor colaborativo para escribir; Git para el resultado, cuando ya es un texto que vale la pena guardar.
- Como herramienta de despliegue o respaldo en sí misma: Un repositorio dice qué versión existe, no que esté corriendo ni a salvo: sin entornos, sin rollback de estado, sin política de retención. Usá en su lugar: Git como fuente de los dos: un pipeline que despliega desde un tag, y respaldos del repositorio y de los datos que no contiene.

Cómo decidir
1. ¿Cambia de a poco y es texto?
2. ¿Trabaja más de una persona a la vez?
3. ¿Hace falta que alguien acuerde antes de integrar un cambio?
4. ¿Hay que poder volver atrás y saber quién cambió qué?
5. ¿Hay que correr algo con cada cambio: tests, controles, un despliegue?
Tres síes y estás en el lugar correcto. La lección 00 muestra cómo funciona el curso y qué necesita tu máquina.

01. Git y GitHub
=================================================================
Uno registra historia. El otro le da al equipo un lugar para colaborar.

El repositorio es más que una carpeta
Una carpeta de trabajo contiene los archivos que editás. Un repositorio Git también registra versiones y sus relaciones. Guardar guide.txt cambia un archivo; registrar un commit agrega un punto en la historia. Son actos distintos.
→ Un archivo guardado no necesariamente quedó en la historia.

Primero, lo local
Git puede registrar y consultar historia sin GitHub. GitHub aloja repositorios y agrega issues, pull requests y revisión. Un commit local no aparece en GitHub hasta que lo transferís. Podés tener varias copias de un repositorio.
→ Registrar y compartir son eventos distintos.

¿Quién ve el cambio?
Ana registra horarios nuevos en su laptop. Bruno todavía ve la versión anterior en su copia. Incluso cuando Ana publica su rama, Bruno tiene que obtener la historia nueva. Tratá cada copia como un lugar separado con su propio conocimiento actual.
→ Siempre nombrá la copia de la que hablás.

02. Commits: instantáneas con un motivo
=================================================================
Una versión es contenido, contexto y ascendencia.

Un punto coherente
Imaginá fotografiar toda la guía después de corregir los horarios. Un commit registra una instantánea del proyecto seguido, un mensaje y metadatos, con enlaces a commits padres. Internamente se puede reutilizar contenido sin cambios; no es una copia completa nueva del disco cada vez.
→ Pensá primero en instantáneas; un diff compara instantáneas.

El grafo explica la historia
Una flecha de un commit a su padre indica a qué estado registrado sigue. El inicial no tiene padre. Uno habitual tiene uno; un merge commit puede tener más. Los identificadores nombran objetos, no una secuencia de números de revisión.
→ Leé ascendencia, no solo fechas.

El motivo ayuda a quien viene después
«Corregir horarios por el cambio de invierno» ayuda a entender por qué cambió una línea. «Actualizar archivo» no. Agrupá cambios por propósito para que otra persona pueda explicar, revisar o revertir una decisión sin desenredar ediciones ajenas.
→ Una decisión entendible es una unidad útil de historia.

03. Tres lugares para un cambio
=================================================================
Editar, preparar y registrar son decisiones separadas.

Tu mesa de trabajo
El working tree es el conjunto de archivos que editás ahora. Ana corrige los horarios y empieza una nota incompleta. Ambos cambios están en su mesa. Quiere registrar solo la corrección terminada.
→ Lo editado puede ser más que lo que conviene registrar.

La próxima instantánea
El staging area, también llamado index, contiene lo elegido para el próximo commit. Es una versión preparada, no solo una lista de nombres de archivo. Si preparás 10:00 y después editás el archivo a 11:00, lo preparado sigue siendo 10:00 hasta que lo prepares de nuevo.
→ Preparar captura contenido de ese momento.

Leé ambas comparaciones
El diff común compara tus archivos de trabajo con el index. El diff preparado compara el index con el commit actual. En el ejemplo, uno muestra 10:00 a 11:00; el otro, 09:00 a 10:00. Un commit normal registra el index.
→ Preguntá qué dos estados usa la comparación.

04. Las ramas son nombres que se mueven
=================================================================
Una línea de trabajo paralela empieza con un puntero.

Dos nombres, un punto de partida
main nombra nuestra historia aceptada. Crear hours desde main le da otro nombre al mismo commit. Crear esa rama no requiere una versión histórica nueva. Los nombres pueden moverse de forma independiente al seguir trabajando.
→ Una rama apunta a un commit; no es una copia de carpeta.

¿Adónde va el próximo commit?
HEAD suele identificar la rama actual. Con hours seleccionada, un commit nuevo adelanta hours y deja main donde estaba. Cambiar de rama selecciona otra historia y actualiza archivos cuando hace falta; Git puede negarse si sobrescribiría ediciones locales.
→ Conocé tu rama actual antes de registrar trabajo.

Los nombres son acuerdos
main es una convención, no una garantía incorporada de calidad. Una rama llamada production puede contener trabajo roto. El equipo decide qué significa cada rama y qué evidencia necesita para avanzar. Una rama no aísla permisos de acceso.
→ El nombre comunica intención; una política la hace cumplir.

05. Merge: unir historias
=================================================================
Combiná trabajo usando su punto de partida común.

Un camino ya está dentro del otro
Si main no avanzó desde que se creó hours, main puede avanzar hasta la punta de hours. Este fast-forward no necesita un merge commit nuevo. Los commits existentes ya describen un camino continuo.
→ Fast-forward mueve un nombre por historia existente.

Avanzaron dos caminos
Ana cambia los horarios mientras Bruno agrega un archivo de contacto. Las ramas divergen. Git usa un ancestro compartido y ambas puntas para combinar cambios. Un merge commit habitual registra el resultado con ambas puntas como padres.
→ Un merge conserva ambas líneas de ascendencia.

El texto encaja; el comportamiento quizá no
Ana cambia la apertura a las 10:00. Bruno anuncia un taller a las 09:30 en otro archivo. Git puede combinar esas ediciones sin conflicto textual. La guía resultante igual se contradice. Probá el significado después de combinar el texto.
→ Sin conflicto textual no significa sin problema.

06. Los conflictos son preguntas sin responder
=================================================================
La herramienta encuentra ambigüedad; las personas deciden el significado.

Una línea, dos intenciones
Desde el mismo inicio a las 09:00, Ana escribe 10:00 y Bruno 11:00. Ambos cambian la misma línea. Git no puede decidir el horario de la biblioteca. Un conflicto señala una elección que la integración automática de texto no puede hacer con seguridad.
→ Un conflicto es información, no prueba de que se perdió historia.

Importan tres versiones

07. Remotos y copias independientes
=================================================================
Un remoto es una dirección con un apodo local.

Clonar crea otro repositorio
Un clon habitual copia historia del repositorio y prepara una versión de trabajo. No es una carpeta compartida en vivo. Editar el clon no edita el origen. Clones especiales superficiales o parciales pueden copiar menos; nuestros experimentos usan clones completos habituales.
→ Un clon es un lugar independiente para trabajar.

origin es un apodo
La configuración de un remoto asocia un nombre como origin con una dirección. Puede estar en GitHub, otro servidor o incluso un disco local. Llamarlo origin no lo convierte en el proyecto oficial ni da permiso para escribir.

Tu última observación

08. Fetch, integrar, publicar

No hay una única operación mágica de «sincronizar».

Enterate de qué cambió

Elegí la integración

09. Fork, clon y rama
=================================================================
Tres formas de separación responden a necesidades distintas.

Una rama queda en un repositorio
Una rama le da nombre a una línea de trabajo dentro de un repositorio. Integrantes con acceso adecuado pueden publicar ramas en el mismo repositorio de GitHub. Sirve cuando el equipo comparte la administración del repositorio.
→ Una rama nueva no es un dueño nuevo.

Un fork crea otro lugar alojado
Un fork de GitHub es otro repositorio vinculado al original en una red de forks. Podés proponer un cambio desde una rama de tu fork sin permiso de escritura en el original. La disponibilidad y los permisos dependen de la visibilidad y las políticas de la organización.
→ Poder proponer no implica poder integrar.

Un clon te da un lugar local
Podés clonar tu fork y configurar origin hacia él y upstream hacia el original. Esos nombres son convenciones. Actualizar tu fork o clon no actualiza automáticamente el proyecto original.
→ Dibujá los repositorios antes de dibujar las ramas adentro.

10. Issues: acordar el problema

Problema y solución evolucionan por separado

11. Pull requests: proponer una diferencia
=================================================================
Una propuesta conecta una rama de origen, un destino y una conversación.

Base y head
La base es la rama de destino; head es el origen del trabajo propuesto. En Faro, base main y head winter-hours significa «incorporar estos horarios a main». Invertir la comparación hace otra pregunta.
→ Nombrá origen y destino antes de revisar.

Una propuesta puede seguir cambiando
Abrir un pull request no hace el merge. Commits nuevos en su rama de origen pueden actualizar la propuesta. La conversación de revisión se refiere entonces a evidencia que evoluciona. Un borrador comunica que la propuesta todavía está en preparación.
→ Un pull request es una conversación alrededor de un cambio.

Hacé revisable la diferencia
Contá el problema, qué cambia, cómo lo comprobaste y qué issue lo motivó. Leé los archivos cambiados antes de pedir revisión. Una propuesta chica sobre horarios es más fácil de razonar que otra mezclada con formato ajeno al problema.

12. Revisión: evidencia y acuerdo
=================================================================
Una señal verde responde una pregunta específica, no todas.

Leé como quien mantendrá el proyecto
Revisá propósito, contenido cambiado y evidencia. Preguntá si los horarios son correctos y si otro aviso los contradice. Un comentario útil nombra una preocupación concreta y su consecuencia, en vez de expresar solamente gusto.
→ Revisá la decisión, además de la ortografía.

Controles humanos y automáticos
Una revisión puede comentar, aprobar o pedir cambios. Una prueba automática verifica afirmaciones elegidas por su autor. Ninguna demuestra por sí sola todos los requisitos. En Faro, un script puede encontrar «10:00», pero una persona debe confirmar que sea la hora pretendida.
→ Preguntá qué cubre realmente cada evidencia.

La propuesta avanzó
Un commit posterior puede cambiar lo revisado. Que una aprobación siga habilitando el merge depende de las reglas del repositorio. El autor no puede aprobar su propio pull request. Practicar solo permite revisar tu diff, pero no una aprobación independiente.

13. Mismos archivos, historias distintas

Merge, squash y rebase conservan distintos tipos de contexto.

Conservá el punto de encuentro

Conservá la decisión resultante
Squash registra el cambio combinado de la propuesta como un commit nuevo en el destino. Los commits originales de la rama no quedan como ancestros por esa integración. Puede facilitar la lectura de main cuando una propuesta tiene muchas correcciones temporales.
→ Squash intercambia historia intermedia por un resultado coherente.

Reaplicá sobre otra base
Rebase reaplica cambios sobre otra base y produce commits nuevos cuando cambia la ascendencia. Coordiná antes de reescribir trabajo que otros usan. Rebase-and-merge en GitHub crea SHAs nuevos; su comportamiento no es idéntico a todo rebase local. Elegí según la historia que querés mantener.

Una edición pendiente, un cambio preparado y un commit compartido son problemas distintos. Restaurar un archivo de trabajo puede descartar trabajo sin registrar. Quitar un cambio de preparación puede dejar la edición intacta. Indicá el resultado deseado antes de elegir una operación.
→ «Deshacer» es un objetivo, no una operación universal.

Agregá una decisión correctiva
Revert registra un commit nuevo que invierte el efecto de uno anterior. El original queda en la historia y explica lo ocurrido. Revertir puede generar conflictos si trabajo posterior depende del contenido. Sirve para trabajo publicado porque no exige mover la rama compartida hacia atrás.
→ Corregir la historia y borrar historia son intenciones distintas.

Mover una referencia
Reset puede mover la rama actual y, según el modo, cambiar el index y los archivos. Un hard reset puede descartar ediciones. Los reflogs registran movimientos locales de referencias por un tiempo limitado; no son respaldo permanente. El lab usa solo un soft reset aislado para comparar mecanismos.

15. Actions: evidencia automática
=================================================================
Un evento inicia trabajo cuyo resultado tiene alcance definido.

Evento, workflow, job, step
Un workflow describe automatización. Un evento como actualizar un pull request puede dispararlo. Los jobs corren en runners, las máquinas que ejecutan el trabajo. Los steps de un job van en secuencia; los jobs pueden ser independientes o tener dependencias. Los nombres describen un flujo de trabajo.
→ Seguí por qué empezó la ejecución y qué ejecutó realmente.

Un ejemplo que falla con sentido
El ejemplo verifica que README contenga 10:00. Primero probá 09:00 y observá la falla; después corregí el texto. Una ejecución verde indica que esa afirmación pasó para la revisión de esa ejecución. No establece el horario del mundo real ni despliega la guía.
→ Un control útil puede demostrar falla y éxito.

La automatización tiene autoridad
Un workflow ejecuta código con permisos y posiblemente secretos. Limitá permisos y revisá cambios a workflows como cualquier código. Una contribución no confiable no debe obtener secretos privilegiados por abrir una propuesta. El curso usa un workflow chico con permiso de solo lectura del contenido.
→ La automatización es código y autoridad, además de una señal verde.

16. Reglas: convertir acuerdos en condiciones

¿Quién puede hacer qué?

Exigí evidencia en el destino

La excepción forma parte de la regla
Los permisos de bypass, activación de reglas y patrones de rama afectan el cumplimiento de la regla. Una configuración que alcanza otra rama no protege main. Revisá quién puede omitir un requisito y por qué; describí el límite real en lugar de decir solamente «protegido».

17. Tags, releases y despliegues
=================================================================
Nombrar una versión, explicarla y ejecutarla son eventos distintos.

Un nombre para un punto elegido
Un tag como v1.0 nombra un punto elegido de la historia. A diferencia de una rama, no avanza automáticamente con commits nuevos. Los equipos suelen tratar los tags publicados como acuerdos estables, aunque Git tenga operaciones para moverlos o borrarlos. Un tag anotado es un objeto con autor, fecha y mensaje; un tag ligero es solo un nombre.
→ La estabilidad es una política de publicación, no una imposibilidad de cambio.

Explicá la versión entregada
Una release de GitHub se basa en un tag y puede agregar notas y archivos descargables. Explicá cambios visibles, límites conocidos y consideraciones para actualizar. El tag nombra el punto de código; la release agrega contexto de entrega.
→ Un número de versión sirve menos sin su significado.

Ejecutar es otro paso
Un despliegue coloca un artefacto elegido en un entorno. Publicar una release no prueba por sí solo que se desplegó algo; una automatización configurada aparte puede conectarlos. Registrá revisión desplegada y entorno para poder responder qué se está ejecutando.
→ Versión de código, artefacto descargable y sistema en ejecución son distintos.

18. La historia recuerda lo que quitás
=================================================================
Ignorar un archivo y eliminar una exposición son problemas distintos.

Elegí qué pertenece a la historia
Archivos generados, configuración local y credenciales normalmente no pertenecen a una historia de código compartida. Una regla .gitignore indica qué archivos sin seguimiento suele ignorar Git. No deja de seguir automáticamente un archivo ya registrado.
→ Las reglas de ignorar actúan sobre la selección, no sobre el pasado.

Borrar es una instantánea nueva
Borrar un archivo y registrar la eliminación lo quita de la instantánea nueva. Commits anteriores todavía pueden contenerlo. Un repositorio privado también tiene lectores y posibles copias; la privacidad no reemplaza mantener credenciales fuera de la historia.
→ Ausente ahora no significa ausente de la historia.

Atendé primero la credencial
Si se expone una credencial real, revocala o rotala primero. Después seguí el proceso documentado del proveedor y coordiná clones y forks afectados. Reescribir un repositorio no garantiza quitarla de toda copia. El lab usa solo un marcador inequívocamente ficticio.
→ Detené la autoridad del secreto antes de limpiar sus rastros.
